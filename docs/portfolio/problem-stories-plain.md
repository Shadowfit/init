# 포폴: 문제 이야기 — 쉬운 말 판

작성: 2026-09-10
용도: **비전공자·비개발 면접관도 읽히는 형태**로 문제해결 경험을 옮긴 판. 기술 용어로 압축된 원본은
[`./problem-solving-log.md`](./problem-solving-log.md)(카드 #1~#11)와 [`./realmysql-experiments.md`](./realmysql-experiments.md)(실험 조건)에 있다.
이 문서는 **새 사실을 만들지 않는다** — 전부 그 두 문서와 `docs/decisions/`에 근거가 있는 것만 옮겼다.

## 0. 이 문서의 규칙 (먼저 읽을 것)

**① 순서를 바꿨다.** 보통은 「현상 → 원인 → 조치 → 수치」로 쓰는데, 여기서는 그 앞에 한 칸을 더 뒀다 —
**「왜 처음엔 그렇게 돼 있었나」**. 그 칸이 비면 모든 이야기가 "실수 하나 고쳤습니다"로 읽힌다.
대부분의 경우 **그때는 그게 맞는 설계였고, 조건이 바뀐 것**이다. 그 차이를 말하는 게 이 문서의 목적이다.

**② 수치는 조건과 함께만 쓴다.** 이 프로젝트의 로컬 측정 박스는 물리 2코어라 **절대 처리량을 못 잰다.**
그래서 "몇 초 걸리던 게 몇 밀리초가 됐다" 식의 절대 시간은 대부분 인용 금지이고, 배수·델타만 남긴다.
각 카드의 `조건` 줄이 그걸 지킨다.

**③ 안 한 것은 안 썼다.** 안 잰 항목은 «미측정»으로 남긴다. 비어 있는 칸을 그럴듯한 숫자로 채우지 않는다.

**④ 작업 주체.** `backend/` 커밋 62개 중 55개가 본인(Khyojae)이다. 이 문서의 카드는 그 범위다 —
AI 서버(FastAPI) 쪽 코드 작업은 팀원과 경계가 섞여 있어 여기에 넣지 않았다.

## 1. 관리자 화면을 만들려다 만난 것 — 같은 표를 읽는 사람이 둘이 됐다

**한 줄(기술 용어)**: 세션 인덱스가 전부 `member_id` 선두라 관리자 목록 조회에 탐색용으로 안 듣는다 → `(status, start_time)`·`users(created_at)` 추가.

**무슨 일이었나.**
관리자 화면에 회원 목록을 20명씩 보여주려고 했습니다. 그런데 화면 한 장을 그리려고 **회원 20만 명을 전부 읽고
그중 89%를 버리고** 있었습니다. 세션 목록도 100만 건을 처음부터 끝까지 훑은 뒤 필요한 27만 건만 남겼습니다.
날짜순으로 보여줘야 하는데, 읽고 나서 **따로 줄을 세우는 작업**도 매번 다시 했습니다.

**왜 그렇게 돼 있었나 — 이게 이 카드의 핵심입니다.**
빠뜨린 게 아닙니다. 그때까지 이 서비스의 모든 조회는 **"내 운동 기록", "내 세션"**이었습니다.
그래서 데이터를 찾아가는 길(인덱스)을 전부 **회원 번호부터** 시작하도록 만든 것이 옳은 설계였습니다.
그런데 관리자 목록은 회원 번호를 **안 주고** 전체에서 상태·기간으로 거릅니다. 길의 첫 갈림길이 안 맞으니
그 길을 탐색에 쓸 수가 없습니다.

즉 **같은 데이터를 읽는 주체가 둘(사용자 축 / 관리자 축)로 갈린 순간**, 하나의 인덱스 전략으로 덮이지 않는
구간에 들어선 것입니다. 이건 쿼리를 어떻게 조립하느냐(QueryDSL)로 풀리는 문제가 아닙니다 — 조립 방식은
실행 계획을 바꾸지 않습니다.

**무엇을 했나.**
관리자 조회 전용 인덱스 2개를 추가했습니다. 컬럼 순서는 **등치 조건을 앞에, 범위·정렬 조건을 뒤에** 뒀습니다
(`status` → `start_time`). 그래야 해당하는 행이 한 덩어리로 뭉치고, 그 안이 이미 날짜순이라 정렬을 다시 할
필요가 없어집니다. 반대로 뒤집으면 날짜마다 상태가 섞여 있어 범위에 걸린 걸 전부 읽고 나서 걸러야 합니다.

**결과** (2026-08-03 채택 → **rig 결함 3건 정정 후 2026-08-04 재측정**):

| | before | after |
|---|---|---|
| 회원 목록 | 19.9만 행 전수, 그중 **11.11%만 유효**, 별도 정렬 | 10.0만 행 범위 스캔, **100% 유효**, 정렬 불필요 |
| 세션 목록 | 99.5만 행 전수, 그중 **8.33%만 유효**, 별도 정렬 | 27.3만 행 범위 스캔, **100% 유효**, 정렬 불필요 |

- 조건: 회원 20만 / 세션 100만 **스크래치(합성) 테이블**. before 상태에도 실제 인덱스 3종을 재현해
  "관리자 인덱스만 없는 상태"를 비교 대상으로 삼았다.
- 🔴 **응답 시간은 안 쟀다(미측정).** 이 카드가 가진 건 실행 계획의 변화까지다. "몇 초 → 몇 ms"를 말할 수 없다.
- 🔴 **인덱스가 다 고치지도 않았다.** 정렬 비용은 모든 조합에서 사라졌지만 **읽는 양이 준 건 가입일 조건이
  걸린 경우뿐**이고, 남은 진짜 비용은 목록이 아니라 **총건수 쿼리**에 있다 — `LIMIT`이 없어 대부분 조합에서
  20만 행을 끝까지 센다. 이건 페이지 번호 UI를 쓰기로 확정하면서 **요구사항으로 감수**했다.
- 🔴 **쓰기 쪽 대가는 방향조차 관측되지 않아 초판 결론을 철회했다.** 인덱스가 늘면 INSERT가 느려지는 게
  이론인데 이 rig에서는 그게 안 보였다. "안 느려졌다"가 아니라 **"못 쟀다"**로 남긴다.

**말할 때**: "인덱스를 빠뜨렸다가 넣은 게 아니라, **읽는 주체가 하나에서 둘로 늘면서 인덱스 전략이 갈리는
지점**을 만난 겁니다. 그리고 넣어보니 절반만 나았고, 남은 비용은 목록이 아니라 총건수 쪽에 있었습니다."

근거: [`../decisions/admin-page-scope.md`](../decisions/admin-page-scope.md) §4·§4-1·§4-3

## 2. "느릴 것"이라고 적어둔 게 틀렸다 — 재보니 이미 최적이었다

**한 줄(기술 용어)**: "리포트 쿼리가 인덱스 없어 풀스캔" 가설을 `EXPLAIN`으로 폐기 — 이미 covering, `Extra=NULL`.

**무슨 일이었나.**
운동이 끝나면 그 세션의 자세 데이터를 읽어 리포트를 만듭니다. 데이터가 계속 쌓이는 표라서
**"여기가 느려질 것"**이라고 문서에 적어뒀고, 인덱스를 추가할 계획을 세웠습니다.

**그런데 재보니 틀렸습니다.**
이 조회는 이미 필요한 길이 나 있었고, 정렬도 그 길 순서 그대로라 **추가 작업이 아예 없었습니다.**
게다가 이 조회는 항상 **한 세션 안에서만** 데이터를 찾기 때문에, 표 전체가 아무리 커져도 읽는 양이 안 늘어납니다.
**추가할 인덱스가 없었습니다.**

**대신 "없었다면 어땠을까"를 만들어 봤습니다.**
인덱스를 일부러 못 쓰게 강제해 같은 조회를 돌렸습니다.

- 실제 크기의 데이터(2.1KB JSON, 412.5만 행)에서 인덱스 사용 **약 3.0ms** ↔ 강제 전수 스캔 **약 27.1초** → **약 9,000배**
- 같은 행 수라도 **내용이 가벼운 더미 데이터면 660배**로 줄어든다 — 행이 작으면 전수 스캔이 밟는 페이지가 적어져
  차이가 과소평가된다. **payload 크기가 "인덱스 유무의 체감 차이" 자체를 증폭시킨다.**

- 조건: 2026-07-20 로컬(물리 2코어) · `SET profiling`(DB 내부 타이밍, 네트워크 왕복 오염 배제).
- 🔴 **"인덱스를 추가해서 9,000배 빨라졌다"가 아니다.** 인덱스는 원래부터 있었고, 이건 **반사실 대조**다.
- 🔴 예전에 쓰던 «7,000배»는 다른 실험 수치를 짜깁기한 추정이라 **폐기**했다.
- ⚠️ 이 재측정판은 ad-hoc 실행이라 **재현 스크립트가 저장소에 없다.**

**말할 때**: "인덱스를 넣기 전에 이미 최적인지부터 쟀고, **넣을 게 없다는 결론**이 나왔습니다.
대신 없었다면 어땠을지를 대조로 만들어서, 이 인덱스가 하는 일의 크기를 숫자로 남겼습니다."

근거: [`./realmysql-experiments.md`](./realmysql-experiments.md) ① · [인용 조건](./realmysql-experiments.md#index-9000x)

## 3. 진짜 병목은 "찾는 속도"가 아니라 "들고 오는 양"이었다

**한 줄(기술 용어)**: 리포트 precompute의 full-entity 로드 → projection DTO. DB→앱 payload −98.7%.

**무슨 일이었나.**
2번에서 "찾아가는 길은 이미 최적"이라는 결론이 났습니다. 그럼 무거운 건 뭐냐 — **들고 오는 짐**이었습니다.
자세 데이터 한 줄마다 관절 좌표가 통째로 들어 있는데(약 2.3KB), 리포트를 만들 땐 그중 **몇 개 값만** 씁니다.
그런데 코드는 매번 **전부 다** 들고 왔습니다.

**왜 그렇게 돼 있었나.**
객체를 통째로 불러오는 게 기본 동작이라 그렇습니다. 그리고 그 큰 값은 데이터 페이지 안에 못 들어가
**따로 떨어진 곳에 저장**되기 때문에, 통째로 읽으면 그때마다 별도로 한 번 더 찾아가야 합니다.
필요한 값만 지정해서 읽으면 그 왕복이 통째로 사라집니다.

**결과** (2026-06-02 로컬 412만 행, warm · 2026-07-15 AWS 1억 행 실제 JSON 재검증):

| | before | after |
|---|---|---|
| DB→앱으로 오는 데이터 | 1,716.8 KB | **22.4 KB (−98.7%)** |
| 쿼리 시간 | — | 로컬 **8배**, AWS 1억 행 **29~41배** |

- 🔴 **«−98.7%»는 DB→앱 구간이다. API 응답 크기가 아니다** — API 응답은 안 변하는 게 정상이고,
  그걸 "효과 없음"으로 읽으면 틀린다.
- 🔴 **"리포트가 빨라졌다"가 아니다.** 이 조회를 부르는 건 세션 종료 시 **세션당 1회 도는 비동기 잡**이라
  사용자는 원래 이 지연을 못 느낀다. 정직한 프레임은 **"반복해서 도는 무거운 잡의 I/O·버퍼풀 점유를 낮췄다"**.
  정상 조회 경로는 이 쿼리를 아예 안 부른다(코드 판독, 미측정).
- 규모가 커질수록 배수가 **커졌다**(8배 → 29~41배). 표가 커져 캐시에 덜 걸리니 그 왕복을 피하는 이득이 커진 것이다.
- ⚠️ 측정 시점은 3컬럼, **현재는 4컬럼**이다 — 4컬럼에서의 절감률은 **미측정**.
- ⚠️ 첫 측정은 **2배**로 나왔었다. 원격 접속 왕복(~50ms)이 100ms 미만 차이를 덮어버린 것이고,
  DB 내부 타이밍으로 바꿔 재서 진짜 값을 찾았다. **첫 숫자를 그대로 안 믿은 게 이 카드의 절반이다.**

근거: [인용 조건](./realmysql-experiments.md#projection-98-7)

## 4. 25번 갈 것을 1번에 — 데이터 적재

**한 줄(기술 용어)**: JPA `saveAll`이 `@GeneratedValue(IDENTITY)` 때문에 batch 미발동 → `JdbcTemplate.batchUpdate` multi-row INSERT.

**무슨 일이었나.**
운동 중 자세 데이터가 묶음으로 들어옵니다. 한 묶음을 저장하는데 **묶음 안의 건수만큼 DB를 왕복**하고 있었습니다.
25건이면 25번 갔습니다.

**왜 그렇게 돼 있었나.**
"묶어서 보내라"는 설정은 켜져 있었습니다. 그런데 **DB가 번호를 매겨주는 방식**을 쓰고 있어서,
저장하기 전엔 번호를 알 수 없고 → 번호를 알아야 다음 단계로 가니 → **묶기가 원천적으로 막혀** 있었습니다.
설정값을 아무리 바꿔도 안 되는 구조였습니다.

**무엇을 했나.** 그 계층을 우회해 **한 문장으로 여러 건을 한꺼번에** 넣도록 바꿨습니다. 25번 → 1번.

**결과** (2026-05-31 로컬):
- 처리량 **+99%**, 응답 중앙값 **−64%**, 상위 1% 지연 **−37%**
- 🔴 **절대 처리량(RPS)은 인용 금지** — 측정 박스가 물리 2코어라 절대값이 의미 없다. **델타만** 쓴다.
- 조건: 워밍업 60초 폐기 후 동시성 5→100 ramp. 같은 절차끼리만 비교.

**말할 때**: "설정으로 안 풀리는 이유가 있었습니다 — 키 생성 방식이 묶기를 막고 있었고,
그래서 그 계층 아래(드라이버 레벨)에서 푸는 게 정석입니다."

근거: [`./problem-solving-log.md`](./problem-solving-log.md) #1

## 5. 한 사람이 동시에 두 개의 운동을 시작할 수 있었다 — 세 번 만에 닫힌 구멍

**한 줄(기술 용어)**: check-then-act TOCTOU → generated column + UNIQUE 시도(errno 1215로 차단) → `@Lock(PESSIMISTIC_WRITE)`로 해결.

**무슨 일이었나.**
사람은 물리적으로 두 운동을 동시에 못 합니다. 그런데 휴대폰을 두 대 쓰거나 네트워크가 느려 재시도가 걸리면,
**한 사람에게 진행 중인 운동 세션이 두 개** 생길 수 있었습니다. 그러면 그날의 집계가 어긋납니다.

**1차 시도 — 확인하고 만들기.** "이미 진행 중인 게 있나?" 물어보고 없으면 만들었습니다.
**이게 안 됩니다.** 두 요청이 거의 동시에 오면, 둘 다 아직 **상대가 만든 걸 볼 수 없는 시점**에 질문하기 때문에
둘 다 "없다"는 답을 받고 통과합니다. 격리 수준을 올려도 마찬가지입니다 — 아직 확정 안 된 데이터는 어차피 안 보입니다.

**2차 시도 — DB가 아예 못 만들게.** "진행 중일 때만 회원 번호가 채워지는 칸"을 만들고 거기에 유일성 제약을
걸려고 했습니다. 설계상으로는 깔끔했는데, 실제로 적용하니 **DB가 거부했습니다**(`ERROR 1215`).
회원이 삭제되면 연쇄 삭제되는 컬럼이라, 그 값을 재료로 자동 계산 칸을 만들 수 없다는 제약이 있었습니다.
**설계 단계에선 안 보였고 실제로 적용해봐야 나온 제약입니다.**

**3차 — 최종.** 세션을 만들기 직전에 **그 회원 한 명을 잠그고**, 잠근 상태에서 확인 → 생성하도록 했습니다.
스키마 변경 없이 구멍이 닫혔습니다. 세션 생성은 사람이 연타하는 화면이 아니라 잠금 비용도 무시할 만합니다.
이 프로젝트에서 **비관적 잠금을 처음 쓴 자리**입니다.

**결과**: 같은 회원이 정확히 동시에 두 개를 시도 → **정확히 1개만 성공**, 나머지는 409로 거절
(`SessionCreateConcurrencyTest`로 검증).

**말할 때**: "제약으로 표현할 수 있으면 제약이 먼저입니다 — 모든 경로에서 보장되니까요.
그런데 **스키마 제약이 기술적으로 막히면 잠금이 유일한 대안**이 됩니다. 이번이 그 경우였습니다."

근거: [`./realmysql-experiments.md`](./realmysql-experiments.md) ③(d)

## 6. 운동은 끝났는데 결과가 영영 안 오는 경우

**한 줄(기술 용어)**: dual-write(트랜잭션 커밋 + gRPC 통보) → 트랜잭셔널 아웃박스 + 지수 백오프.

**무슨 일이었나.**
운동을 끝내면 서버가 분석 서버에 "이 세션 끝났으니 결과 정리해줘"라고 알립니다.
그런데 **그 알림 한 번이 실패하면 결과가 영영 회수되지 않았습니다.** 사용자 입장에서는 운동은 다 했는데
리포트가 안 나오고, 나중에 시스템은 그 세션을 **실패로 잘못 분류**합니다.

**왜 그렇게 돼 있었나.**
"DB에 저장" 과 "상대에게 알림"이 **서로 다른 두 시스템**이라 하나로 묶을 수가 없었습니다.
저장은 됐는데 알림만 실패하는 순간이 존재하고, 그때 알림은 그냥 사라졌습니다.
사라지는 길이 하나가 아니라 **둘**이었습니다 — 전송이 실패해서 사라지는 길, 그리고 상대 서버가 아프다고 판단해
호출 자체를 건너뛸 때 사라지는 길.

**무엇을 했나.**
알림을 "보내는 행위"가 아니라 **"보내야 할 일감"으로 같은 DB에 함께 저장**했습니다.
저장이 성공하면 일감도 반드시 남고, 별도 발행기가 성공할 때까지 재시도합니다.

**결과** (2026-07-29, 전체 스택을 실제로 띄우고 분석 서버를 인위적으로 죽여 측정):

| 시나리오 | 무슨 일이 벌어졌나 |
|---|---|
| **네트워크 단절** | 일감이 살아남고 재시도 간격이 8초→16초→32초로 정확히 2배씩 증가 → 복구 후 10초 안에 전송 완료, 세션 정상 종료 |
| **분석 서버 재시작** | 재시도 없이 **즉시 실패 확정** — 상대가 그 세션을 아예 모르므로 재시도가 원리상 무의미. 세션도 6초 만에 실패 처리(예전엔 30분 넘게 기다렸다) |
| **회로 차단 상태** | 일감을 **버리지 않고** 보류 → 복구 후 전송. 예전 설계에서 알림을 버리던 구간이 사라졌다 |

- 세션 종료 요청 자체는 **HTTP 200을 59~135ms**에 돌려줬다 — 분석 서버가 얼어붙어 있어도 사용자는 안 기다린다.
- 🔴 **"유실 0"은 통보의 *전달*에 한한다.** 분석 서버가 재시작되면 통보가 가도 **분석 결과 자체는 유실**된다.
  전달과 결과 보존은 별개 축이고, 이 설계는 앞쪽만 보장한다.
- ⚠️ "Kafka 쓰면 되잖아"는 이 문제를 **안 푼다** — "DB 저장 + 큐에 넣기"가 여전히 두 시스템이다.
  브로커는 아웃박스가 공급하는 하류이지 대안이 아니다. 이 프로젝트는 통보 대상이 하나라 브로커를 생략했다.

근거: [`../decisions/outbox-reliable-messaging.md`](../decisions/outbox-reliable-messaging.md) §1·§6

## 7. 오래된 데이터를 버리는 값 — 18.6분 vs 1.8초

**한 줄(기술 용어)**: `pose_data` Range 파티션. `DELETE WHERE` 대비 `DROP PARTITION` 625배(행당 정규화 570배).

**무슨 일이었나.**
자세 데이터는 리포트를 만들고 나면 원본을 오래 들고 있을 이유가 적습니다. 그런데 오래된 것을 지우려면
**한 줄씩 지워야** 했고, 830만 건에 **18.6분**이 걸렸습니다. 게다가 다 지운 뒤에도 **디스크 952MB가 그대로**
남았습니다 — 안이 비었을 뿐 파일은 그대로입니다.

**무엇을 했나.**
데이터를 날짜 구간별로 **서랍을 나눠** 담도록 바꿨습니다. 그러면 만료는 "한 줄씩 지우기"가 아니라
**서랍째 버리기**가 됩니다.

| 방식 | 행수 | 소요 | 디스크 |
|---|---|---|---|
| 한 줄씩 삭제 | 8,301,450 | **18.6분** | 952MB 그대로 |
| 서랍째 버리기 | 7,560,000 | **1.8초** | ~910MB 즉시 회수 |

**여기서 정직해야 하는 것들:**
- 🔴 **두 팔의 행수가 다르다.** 625배는 정규화 전 값이고, 행당으로 맞추면 **570배**다.
- 🔴 **서랍째 버리기도 공짜가 아니다.** 1.8초의 대부분은 ~910MB 파일 삭제 I/O다. "행 단위 비용이 없다"는 뜻이지
  진짜 O(1)이 아니다. (빠른 스토리지에서는 실제로 156~264MB 파티션이 18~21ms에 지워졌다.)
- 🔴 **조회 이득은 0이다.** 서랍을 나누면 조회도 빨라진다고들 하는데 **이 프로젝트에선 아니다** —
  세션 단위 조회는 날짜 조건이 없어서 **14개 서랍을 전부 뒤진다**. 오히려 미세하게 손해다.
- 🔴 그래서 **파티션의 정당화는 조회가 아니라 보존정책(TTL) 하나뿐**이다.
  "1억 행이니까 파티션"이 아니라 "**버리는 방식 때문에** 파티션"이다.
- 🔴 **서랍으로 바꾸는 전환 자체는 96분**이 걸렸다(1억 행 전체 재작성, 그동안 테이블 잠김).
  운영이라면 처음부터 파티션 테이블로 만들거나 무중단 전환 도구를 써야 할 이유다 —
  그리고 그 "써야 할 이유"도 나중에 실측으로 바꿨다(다음 카드).
- 조건: 2026-06-03 로컬 · 더미 JSON. **절대 시간은 하드웨어 종속이라 「운영에서 N분」으로 인용 금지.**

근거: [인용 조건](./realmysql-experiments.md#drop-partition-625x)

## 8. "무중단으로 하세요"를 권고에서 실측으로 바꿨다

**한 줄(기술 용어)**: 차단 `ALTER` ↔ `pt-osc` 대조. DDL 소요는 1.64배 느리지만 **최대 쓰기 정지가 최소 187배 짧다.**

**무슨 일이었나.**
7번의 "운영이라면 무중단 도구를 써야 한다"는 문장은 **교과서에서 가져온 권고**였습니다. 실제로 재보기로 했습니다.
같은 조건에서 두 방식을 교대로 6판 돌렸습니다(순서 효과를 상쇄하도록 `A B B A A B`, 앞에 버림 2판).

| | 그냥 바꾸기 | 무중단 도구 |
|---|---|---|
| 작업 시간 | 68~70초 | 112~114초 (**1.64배 느림**) |
| **쓰기가 멈춘 최대 시간** | **68~69초** | **30~364 ms** (**최소 187배 짧음**) |
| 그동안 성공한 쓰기 | 18회 | 553~558회 |
| binlog 증가 | 0 MB | **441 MB** |
| 디스크 최대 | 2,359 MB | 2,348 MB |

**여기서 나온 발견 두 개가 이 카드의 값입니다:**
- ⭐ **"느리지만 조금씩은 통과"가 아니었다.** 그냥 바꾸기의 최대 정지 시간(≈69초)이 작업 시간(≈69초)과 거의 같다 —
  **전 구간 차단**이다. 에러는 6판 모두 0이었으니 쓰기는 죽은 게 아니라 **줄 서서 기다린** 것이고,
  그래서 이 정지값이 의미를 갖는다.
- ⭐ **"무중단 도구는 복사본을 만드니 디스크를 더 쓴다"가 여기선 틀렸다.** 두 팔의 디스크 사용이 같다 —
  그냥 바꾸기도 어차피 전체 사본을 만들기 때문이다. **무중단 도구의 진짜 대가는 디스크가 아니라 binlog**(441MB)이고,
  그건 복제 지연으로 이어지는 비용이라 다른 질문이 된다.
- ⚠️ 애초에 **선택지가 둘뿐이었다** — 이 종류의 변경은 서버가 온라인 방식을 거절한다(errno 1845).
  "온라인 DDL 쓰면 되잖아"가 성립하지 않는 경우다.
- 조건: 2026-08-12 EC2 m6i.xlarge · 1,000만 행. **7번의 로컬 96분과는 규모·기계가 달라 직접 비교가 아니다.**

근거: [`../decisions/online-ddl-vs-blocking-alter.md`](../decisions/online-ddl-vs-blocking-alter.md), [결과](../../loadtest/results/online-ddl-aws-2026-08-12/README.md)

## 9. 뒤쪽 페이지로 갈수록 느려지는 이유

**한 줄(기술 용어)**: offset 페이지네이션은 O(N)(스캔 후 폐기) → keyset(cursor)으로 전환, 깊이 무관 평탄.

**무슨 일이었나.**
목록에서 뒷페이지로 갈수록 느려집니다. 흔히 "데이터가 많아서"라고 하는데 정확한 이유는 다릅니다 —
**"100번째 페이지를 보여줘"는 앞의 99페이지 분량을 전부 읽고 버린 뒤 100번째를 주는 방식**이기 때문입니다.
읽고 버리는 양이 페이지 깊이에 정비례합니다.

**무엇을 했나.**
"몇 번째부터"가 아니라 **"이 지점 다음부터"**로 물어보게 바꿨습니다. 그러면 깊이에 상관없이 바로 그 자리로 갑니다.

| 깊이 | 기존 방식 | 바꾼 방식 | 배수 |
|---|---|---|---|
| 1만 | 3.04 ms | 0.079 ms | 39배 |
| 10만 | 27.7 ms | 0.035 ms | 798배 |
| 1,000만 | 2,933 ms | 0.046 ms | 64,039배 |
| 5,000만 | 25,963 ms (26초) | 0.053 ms | **489,868배** |

- 🔴 **«489,868배»는 깊이 5,000만 한 점의 값이다.** 얕으면 배수가 급격히 작아진다(10만 → 798배, 0 → 1배).
  "페이지네이션 바꿨더니 49만 배"로 인용하면 틀린다.
- ⭐ **캐시에 다 올라와 있어도 선형 저하가 유지된다** → 병목은 디스크가 아니라 **읽고 버리는 CPU** 자체다.
  이걸 확인했기 때문에 "메모리를 늘리면 되지 않나"라는 답이 닫힌다.
- 실제 크기의 데이터에서는 더 나빠진다 — 같은 깊이에서 더미 26초 ↔ 실제 JSON **941초**(약 36배).
  행이 무거우면 읽고 버리는 페이지 수가 그만큼 늘기 때문이다.
- 조건: 2026-06-03 로컬 1억 행 더미 JSON · warm 3회째 · `EXPLAIN ANALYZE`.
  AWS 재검증판의 **keyset 절대값(54~56ms)은 인용 금지** — 원격 접속 왕복이 바닥에 깔린 값이다.

근거: [인용 조건](./realmysql-experiments.md#keyset-489868x)

## 10. 측정을 믿기 전에 측정 장치를 믿을 수 있는지 확인한다 (3층)

이 카드는 **세 개를 따로 말하는 것보다 층으로 엮는 게 세다.** 절차 → 데이터 → 장치 순으로 한 층씩 내려간다.

### ① 절차가 틀렸다 — 워밍업
개선안이 **오히려 느리게** 나왔습니다. 원인은 개선안이 아니라 **비교 조건**이었습니다.
기존 것은 58분 동안 데워진 상태였고, 개선안은 켠 직후였습니다. 잰 게 "개선 효과"가 아니라 "워밍업 차이"였습니다.
→ 재빌드 → 차갑게 기동 → **워밍업 60초 폐기** → 리셋 → 측정, 같은 절차끼리만 비교하도록 고정했습니다.

### ② 데이터가 틀렸다 — 분포
필터 조합별 실행 계획을 쟀는데 **"핵심"이라고 지목해둔 조합의 결과가 0건**이었습니다.
계획은 멀쩡해 보였고 스크립트는 매번 성공했습니다.

원인은 데이터를 만드는 두 줄이 **같은 변수의 함수**였다는 것입니다. 회원 번호가 20만 주기이고 상태가 4주기인데
20만은 4의 배수라, **회원 20만 명 중 19만 9,920명(99.96%)이 평생 한 가지 상태의 세션만** 가졌습니다.
검색어에 걸리는 회원 2,000명이 전부 같은 상태라 그 조합은 **구조적으로 0건**이었습니다.

**한 번에 안 고쳐졌습니다.** 해시 함수로 바꿨는데 그것도 틀렸습니다:

| 오프셋 | CRC32 | MD5 | 무작위 기대 |
|---|--:|--:|--:|
| n vs n+1 | 0.0044 | 0.2508 | 0.25 |
| **n vs n+200,000** | 🔴 **0.0000** | 0.2524 | 0.25 |

`0.0000` — **한 회원의 연속된 세션이 절대 같은 상태가 될 수 없습니다.** 종속이 사라진 게 아니라 방향만 뒤집혔습니다.
MD5로 다시 교체했고, 재발 방지로 **시딩 자기검증 7종**을 넣어 하나라도 실패하면 측정을 시작하지 않게 했습니다.

### ③ 장치가 대상을 바꿨다 — 부작용
실행 계획 캡처를 돌릴 때마다 데이터 상태가 조금씩 달라졌습니다.
캡처 장치가 애플리케이션 전체를 띄우는 방식이라, 거기 포함된 **타임아웃 스케줄러가 시딩된 데이터를 실제로 바꾸고**
있었습니다. 1회 실행에 160건, **오염량이 테스트가 도는 시간에 비례**했습니다.
→ 스케줄링을 끌 수 있게 하고(운영 기본값은 켜짐 유지) 캡처 장치에서만 껐습니다.

**말할 때**: "0건을 잡아낸 건 실행 계획이 아니라 **결과값에 대한 의심**이었습니다.
계획만 보면 멀쩡했거든요. 그리고 CRC32로 고친 판도 틀렸는데, **고쳐졌는지를 다시 쟀기 때문에** 드러났습니다.
'고쳤다'고 선언하기 전에 고쳐졌는지 재는 것까지가 수정이라고 봅니다."

## 11. 안 한 결정 하나 — 캐시 서버를 안 넣었다

**무슨 일이었나.**
"조회가 느려질 테니 캐시 서버(Redis)를 넣자"는 압박이 있었습니다.

**판단.**
넣지 않았습니다. 이유는 하나입니다 — **지금 DB가 부족하다는 게 엄격하게 증명된 적이 없기 때문**입니다.
실제로 2번·3번 카드에서 확인된 건 "조회 경로가 느리다"가 아니라 **"들고 오는 양이 많다"**였고,
그건 캐시가 아니라 읽는 방식으로 풀렸습니다.

넣었다면 인프라가 하나 늘고, 원본과 캐시가 어긋나는 문제를 새로 떠안습니다.
**병목을 측정으로 입증한 뒤에 도입하는 게 맞다**고 봤습니다.

근거: [`../decisions/redis-introduction.md`](../decisions/redis-introduction.md)

## 12. 이 문서가 **인용하지 않는** 것 (스스로 거는 제동)

포트폴리오에서 숫자는 쉽게 커진다. 아래는 **이 프로젝트에서 실제로 폐기하거나 조건을 좁힌 인용**들이다.
이 목록이 있다는 것 자체가 이 문서의 신뢰도다.

| 인용 | 왜 안 쓰나 |
|---|---|
| «7,000배»(인덱스) | 다른 실험 수치를 짜깁기한 **추정**이라 폐기. 대조 재측정으로 9,000배를 새로 냈다 |
| «keep-alive가 +38%» | 38,400건 중 38,347건이 조기 실패였다 — **"빨리 실패한 것"**을 개선으로 읽었다 |
| 로그인/조회의 «N초 → N ms» | **이 프로젝트엔 그런 측정이 없다.** 관리자 인덱스 카드는 실행 계획까지만 쟀다 |
| 절대 처리량(RPS) | 로컬 측정 박스가 물리 2코어라 **절대 천장을 못 잰다.** 메커니즘·상대·델타만 신뢰한다 |
| 절대 시간(18.6분·1.8초·96분 등) | 하드웨어 종속. 같은 라운드 안의 **배수**로만 쓴다 |
| «내구성 완화가 −15%» | 4팔×4반복 재현에서 부호도 크기도 안 나왔다 — **1판짜리 잡음**이었다 |
| «300연결에서 커넥션 대기 15» | 3판 재현에서 항상 0. 반복 없는 1판 노이즈였고, 거기서 파생된 개선안 3개도 함께 폐기 |
| 선택도·카디널리티에 의존하는 결론 | 합성 데이터가 **단일 템플릿 복제라 값 분포가 균일**하다. 그 축은 아직 못 잰다 |

## 13. 아직 비어 있는 칸 (다음에 할 것)

- **관리자 조회의 실제 응답 시간** — 실행 계획은 쟀고 시간은 안 쟀다. 반복 포함 라운드가 필요하다(1판짜리는 안 된다).
- **인덱스 6번째의 쓰기 대가** — 방향조차 관측되지 않아 초판 결론을 철회한 상태 그대로다.
- **4컬럼 projection의 절감률** — 측정은 3컬럼 시점 값이다.
- **재현 rig이 없는 «9,000배»** — ad-hoc 실행이라 스크립트가 저장소에 없다.
