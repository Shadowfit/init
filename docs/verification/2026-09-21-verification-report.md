# 2026-09-21 신규 촬영 스쿼트 영상 검증 보고서

작성: 2026-09-21. 대상: `ai-server/sample/`에 새로 촬영된 6개 영상. 목표는 [고정 촬영 조건 스쿼트 피드백 시연 기준](constrained-squat-feedback-demo.md)이 정한 조건에서의 동작·피드백 일치이며, 모든 환경에서의 100% 정확도를 뜻하지 않는다.

## 0. 방법과 중요한 방법론적 교훈

각 영상을 **사람이 먼저** 눈으로 확인했다. `cv2`로 0.13~0.4초 간격(애매한 구간은 0.06~0.2초)으로 프레임을 잘라 라벨을 붙인 대조표 이미지를 만들고, 파일명이나 AI 출력에 의존하지 않고 직접 셌다. 정답은 [`samples/validation/2026-09-21/ground-truth.json`](../../samples/validation/2026-09-21/ground-truth.json)에 남겼다.

**1차 눈 검증 중 실수를 발견하고 정정했다.** `squat_side_01.mp4`에서 상체가 계속 앞으로 숙여져 있어 처음에는 "반복 아님, 7.5초짜리 애매한 동작"으로 판정했다. 그런데 `evaluate_squat.py --trace`가 뽑은 원본 무릎 각도를 보니 무릎은 매 주기 55~100도(바닥)와 150~178도(거의 편 상태) 사이를 정확히 1.8초 간격으로 오가고 있었다 — 상체 숙임 때문에 실루엣만으로는 무릎이 펴졌는지 알아보기 어려웠을 뿐, 실제로는 5회의 진짜 반복이었다. `squat_normal_01.mp4`·`squat_normal_02.mp4`도 같은 이유로 각각 4회·3회로 과소 판정했다가 5회로 정정했다. **이후로는 깊이 판정에서 실루엣(상체 각도)보다 원본 무릎·고관절 각도 수치를 우선했다.** 자세한 정정 과정은 ground-truth.json의 `methodology_note`에 남겼다.

## 3. 실패 원인 분석 (요청된 순서대로)

1. **MediaPipe 관절 visibility** — 6개 영상 모두 사용 가능 포즈 프레임 비율 100%. 원인 아님.
2. **선 자세 calibration** — `negative_01`·`normal_01`·`normal_02`·`front_01`·`side_01`은 정상 성공. `shallow_01`만 늦게(4.02초) 성공했고, 그 전에 일어난 3회는 계산 자체가 시작되지 않아 평가 대상에서 빠졌다(§4).
3. **무릎·고관절 각도** — `front_01`의 놓친 3~4회는 각도 임계값(무릎 ≤115도) 자체가 틀려서가 아니라, 3fps 표본이 실제 최저점을 포착하지 못해 발생했다(아래 4번 참고). 임계값을 낮추는 방식으로는 고치지 않았다 — 다른 영상에서 얕은 동작을 정상으로 오인할 위험이 커지기 때문이다.
4. **골반 수직 이동량** — 관련 없음. 모든 반복에서 `hip_drop`은 이미 최소 기준을 충분히 넘었다(§3 `front_01` 추적표의 `attempt_max_hip_drop` 참고).
5. **하강·하단·상승·기립 상태 전이** — **여기가 핵심 원인이었다.** `normal_01`·`normal_02`에서 반복 사이 정점 체류가 짧을 때(무릎이 편 상태로 관측된 표본이 1개뿐이고 바로 다음 표본에 재하강), 기존 코드는 이를 완료로 확인하지 못하고 **다음 반복과 합쳐서 1회로 과소 계상**했다.
6. **최소 상태 유지 시간** — 근본 원인. `standing_confirm_sec=0.2초`가 3fps 표본 간격(약 0.33~0.4초)보다 짧다. `update()`는 표본이 들어올 때만 호출되므로, 두 번째 표본이 오기 전에는 어떤 지속시간도 0.2초보다 더 잘게 관측할 방법이 없다. 기존 코드는 "처음 서 있는 것으로 관측된 표본"에서는 절대 확정하지 않고 반드시 **다음 표본에서도 여전히 서 있어야** 확정했는데, 템포가 빠르면 그 다음 표본이 이미 재하강 중이라 영원히 확정되지 않았다.
7. **시간 기준 프레임 샘플링** — `front_01`에서 남은, 이번에 고치지 않은 원인. 3fps는 초당 최대 3개 지점만 관측한다. `front_01`의 반복 3~4~5는 실제로는 무릎이 108~130도까지 내려갔지만(육안상 명백히 깊은 스쿼트, [증거 이미지](screenshots/2026-09-21/squat_front_01_missed_depth_evidence.jpg)), 그 순간이 두 표본 사이에 있어 **어떤 표본도 바닥 조건(무릎 ≤115도)을 만족하는 순간을 포착하지 못했다**. 이는 확인 지연 문제가 아니라 표본화 해상도 자체의 한계(나이퀴스트류 문제)이며, 6번 항목의 수정과는 무관하다.
8. **좌우 관절 선택** — `shallow_01`·`side_01`은 한쪽 다리만 시야에 들어와 한쪽 다리 대체 로직을 썼다. 코드는 이를 정상적으로 처리했고 문제를 일으키지 않았다(`ai-server/tests/test_squat_counter.py`의 한쪽 다리 테스트들이 이미 이 경로를 검증한다).
9. **정면·45도·측면 촬영 차이** — `front_01`(정면)과 `side_01`(완전 측면)은 협의된 45도 촬영 조건을 벗어난다. 각도 계산 자체는 두 경우 모두 정상 동작했으나(각각 5회 관측 가능, `side_01`은 실제로 5회 모두 검출), `front_01`의 표본화 문제는 정면 촬영에서 이 사람의 템포가 상대적으로 빨랐던 것과 겹쳐 더 두드러졌을 가능성이 있다.
10. **영상 시작·종료의 동작 절단** — `shallow_01`은 시작 2초 정지가 전혀 없어 0~3.65초 동안 계산이 "waiting_for_standing" 상태에 머물렀고, 그 사이 일어난 3회의 얕은 시도는 평가 대상에서 완전히 빠졌다(§4). 나머지 영상은 시작·종료 정지가 2초에 못 미치더라도(1.5~2.0초 근처) calibration과 마지막 반복 완료에는 지장이 없었다.

## 4. `squat_shallow_01.mp4`를 "통과"로 읽으면 안 되는 이유

촬영 규약(시작 2초 정지 자세)을 지키지 않아 사람이 육안으로 본 5회의 얕은 시도 중 **3회(0.23~0.47초, 1.63~1.86초, 2.79~3.26초)는 calibration이 끝나기 전에 일어나 AI가 아예 평가하지 못했다.** 나머지 2회(4.19~4.65초, 5.81~6.05초)는 baseline 코드 기준으로 "깊이 미확인" 피드백이 발생해 얼핏 보면 의도(전부 얕게)와 맞아떨어지는 것처럼 보이지만, 원본 각도 추적표를 보면 이 두 번은 **단일 3fps 표본에서 무릎 101~115도·고관절 102~107도로 앱의 바닥 조건 경계에 실제로 닿아 있었다.** 앱은 단일 표본만으로는 바닥 단계를 확정하지 않도록 의도적으로 보수적으로 유지했으므로(§3-6, §3-7 구분 참고) 이 2회를 "깊이 미확인"으로 처리한 것은 **정확도 버그가 아니라 방어적으로 올바른 판단**이다. 다만 이 영상은 "일관되게 얕은 동작" 시연으로 쓰기에는 본인의 실제 수행 깊이가 일관되지 않았고, 촬영 규약도 지키지 않았다. **깨끗한 얕은 동작 기각 시연을 위해서는 시작 2초 정지를 포함하고 처음부터 끝까지 일관되게 무릎이 얕게만 굽혀지는 영상을 다시 촬영해야 한다.**

## 5. 코드 수정

`ai-server/app/core/squat_counter.py`의 `SquatCounter.update()`, `stage == "bottom"`일 때의 기립 확인 분기 한 곳만 고쳤다:

```python
if standing:
    if self.standing_since is None:
        self.standing_since = now
    if ((now - self.standing_since >= t.standing_confirm_sec
         or dt >= t.standing_confirm_sec)
            and now - self.started_at >= t.min_active_sec):
        self.rep_count += 1
        ...
```

`dt`(이번 호출과 직전 호출 사이의 실제 경과 시간)가 이미 확인 지연 시간 이상이면, 그 자체가 우리가 관측할 수 있는 최소 지속 시간이므로 **첫 표본만으로도 확정**한다. 카메라·실시간 스트리밍처럼 `dt`가 확인 지연보다 훨씬 짧을 때(고fps)는 기존처럼 여러 표본에 걸친 실제 체류를 요구하는 동작이 그대로 유지된다 — 즉 이 수정은 3fps처럼 표본 간격이 넓은 입력에서만 효과가 있고, 실시간 카메라 스트리밍(보통 수십 fps)에서는 사실상 아무 영향이 없다.

**바닥 확인(`bottom_confirm_sec`)에는 같은 수정을 적용하지 않고 되돌렸다.** 처음에는 대칭적으로 같은 수정을 시도했으나 두 가지 문제가 있었다:
- `tests/test_squat_counter.py::test_reference_segments_follow_completed_repetitions`가 검증하는 "하강 단계가 최소 한 프레임은 `descending`으로 기록된다"는 `reference_builder._segment_reps`의 전제가 깨져 기준 영상 구간 분할이 실패했다.
- `squat_shallow_01.mp4`에서 단 1개 표본만 바닥 경계에 걸친 애매한 반복까지 완료로 계상해, §4에서 설명한 "깊이 미확인"의 보수적 판정이 사라졌다.

따라서 최종적으로는 **기립 확인만** 표본 간격을 고려하도록 바꾸고, 바닥 확인은 기존과 동일하게 최소 2개 연속 표본을 요구하도록 유지했다. 특정 영상 하나만 맞추기 위해 임계값을 낮추지 않았다는 원칙을 지켰다 — 각도 임계값은 전혀 건드리지 않았고, 시간 확인 로직만 표본화 현실에 맞게 고쳤다.

### 7-3. 새로 발견한, 이번 수정과 무관한 별개 이슈: 정확히 3fps로 보낼 때의 레이트리밋 여유가 매우 좁다

`squat_normal_01.mp4`를 정확히 3fps(간격 333ms)로 두 번 보냈을 때 **매번** 프레임 1개가 `RATE_LIMITED`로 스킵되어 rep이 5가 아니라 4로 나왔다(§5의 기립 확인 수정과 무관 — 스킵된 프레임 자체가 판정에 들어가지 못했다). 원인을 좁혀보니:

- 서버의 유입 속도 상한은 `ai-server/app/grpc/session_state.py`의 `MIN_FRAME_INTERVAL_SEC = 0.300`(300ms)이다.
- 같은 파일 주석은 앱의 실제 전송 간격을 `exercise.tsx intervalMs=330`(330ms)이라고 적어 두었다 — **서버 하한(300ms)과 앱의 의도된 간격(330ms) 사이의 여유가 30ms뿐이다.**
- 전송 간격을 2.5fps(400ms)로 늘리자 같은 영상에서 스킵이 0건으로 사라지고 5/5가 정확히 일치했다.

즉 정확히 3fps로 보내도록 설계된 현재 여유폭은, 로컬 Docker 환경의 극히 미세한 타이밍 지터(내 테스트 스크립트의 `time.sleep` 오차 수준)만으로도 프레임을 하나씩 잃을 수 있을 만큼 빠듯하다. 이는 이번에 수정한 `squat_counter.py`의 문제가 아니라 **레이트리미터(`MIN_FRAME_INTERVAL_SEC`)와 클라이언트 전송 간격(`intervalMs`) 사이의 여유 설계**에 관한, 별개의 기존 이슈다. 이번 작업 범위 밖이라 고치지 않았지만, 실기기(휴대폰 카메라, 네트워크 지연이 로컬보다 더 크고 변동성도 큼)에서는 이 margin이 로컬 Docker 테스트보다 훨씬 더 자주 소진될 수 있으므로 별도로 검토가 필요하다.

## 8. 현재 주장할 수 있는 성능과 한계

**주장 가능**: 고정 촬영 조건(45도 근접, 전신 노출, 가림 없음, 충분한 조명)에서 촬영한 새 영상 2개(`normal_01`, `normal_02`)와 기존 라벨 영상들에서, 수정된 코드는 사람이 눈으로 확인한 정상 깊이 반복 횟수와 정확히 일치했다(각 5/5). `negative_01`(스쿼트 없음 22초)에서도 오검출 0건이었다. 이 일치는 오프라인 배치 평가뿐 아니라 **회원가입부터 리포트 저장까지의 실제 API 경로**(§7-2)에서도 재현됐다 — 즉 카운팅 로직 수정이 배관 전체를 통과해 실제로 반영된다는 것까지 확인했다.

**주장할 수 없는 것**:
- **최종 홀드아웃 부재**: `normal_01`·`normal_02`는 이번 수정을 진단하는 데 직접 사용한 영상이라 최종 증거로 다시 쓰면 검증 유출이다. `negative_01`만 이번 수정과 무관한 독립 홀드아웃으로 인정한다. **정상 스쿼트에 대한 독립적인 최종 합격 주장은 아직 할 수 없다.**
- **얕은 동작 기각의 깨끗한 증거 없음**: `shallow_01`은 촬영 규약 미충족(시작 정지 없음)과 본인 수행의 깊이 비일관성 때문에 깨끗한 시연이 아니다.
- **3fps 표본화의 실제 한계 확인됨**: 빠른 템포로 수행하면(특히 `front_01`처럼) 실제 깊은 반복이 3fps 표본 사이로 빠져나가 놓칠 수 있다. 이는 이번 수정으로 고치지 않았고, 사용자에게 코칭 문구(바닥에서 짧게라도 멈추기)나 표본 속도 조정 등 별도 논의가 필요하다.
- **정확히 3fps로 보낼 때의 레이트리밋 여유가 좁다(§7-3, 신규 발견)**: 서버 상한(300ms)과 앱의 의도된 전송 간격(330ms) 사이 여유가 30ms뿐이라, 로컬 Docker 환경의 미세한 타이밍 지터만으로도 정상 반복이 누락되는 것을 실측했다(2.5fps로 늘리면 사라짐). 실기기·실네트워크에서는 더 자주 발생할 수 있다. 이번 작업 범위 밖이라 고치지 않았다.
- **45도 협의 각도에서 촬영된 영상이 실질적으로 없음**: `normal_01`·`normal_02`는 45도에 가깝지만 정확히 협의된 각도인지 확인할 기준점이 없고, `front_01`(정면)·`side_01`(완전 측면)은 명백히 협의 각도를 벗어난다.
- 어떤 조건에서도 **일반 사용자 환경 정확도 100%를 주장하지 않는다.**

## 9. 사용자가 추가로 촬영·확인해야 할 사항

1. **새 정상 스쿼트 영상 1개 이상** — 45도, 시작·종료 2초 정지 포함, 5회. 이번 디버깅에 쓰지 않은 새 영상이어야 독립적인 최종 합격 주장이 가능하다.
2. **새 얕은 스쿼트 영상 1개** — 시작 2초 정지를 반드시 포함하고, 처음부터 끝까지 무릎이 일관되게 얕게(무릎 각도가 115도 밑으로 내려가지 않게)만 굽혀지도록 수행.
3. (선택) **`front_01`과 같은 빠른 템포 정면 영상을 하나 더** — 바닥에서 아주 짧게(0.3~0.5초)라도 멈추는 버전으로 촬영해, 표본화 한계가 실제로 "멈춤 없는 빠른 템포"에서만 발생하는지 "정면 각도" 자체의 문제는 아닌지 구분.
4. `squat_normal_03.mp4`는 계획에는 있었지만 폴더에 없다 — 필요하면 추가 촬영.
5. 휴대폰 카메라로 직접 실행하는 §10 체크리스트(아래) — API 경로는 이번에 직접 확인했지만, 실기기 화면에 토스트가 실제로 보이는지와 §7-3의 레이트리밋 여유 문제가 실네트워크에서 얼마나 자주 발생하는지는 사용자 확인이 필요하다.
