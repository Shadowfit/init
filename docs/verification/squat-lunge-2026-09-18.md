# 스쿼트·전방 런지 검증 기록 (2026-09-18)

## 결론

반복 횟수 판정과 런지 세션 저장의 자동 테스트는 통과했다. 저장소의 스쿼트 영상 7개 중 최초 구현에서 추적 품질 검사를 통과한 것은 1개였고, 첫 실영상 수동 대조에서는 6개 스쿼트 영상 모두 불일치하며 평균 절대 오차가 5.83회였다. 추가 보정 후 같은 6개 영상에서는 **2개가 정확히 일치하고 평균 절대 오차가 3.33회**다. 다만 랙 가림과 다른 종목의 오검출이 남아 있어 **실제 사용자 촬영 정확도 또는 앱 전체 동작을 합격 처리할 수 없다.** 아래 앞부분은 변경 단계별 기록이며, 최신 결과는 문서 끝의 '스쿼트 횟수 판정 추가 수정'에 있다. 결과는 모두 현재 작업 트리의 미커밋 코드 기준이다.

## 저장소 영상 평가

`scripts/evaluate_squat.py`로 MediaPipe 자세 추출과 스쿼트 반복 판정을 **3fps**에서 재생했다. `사용 가능 프레임`은 필수 관절의 추적·가시성 조건을 통과한 프레임이다. 아래는 사용자 수동 라벨을 받기 전 최초 결과다. 당시에는 정답 횟수가 없어 오차를 계산하지 않았다.

45도 정면 영상은 자세 추출 자체는 됐지만 첫 동작이 선 자세 보정 전에 시작됐다. 두 번째 동작은 3fps에서 양쪽 무릎의 평균 각도가 하단 기준 100도 이하인 프레임이 1개뿐이어서 `bottom_confirm_sec`를 충족하지 못했다. 12fps로 재생해도 무릎 평균 각도 최솟값이 약 106도로 하단 판정에 진입하지 않았다. 0회는 이 코드의 완료 조건에서 나온 결과이며, 사람 기준 정답 여부는 미확인이다. 나머지 6개는 추적 품질 기준을 통과하지 못했다.

### 추가 원인 분석

민감도 확인용으로 관절 가시성 기준만 0.55에서 0.35로 낮추자 `kkw_front_squat.mp4`는 45/45프레임·2회, `kkw_45-degree_backview_squat.mp4`는 25/25프레임·1회, `sqaut_roi_0509.mp4`는 45/54프레임·0회가 됐다. 이는 기준값에 결과가 크게 좌우된다는 뜻이지, 0.35가 올바른 기준이라는 증거는 아니다. 특히 `sqaut_roi_0509.mp4`는 품질 기준은 통과해도 선 자세 보정 후 프레임이 4개뿐이라 횟수 검증에 적절하지 않다. 정답 횟수 없이 기준을 낮추면 오검출 여부를 알 수 없으므로 제품 기본값은 변경하지 않았다.

45도 정면 영상의 [3fps 추적표](squat-45-front-trace.csv)와 [12fps 추적표](squat-45-front-trace-12fps.csv)를 보관했다. 프레임을 더 자주 처리해도 하단 자세가 확정되지 않아 0회였다. 현재 양쪽 무릎 각도를 평균내는 방식은 측면·45도 촬영에서 한쪽 다리의 추정 오차에 민감하다.

이 최초 평가에서는 카메라 안내가 측면 촬영을 권장하면서도 카운터는 양쪽 어깨·골반·무릎·발목을 모두 가시성 0.55 이상으로 요구했다. 측면에서 먼쪽 다리가 가려지는 영상과 이 조건이 충돌했다. 아래의 한쪽 다리 가시성 개선은 이 문제를 대상으로 한다.

추가로 사용자가 내려받은 AI Hub 크로스핏 샘플 영상 8시점과 에어 스쿼트 학습 라벨 2,888개를 검사했다. 같은 동작의 8시점 중 영상 전체 경로에서는 3시점만 1회를 검출했다. 상세 결과와 독립 표본이 아니라는 한계는 [AI Hub 검증 기록](aihub-crossfit-squat-2026-09-18.md)에 정리했다.

### 사용자 수동 횟수와 대조

사용자가 같은 영상 7개에 완료 횟수를 붙였다. `samples/validation/labels.csv`에 로컬 라벨을 기록하고 `scripts/evaluate_dataset.py`로 앱 기본값인 3fps에서 재평가했다. `labels.csv`와 `results.csv`는 로컬 평가 파일로 Git에서 제외된다. `평가 유효`는 관절 사용 가능 프레임이 70% 이상이고 한 번이라도 선 자세를 확인한 운영상 조건일 뿐, 정확한 포즈나 충분한 주기 추적을 보증하지 않는다.

| 영상 | 수동 횟수 | 검출 횟수 | 절대 오차 | 선 자세 보정 상태 프레임 / 표본 |
|---|---:|---:|---:|---:|
| 45도 정면 | 2 | 0 | 2 | 12/22 |
| 정면 (랙이 무릎 가림) | 3 | 2 | 1 | 44/45 |
| `squat.mp4` (랙이 무릎 가림) | 9 | 0 | 9 | 1/72 |
| 45도 후면 | 2 | 1 | 1 | 13/25 |
| ROI | 7 | 0 | 7 | 13/54 |
| 60kg (랙이 무릎 가림) | 15 | 0 | 15 | 65/185 |
| 데모 (스쿼트 없음) | 0 | 0 | 평가 제외 | 0/31 |

스쿼트가 있는 6개 영상의 **수동 총합 38회 대비 검출 총합 3회**, 영상별 **정확히 일치 0/6개**, **평균 절대 오차 35/6=5.83회**다. 총횟수 라벨만 있으므로 3개 검출이 실제 동작과 시간상 일치하는지 확인하지 못했다. 따라서 3/38을 재현율로 표현하지 않는다. 데모 영상은 0회를 출력했지만 자세 추적 가능한 프레임이 0개여서 오검출 방지의 성공 사례로 계산하지 않는다.

상태 전이로 확인한 누락 원인은 다르다. 45도 정면은 첫 회를 선 자세 보정 전부터 시작했고 두 번째 회는 2D 무릎 각도가 하단 경계를 넘지 못했다. 정면은 세 번째 하단을 잡았지만 영상 끝까지 다시 선 상태를 확인하지 못했다. `squat.mp4`와 ROI는 대부분의 프레임에서 선 자세 조건을 확인하지 못했다. 45도 후면은 두 번째 주기 시작 시 발 좌표 변화로 초기화됐다. 60kg은 몇 차례 하단까지 잡았지만 랙에 가린 프레임에서 발 좌표가 기준 몸통 길이의 약 0.4~1.0배까지 튀어 주기를 반복 초기화했다. 실제 발 이동인지 포즈 추정 오류인지는 가림 때문에 확정할 수 없다. 가시성만으로 `평가 유효`를 판단하는 현재 기준은 이 문제를 걸러내지 못한다.

이 7개만 보고 논문 각도 경계나 발 이동 허용폭을 일괄 완화하면 오검출이 늘 수 있다. 특히 랙에 가린 영상은 2D 관절 좌표 자체가 불안정하다. 독립적인 가림 없는 휴대폰 촬영본과 동작별 완료 시각, 움직임이 비슷한 비스쿼트 동작을 확보해 수정 전후 누락과 오검출을 함께 확인해야 한다.

저장소에 **전방 런지 촬영 영상은 없다.** 따라서 런지에 대해서는 합성 좌표와 서비스 계약까지만 검증했다. 좌우 실제 인식률은 측정하지 못했다.

## 실사용 검증 전 남은 조건

1. 기존 스쿼트 7개 영상의 수동 총횟수 대조는 완료했다. 다음에는 측면에서 머리부터 발끝까지 보이는 사용자 휴대폰 스쿼트·전방 런지 촬영본과 사람이 센 총횟수·런지 좌우 횟수로 앱 촬영 조건에서 독립 검증한다. 완료 시각도 적으면 어떤 주기를 놓치거나 잘못 센 것인지 판별할 수 있다. 영상 끝에 선 자세를 잠시 유지해야 완료 판정을 확인할 수 있다.
2. 같은 촬영 조건으로 앱 카메라 → AI `/pose` → Spring 세션 저장 → 홈 기록까지 한 번 연결한다. 현재 `ai-server/.env`의 `AI_PUBLIC_TOKEN`과 `frontend/.env.local`의 `EXPO_PUBLIC_AI_PUBLIC_TOKEN`이 모두 비어 있다. Docker Desktop에서 기존 `shadowfit-backend` 컨테이너도 DB 호스트 `shadowfit-mysql`을 찾지 못해 재시작 중이므로, 앱 전체 경로는 아직 검증하지 못했다.

실영상 정확도를 판단할 때는 촬영본별 수동 정답과 검출 횟수를 비교하고, 정상 동작뿐 아니라 얕은 동작·가림·정면·워킹/후방 런지의 오검출도 따로 기록한다. 영상이 분석 조건을 충족하지 못하면 0회를 정확한 판정으로 취급하지 않는다.

## 영상 도착 전 준비 (2026-09-18)

`samples/validation/labels.template.csv`와 촬영·정답 작성 안내를 만들고, `ai-server/scripts/evaluate_dataset.py`로 여러 영상을 같은 3fps 조건에서 일괄 평가하도록 준비했다. 기존 스쿼트 영상 두 개로 결과 CSV를 생성하고, **정답이 없는 영상과 추적 실패 영상이 MAE에 들어가지 않는 동작**을 확인했다. 이 확인에 사용한 임시 0회 표기는 실제 사람이 센 정답이 아니다. 런지 실영상은 여전히 없어 런지 배치 결과는 아직 없다.

Docker Desktop 실행 후 격리된 MySQL 8.0 Testcontainers에서 `FlywayMigrationValidationTest`를 재실행해 2개 테스트가 모두 통과했다. 로그에서 V22를 포함한 마이그레이션 22개가 적용됐고 Spring 컨텍스트가 JPA 스키마 검증을 통과한 것을 확인했다. 첫 실행은 gRPC 임시 포트 충돌로 실패했으며, 재실행 명령에서만 `GRPC_SERVER_PORT=-1`로 gRPC 서버를 꺼서 해결했다. 사용자 DB는 사용하지 않았다.

## 스쿼트 횟수 판정 추가 수정 (2026-09-18)

위의 표는 당시 구현의 기록이다. 이후 실제 영상에서 선 자세 판정이 너무 엄격하고, 운동 전에 발을 옮긴 것을 동작 중 발 이동으로 오인하는 문제를 확인했다. 서기 각도에 2D 추정 오차 여유를 두고, 각도와 함께 몸통 길이로 정규화한 골반 하강을 확인하도록 바꿨다. 준비 자세에서는 발 기준점을 갱신하고, 하강 중 한두 프레임의 발 좌표 오류는 건너뛰되 지속적인 발 이동은 주기를 취소한다. 이 여유값은 **기존 영상에 맞춰 정한 구현 값**이며 논문에서 검증한 성능 수치가 아니다.

MediaPipe를 포함한 `scripts/evaluate_dataset.py` 3fps 재실행 결과다. 데모 영상은 포즈 프레임이 0개라 정답 0회여도 정확도에서 제외한다.

| 영상 | 수동 횟수 | 이전 검출 | 현재 검출 | 현재 평가 유효 |
|---|---:|---:|---:|---|
| 45도 정면 | 2 | 0 | 2 | 예 |
| 정면, 랙 가림 | 3 | 2 | 2 | 예 |
| `squat.mp4`, 랙 가림 | 9 | 0 | 2 | 아니오 (44/72 사용 가능 프레임) |
| 45도 후면 | 2 | 1 | 2 | 예 |
| ROI | 7 | 0 | 5 | 예 |
| 60kg, 랙 가림 | 15 | 0 | 5 | 예 |
| 데모, 전신이 보이지 않음 | 0 | 0 | 0 | 아니오 (0/31 사용 가능 프레임) |

사람이 센 횟수가 있는 스쿼트 영상 6개 중 **정확히 일치한 영상은 2개**다. 같은 6개를 모두 비교한 절대 오차 평균은 5.83회에서 **3.33회**로 감소했다. 운영상 포즈 품질을 통과한 현재 영상 5개만 계산하면 평균 절대 오차는 **2.6회**다. 가림이 없다고 알려진 세 영상에서는 2/3개가 일치하고 평균 절대 오차가 0.67회다. 그러나 이 영상들을 보면서 판정값을 정했으므로 어느 수치도 독립 검증 정확도가 아니다. ROI는 시작부터 앉은 자세라 첫 동작을 확인할 수 없고, 짧은 선 자세를 놓친 주기도 있다. 랙이 무릎을 가린 영상은 여전히 크게 누락된다.

AI Hub 에어 스쿼트 샘플의 같은 동작 8시점에서는 1회 검출이 6/8에서 **7/8**로 늘었다. 학습용 2D 관절 좌표의 에어 스쿼트 361개 기록·2,888개 시점에서는 1회 출력 시점이 2,012개에서 **2,398개**로 늘었다. 이 자료에는 확인된 회차별 정답과 MediaPipe 가시성 점수가 없어 **정확도나 재현율로 해석하지 않는다**. 같은 AI Hub 좌표를 다른 종목에 넣으면 스쿼트가 아닌 동작도 세는 사례가 있다. 예를 들어 선택 순서상 첫 30개의 `camera0` 정상 데드리프트 좌표 모두에서 스쿼트 카운터가 2회를 출력했다. 현 판정기는 운동 종목 자체를 구분하지 못한다.

AI 테스트는 `test_camera.py`를 제외하고 **199 passed, 61 subtests passed**다. 실제 촬영본에서 독립적으로 확인해야 할 것은 스쿼트 완료 시각, 런지 좌우 횟수, 장애물이 없는 카메라 시점별 누락, 비스쿼트 동작의 오검출이다. 현재 결과로 제품 수준 성능이나 AI 모델 학습 완료를 주장하지 않는다.
