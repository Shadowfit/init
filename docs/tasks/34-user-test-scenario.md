# 1차 사용자 테스트 시나리오 (Week 5, 10/12 ~ 10/16)

> 상태: 초안 (2026-09-14) · 09-23 갱신 — 범위를 소셜 L1 사용자 테스트로 못박고, 09-17 프론트 커밋 뒤의 화면 상태와 리포트 전제를 바로잡았다. §7 미결 항목은 사용자 confirm 대기.
> 이 문서는 [`24-semester2-plan.md`](./24-semester2-plan.md) 4~5주차 «사용자 테스트 준비» 의 첫 산출물이다 — 시드(계정·모임·이력)와 로깅이 **무엇을 위해** 있는지를 여기서 정하고, 시드·로깅 작업은 이 문서를 입력으로 받는다.

## 1. 목적

**범위: 소셜 L1 사용자 테스트.** 제품 전체 시연 대본(실시간 음성 교정 · 세션 리포트 같은 PDF 핵심 경로)은 [`37-product-scenario-and-use-cases.md`](./37-product-scenario-and-use-cases.md) 가 맡는다 — 이 문서는 그걸 대체하지 않고, 37 도 이 문서를 대체하지 않는다. 유스케이스 번호는 [`../usecase/README.md`](../usecase/README.md).

- 소셜 L1(§4-1 12개, 09-14 전부 머지)을 **실사용자 손에서** 돌려 이음새의 결함을 찾는다. 코드 테스트(통합 12·단위 11·저니 1)가 못 보는 것 — 실기기 카메라·네트워크 단절·앱 백그라운드·타인의 행동 타이밍.
- 관리자 통계(BE-05)·패턴 분석(BE-07)·추천(BE-08)의 **입력 데이터가 처음 생기는** 자리다. 이 주 이전엔 실데이터가 없다.
- 2차 테스트는 없다(09-11 결정, 리허설로 대체). **1차가 유일한 실사용 기회**다.

## 2. 전제 — 지금 상태에서 사실인 것

| 축 | 사실 | 시나리오에 미치는 영향 |
|---|---|---|
| 프론트 | ~~소셜 화면 0개~~ → **09-17 프론트 커밋으로 모임 탭 · 코드 참여 · 친구 현황 · 피드 · 리액션 · 모임 캘린더 · 알림함이 들어왔고, 09-21 에 응원(E-10)도 붙었다.** 남은 건 푸시 토큰(`expo-notifications` 미설치) · 스트릭 카드 · WS 클라이언트 | 소셜 시나리오는 푸시(0-3) · 스트릭(1-8) · WS(V-3) 를 빼면 화면으로 밟을 수 있다 |
| 세션 완료 | 실기기 카메라 → AI 서버 분석 → gRPC `CompleteAnalysis` 로 COMPLETED. **AI 서버 없이는 출석이 안 생긴다** | 서버는 AI 포함 풀스택으로 떠 있어야 함. 출석 = COMPLETED 세션 1건 이상 |
| 리포트 | ~~세션 리포트에 LLM 호출~~ → **세션 리포트엔 LLM 이 없다** — worst 구간 · 이전 비교는 세션 종료 때 precompute. LLM(Gemini)은 주간 AI 총평(C-04)만 쓰고, 실패하면 템플릿 문장으로 폴백 | 리포트가 LLM 때문에 비는 경로는 없다. 대신 리포트 **화면이 `MOCK_REPORT` 상수**라 37 §6 G2 전엔 실데이터가 안 보인다 |
| 푸시 | 백엔드는 완성(`push_tokens`·아웃박스 `PUSH_NOTIFICATION`·Expo 클라이언트). 프론트 토큰 등록·EAS 자격증명 없음 | 푸시 없이도 재촉은 **저장 + 알림함**으로 성립. 푸시는 «되면 확인» 축 |
| 접속 | HTTPS(OP-02)는 호스트 생기면 | 외부 참여자 = HTTPS 필수. 미해결이면 참여자를 같은 네트워크 안으로 제한 |
| 시드 | `dev-seed.sql` 은 부하테스트 픽스처(계정 2 + 더미 세션 801)라 **배포 DB 에 안 넣는다**(14 §②). 운동 카탈로그는 Flyway V2(스쿼트만 `analysis_supported`) | 사용자 테스트 시드는 **별도 파일**이어야 한다 — §5 |

## 3. 참여자와 구성 (수치는 §7 미결)

- 참여자 **N명**(24 문서 «5~10명»), 스쿼트 가능한 실기기(Android/iOS) 소지.
- 모임 **M개**를 운영자가 미리 만들어 두고 초대 코드를 배포 — 참여자가 모임을 «만드는» 경로는 이번 테스트 밖(코드로 참여가 레퍼런스의 주 경로, §3-F).
- 운영자 계정 1 (ADMIN) — 관리자 통계·세션 목록으로 진행 상황을 본다. **`Member.role` 은 이미 있다**(`UserRole.ADMIN`) — 24 문서 «role 없으면 +1h» 리스크는 해소됨.
- 모임당 인원은 재촉이 성립할 만큼 — «오늘 안 한 사람»이 하루에 한 명은 나와야 재촉 버튼이 눌린다. 전원이 매일 하면 재촉 경로는 0회로 끝난다(§7 ③).

## 4. 시나리오 — 참여자가 밟는 순서

각 행: 무엇을 하나 / 어느 화면(있음·없음) / 뒤에서 도는 API / 관측 지점.

### D0 — 진입 (테스트 시작일, 운영자가 옆에 있을 때)

| # | 행동 | 화면 | API | 관측 |
|:--:|---|:--:|---|---|
| 0-1 | 앱 설치, 가입, 온보딩(페르소나·키/몸무게) | 있음 | `POST /member/signup` → `PATCH /member/onboarding/{email}` | 가입 실패 로그, 온보딩 이탈(`onboarding_completed=false` 잔존) |
| 0-2 | **코드로 모임 참여** — 운영자가 준 8자리 입력 | 있음 (09-17) | `POST /groups/join` | 대소문자·오타 400/404 빈도, 더블탭 |
| 0-3 | 푸시 권한 허용 → 토큰 등록 | ❌ 없음(`expo-notifications` 미설치) | `POST /push-tokens` | 토큰 행 수 = 허용한 참여자 수 |
| 0-4 | 홈에서 «친구의 운동 현황»이 보인다 — 같은 모임 사람들, 전원 «오늘 안 함» | 있음 (09-17) | `GET /friends` | 응답 인원 = 모임 인원 − 1 |

|:--:|---|:--:|---|---|

## 5. 시드에서 도출되는 것 (② 입력)

이 시나리오가 성립하려면 테스트 시작 시점 DB 에 있어야 하는 것:

| 대상 | 내용 | 근거 |
|---|---|---|
| 운영자 | ADMIN 1 | §3, 관리자 통계 |
| 참여자 계정 | **만들지 않는다** — 0-1 이 가입 경로 자체를 테스트한다. 대신 운영자용 더미 참여자 1~2 (모임이 비어 보이지 않게, 재촉 대상 보장) | 0-4·1-5 |
| 모임 | M개, 초대 코드 고정(시드에서 값 지정 — 배포 전 인쇄·전달 가능하게), 더미 참여자 소속 | 0-2 |
| 세션 이력 | 더미 참여자에게 **직전 며칠 COMPLETED 세션** — 캘린더·streak 가 첫날부터 비어 있지 않게. 실제 참여자 이력은 없음(진짜 D1 부터) | 1-7·1-8 |
| 운동 카탈로그 | V2 그대로(스쿼트만). 런지·플랭크는 `analysis_supported=false` 라 세션 생성이 W007 로 막힘 — 화면에서 안 보이거나 «준비 중»으로 보여야 함 | 1-1 |
| 넣는 방식 | `dev-seed.sql` 과 **별도 파일**(`mysql/user-test-seed.sql`), Flyway 밖. 배포 DB 에 수동 적용 | §2 시드 행 |

## 6. 관측 — 무엇을 남기고 무엇을 볼 것인가

기준값(threshold)은 두지 않는다 — 실측이 처음이라 baseline 이 없다. 아래는 **세는 것**의 목록이다.

- **서버 로그(ERROR)**: AI 콜백 실패·주간 총평 LLM 실패(템플릿 폴백)·아웃박스 재시도 소진(`FAILED`)·푸시 `DeviceNotRegistered`/전송 실패·WS 전송 실패 정리. → 로깅 강화(③)의 대상이 이 다섯이다. OP-01 알람은 이 중 «재시도 소진» 류에만.
- **DB 로 세는 것**(테스트 종료 후 한 번): 참여자별 COMPLETED/FAILED 세션 수, 모임별 자동 글 수, 리액션 수, 재촉 수(보낸/받은/409), 알림 읽음 비율, 푸시 SENT/실패, 탈퇴 수.
- **참여자에게 묻는 것**(종료 설문, 5문항 이내): 재촉을 받았을 때 알아챘나(어떤 경로로) / «오늘 했나» 표시가 본인 인식과 맞았나 / 세션이 실패했을 때 이유를 알 수 있었나 / 모임 피드를 하루 몇 번 봤나 / 다시 쓸 의향.

## 7. 미결 — 사용자 confirm 필요

| # | 항목 | 후보 | 걸린 것 |
|:--:|---|---|---|
| ① | **프론트 소셜 화면을 누가 10/9 까지 만드나** | a. 프론트 담당 / b. 백엔드 작업자가 최소 화면 / c. 소셜은 1차에서 빼고 운동 루프만 | ①이 c 면 §4 의 ❌ 행 전부 제외, 시드도 모임 없이 계정만. **이 문서의 절반이 ①에 걸려 있다** |
| ② | 참여자 수 N·모임 수 M | N=5~10(24 문서), M=1(전원 한 모임) 또는 2(모임 간 비교) | M=2 면 «다른 모임 사람은 친구 아님» 경계가 실사용에서 검증됨. 인원이 갈려 재촉 기회는 줄어듦 |
| ③ | 재촉이 0회로 끝나는 걸 막을 장치를 두나 | a. 없음(자연 발생만) / b. 운영자 더미 참여자가 «안 한 사람» 역할 | b 면 재촉 경로는 반드시 1회 이상 밟히지만 «진짜 사용자 간» 재촉은 아님 |
| ④ | 푸시를 1차 범위에 넣나 | a. 넣음 — `expo-notifications` + EAS 자격증명 선행(비코딩) / b. 뺌 — 알림함만 | a 는 프론트 일정에 +, b 면 V-3 의 «홈에서 재촉 받기»는 확인 불가 |
| ⑤ | 참여자 위치 | a. 외부(HTTPS 필수) / b. 같은 네트워크 | OP-02 진행에 종속 |

①이 정해져야 ②~⑤와 시드(§5)가 정해진다. ①을 먼저.

> 09-23 사실 메모(결정 아님): ①의 전제였던 «소셜 화면 0개» 는 09-17 프론트 커밋으로 대부분 풀렸다 — 프론트 담당이 만든 셈이다. ①을 닫을지는 사용자 confirm.
