## 구현된 판정

`ai-server/app/core/squat_counter.py`의 `SquatCounter`를 실시간 `StreamingSquatAnalyzer`와 업로드 영상 `analyze_squat_frames`가 함께 사용한다. 이미지 가로세로비를 반영한 2D 좌표로 어깨·고관절·무릎·발목을 계산한다. MediaPipe의 정규화된 `z`를 실제 깊이로 취급하지 않는다. 측면에서 먼쪽 다리가 가려질 수 있어 한쪽의 어깨·고관절·무릎·발목이 모두 추적되면 계산을 이어간다. 양쪽이 보일 때는 기존 좌우 평균을 유지한다. 이 가시성 처리 역시 논문의 성능 검증을 받은 방법은 아니다.

1. 양쪽이 보이면 좌우 무릎·고관절 각도의 평균, 한쪽만 보이면 해당 다리의 각도로 충분히 선 자세를 확인한 뒤 시작한다. 영상이 앉은 자세에서 시작해도 그것만으로 1회를 만들지 않는다.
2. 같은 각도가 깊이 조건을 만족한 것을 확인한다. 얕은 굽힘은 세지 않는다. 좌우 평균과 한쪽 다리 대체는 논문의 단일 `knee_angle`·`hip_angle` 입력을 2D MediaPipe에 대응한 구현 선택이며, 논문이 이 결합 방식을 검증했다는 뜻은 아니다.
3. 다시 충분히 서면 1회를 추가한다. 이때만 기존 저장·리포트용 완료 이벤트를 낸다.
4. 양쪽 다리 모두 관절이 가려지거나 추적이 끊기면 진행 중인 주기만 버린다. 한쪽만 보이는 프레임에서도 이전부터 계속 추적된 다리가 있어야 하며, 동작 중 추적 대상 다리가 완전히 바뀌면 주기를 버린다. 준비 자세에서 선 채로 발 위치를 조정할 때는 발 기준점을 갱신한다. 하강이 시작된 뒤 발 좌표가 한두 프레임 튀면 그 프레임을 건너뛰고, 0.7초 이상 계속 벗어나면 진행 중인 주기를 취소한다. 완료된 횟수는 유지한다.

기본 경계는 코드의 `SquatThresholds`에 모았다. 160°/100°/150° 각도는 Sousa의 Listing 1에서 가져왔다. 실제 2D 관절 추정의 잡음을 고려해 **서기 무릎 152° 이상, 바닥 무릎 115° 이하**의 허용 구간을 두고, 바닥 판정에는 **준비 자세 대비 골반 하강이 몸통 길이의 0.25배 이상**인지도 확인한다. 이는 저자들이 검증한 숫자가 아니라 기존 촬영본에 맞춰 정한 구현 값이다. **서기 확인 0.2초, 바닥 확인 0.12초, EMA 0.12초, 추적 공백 1.2초, 가시성 0.55, 발 위치 허용폭**도 3fps 서비스와 잡음에 맞춘 구현 값으로, 논문 검증값으로 표현하지 않는다. 오래 앉아 쉬는 동작을 스쿼트로 세지 않으려고 깊은 자세가 **연속 8초를 넘으면** 주기를 취소한다. 이는 제품 규칙이며, 8초 이상 유지하는 스쿼트는 빠질 수 있다. 각도만으로 의자에 앉기와 긴 홀드 스쿼트를 완전히 구분할 수 없다.

### 2026-09-21: 서기 확인 지연이 3fps 표본 간격보다 짧아 연속된 두 반복을 하나로 합치던 문제

새로 촬영한 6개 영상(`docs/verification/2026-09-21-verification-report.md` 참고)을 사람이 직접 눈으로 검증하고 `--trace`의 원본 무릎·고관절 각도와 대조한 결과, `squat_normal_01.mp4`·`squat_normal_02.mp4`에서 반복 사이의 짧은 기립(1개 표본에서만 무릎이 편 상태로 관측되고 다음 표본에서 바로 재하강)이 완료로 확인되지 않고 **다음 반복과 합쳐져 1회로 과소 계상**되는 것을 확인했다. `update()`는 3fps로 샘플링된 프레임에서만 호출되므로 표본 간격(약 0.33~0.4초)이 이미 `standing_confirm_sec`(0.2초)보다 길다 — 즉 두 번째 표본이 오기 전에는 어떤 지속 시간도 이보다 더 잘게 관측할 수 없다. 기존 로직은 "서 있음"이 처음 관측된 표본에서는 확정하지 않고 **다음 표본에서도 여전히 서 있어야만** 확정했는데, 사용자가 정점에서 오래 멈추지 않는 빠른 템포에서는 그 다음 표본이 이미 재하강 중이라 영원히 확정되지 못했다.

수정: 표본 간격(`dt`)이 이미 확인 지연 시간 이상이면, 그 자체가 우리가 관측할 수 있는 최소 지속 시간이므로 **첫 표본만으로도 확정**한다(`ai-server/app/core/squat_counter.py`의 `stage == "bottom"`일 때의 기립 확인 분기). 카메라·실시간 스트리밍처럼 `dt`가 확인 지연보다 훨씬 짧을 때는 기존처럼 여러 표본에 걸친 실제 체류를 요구하는 동작이 그대로 유지된다 — 즉 이 수정은 높은 프레임레이트 입력에서는 사실상 아무 영향이 없다.

바닥 확인(`bottom_confirm_sec`)에도 같은 논리를 처음 적용했으나, 단일 표본만으로 바닥을 확정하면 `tests/test_squat_counter.py::test_reference_segments_follow_completed_repetitions`가 검증하는 "하강 단계가 최소 한 프레임은 기록된다"는 `reference_builder._segment_reps`의 전제가 깨지고, `squat_shallow_01.mp4`에서 단 1개 표본만 바닥 구간에 걸친 애매한 반복까지 완료로 계상해 버렸다. 이 변경은 되돌렸다 — **바닥 확인은 기존과 동일하게 최소 2개 연속 표본을 요구**하며, 기립 확인만 표본 간격을 고려하도록 바꿨다.

수정 전후로 기존 `samples/raw/`의 라벨된 영상을 다시 돌려 회귀를 확인했다: 45도 정면(2/2)·45도 후면(2/2)·정면(3/3)은 그대로였고, ROI 영상(`sqaut_roi_0509.mp4`)은 같은 합침 문제로 5회였던 것이 6회로 개선되며 사람이 센 7회에 더 가까워졌다(여전히 촬영 규약 미충족이라 100% 일치를 주장하지 않음). `ai-server/tests/`는 카메라 하드웨어 테스트를 제외하고 200 passed·61 subtests passed로 동일하다.

이 수정으로도 해결되지 않는, 별개의 한계가 하나 더 확인됐다: `squat_front_01.mp4`(정면 촬영, 빠른 템포)에서는 5회 중 3회가 바닥 구간에 **어떤 표본도 걸치지 않아** 아예 감지되지 못했다. 이는 확인 지연 문제가 아니라 3fps 표본 자체가 실제 최저점을 놓치는 나이퀴스트(표본화) 한계이며, 임계값을 더 낮추는 방식으로 고치면 다른 영상에서 얕은 동작을 진짜 반복으로 오인할 위험이 커진다. 현재는 이 한계를 임계값 조정으로 덮지 않고 문서화만 한다.

기존 무릎 100°/150°와 4·15프레임 중심의 실시간 판정, 업로드 영상의 별도 판정, 기준 영상 분할의 별도 155° 규칙을 한 완료 이벤트로 통일했다. `reference_builder.py`도 새 완료 횟수와 주기 상태를 사용한다. 프레임 수가 바뀌어도 시간 기준은 유지되며, 너무 낮은 촬영 FPS로 바닥 구간이 한 장도 잡히지 않으면 감지할 수 없다.

업로드 영상의 `quality_score`는 검증되지 않은 단일 점수를 생성하지 않고 `null`이다. 기존 실시간 `sync_rate`는 기준 영상과의 DTW 유사도이며, 표시 문구와 BACK_BENT 35° 규칙도 기존 휴리스틱이다. **논문 기반 반복 판정이 자세 점수 또는 안전 판정의 연구 검증을 뜻하지 않는다.**

## 확인 방법과 현재 한계

합성 궤적 테스트는 시작부터 앉아 있는 장면, 얕은 스쿼트, 느린 상승, 5초 홀드, 10~90초 앉아서 쉬기, 3·10·30fps, 관절 소실, 한쪽 다리 가림·추적 대상 교체, 발 이동, 영상·기준 영상 분할 및 실시간 저장 이벤트를 검증한다. 이는 실제 사람 촬영 정확도의 근거가 아니다.

저장된 `ai-server/scripts/demo_videos/demo_squat.mp4`를 업로드 경로로 재생한 결과, 308프레임 중 분석 가능한 자세 프레임이 **0개**였다. 한쪽 다리 허용 이후에도 3fps 표본 31프레임 중 0개였다. 따라서 이 영상의 `0회`를 정답과 일치한다고 해석하지 않는다. 실제 측면 촬영본에서 머리부터 발목까지 나오게 찍고 사람이 센 횟수와 아래 명령으로 비교해야 한다.

과거 `ai-server/analysis_data/`의 추출 좌표도 보조 확인했다. 이 추출 좌표에는 원본 영상의 화면 비율이 없고, 당시에는 사람 기준 횟수도 없었다. 이후 사용자가 원본 정면 영상은 3회, 45도 정면 영상은 2회라고 라벨링했다. 2026-09-18 수정 후 MediaPipe 전체 경로로 다시 재생하면 각각 2회와 2회가 검출된다. 추출 좌표의 과거 검출값이 정답과 같았어도 개별 주기 시각이 맞는지는 확인되지 않았다. **실영상 누락은 여전히 남아 있으며**, 같은 영상에 맞춰 조정한 결과를 일반 사용자 정확도로 취급하지 않는다.

```powershell
cd ai-server
python scripts/evaluate_squat.py .\clips\squat.mp4 --expected 5 --trace .\squat-trace.csv
```

결과의 `evaluation_valid=false`이면 추적·시작 자세 확인 실패이므로 `absolute_error=null`이다. 정면 촬영, 가림, 사람마다 다른 가동 범위, 의자에 앉기/긴 홀드의 혼동은 촬영본을 따로 모아 평가해야 한다.

## 2026-09-21: 풀 스쿼트 / 하프 스쿼트 깊이 모드

사용자가 운동 시작 전(종목 선택과 같은 화면)에 "풀 스쿼트"/"하프 스쿼트" 중 하나를 고르면, 그 모드의 목표 깊이에 맞춰 반복을 인정하고 세션 종료 후 리포트에 깊이 정확도 점수·등급·회차별 코멘트를 보여준다.

### 임계값

`ai-server/app/core/squat_counter.py`에 `HALF_SQUAT_THRESHOLDS`(`DEPTH_MODE_THRESHOLDS` 딕셔너리로 `"FULL"`/`"HALF"` 선택)를 추가했다. 풀 스쿼트 기준(160°/100°/150°, `bottom_knee_margin=15`)은 전혀 건드리지 않았다.

- **`bottom_knee=125.0`**(+margin 15 = 실질 진입 140°) — 사용자가 확정한 하프 스쿼트 목표 밴드(무릎 115~140도)의 얕은 쪽 경계에 맞춘 값. 이 숫자 자체는 사용자 지정이라 실측 여부와 무관하다.
- **`bottom_hip=154.0`, `min_hip_drop=0.15`(VALIDATE)** — 🔴 **실촬영 하프 스쿼트 영상이 없어 실측값이 아니다.** 풀 스쿼트의 무릎:고관절 굴곡 비율(서기 160°→바닥 100°까지 60°, 같은 구간 고관절은 160°→150°까지 10°, 비율 10/60)을 하프 스쿼트의 무릎 굴곡(160°→125°까지 35°)에 그대로 적용해 `35 × (10/60) ≈ 5.8° → bottom_hip ≈ 154°`로, `min_hip_drop`도 같은 비율로 `0.25 × (35/60) ≈ 0.15`로 비례 추정했다. 2026-09-21 검증에서 확립한 원칙("실측 없이 임계값을 믿지 않는다")을 그대로 적용해, **이 두 값은 하프 스쿼트 실촬영 영상으로 검증되기 전까지 잠정값으로 취급한다.** 검증 절차는 아래 참고.

`SquatCounter` 자체는 기존과 동일한 FSM을 쓴다 — 모드가 다른 것은 "바닥"으로 인정하는 각도 범위뿐이다.

### 배선: 세션별 상태로 흘려야 하는 이유

`StreamingSquatAnalyzer`는 `app/core/analyzer_registry.py`가 프로세스 기동 시 **딱 하나만 만들어 모든 세션이 공유하는 stateless 싱글턴**이다("stateless 클래스라 공유 가능" 주석). 그래서 분석기 자신의 `self.thresholds`를 세션마다 바꾸는 방식은 쓸 수 없다 — 동시에 실행 중인 풀/하프 세션이 서로의 임계값을 덮어쓰게 된다. 대신 `persona`가 이미 쓰고 있는 세션별 상태 경로(`SessionState.persona` → `SessionStateRegistry.create`/`create_if_absent`)를 그대로 따라 `depth_mode`를 흘리고, `SquatCounter`가 지연 생성되는 시점(`squat_analyzer.py`의 `process_frame`)에만 `state.depth_mode`로 임계값을 고른다. 재부착에서는 `persona`와 동일하게 기존 값을 덮어쓰지 않는다.

전달 경로: 프론트(종목 선택 화면) → `VideoRequestDto.depthMode` → `Session.squatDepthMode`(DB, `V23__add_squat_depth_mode.sql`) → `AnalyzeRequest.depth_mode`(gRPC, persona와 나란히) → `SessionState.depth_mode` → `SquatCounter` 생성 시 `DEPTH_MODE_THRESHOLDS` 조회.

### 깊이 정확도 점수와 회차별 코멘트

카운팅(반복 인정 여부)과 별개로, **채점은 backend에서** `pose_data.smoothed_knee_angle`(이미 저장되는 값, `SessionAnalysisCalculator`가 worst rep 판정에 쓰는 것과 같은 데이터)만으로 계산한다(`SquatDepthAnalysisCalculator`). 회차별 최소 무릎각을 모드별 목표(풀: 100도 이하 만점·115도까지 선형 감점, 하프: 115~140도 밴드 중심 만점·경계에서 70점)로 채점해 평균을 세션 점수로 낸다. 회차별 코멘트는 우선순위(인접 회차 낙차 → 하프 모드에서 풀 스쿼트급으로 깊어짐 → 얕은 회차 → 편차 큼 → 전부 양호)로 최대 4문장까지 생성한다.

**AI 임계값(반복 인정)과 backend 채점(점수)은 서로 다른 숫자를 쓰지만 개념적으로 연결돼 있다** — 하프 스쿼트 밴드(115~140도)가 바뀌면 `HALF_SQUAT_THRESHOLDS`와 `SquatDepthAnalysisCalculator`의 상수를 함께 재검토해야 한다.

실시간 중에는 기존 토스트(횟수·"깊이 확인/미확인")만 그대로 노출한다 — 깊이 점수·회차별 코멘트는 **운동 종료 후 리포트 화면에만** 나타난다. 실시간 음성 안내는 이 저장소에 아직 구현되어 있지 않다(`frontend/app/(tabs)/exercise.tsx`에 "TTS 보류" 주석만 있음).

### 검증 필요

이 기능은 **하프 스쿼트 실촬영 영상으로 아직 검증되지 않았다.** 2026-09-21 검증 보고서와 같은 절차 — 촬영 규약(45도, 전신, 시작·종료 2초 정지, 무릎이 115~140도 안에서 멈추는 깨끗한 5회) 준수 영상을 확보해 `evaluate_squat.py --depth-mode HALF --trace`로 사람 판정과 대조하고, `e1_walkthrough.py --depth-mode half`로 API 경로 전체를 확인한 뒤, `docs/verification/`에 별도 리포트로 남긴다. **그 전까지는 하프 스쿼트 모드의 정확도를 사용자에게 확정적으로 주장하지 않는다.**
