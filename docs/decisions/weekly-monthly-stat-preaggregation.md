## 0. 현재 코드 상태 — "통계"가 이미 없는 게 아니다

`WeeklySummaryService.getWeeklySummary`(회원 1명 · 기준일이 속한 1주)가 **이미 라이브 쿼리로** 존재한다:

| 층 | 구현 | 읽는 것 |
|---|---|---|
| A층 (`totalsBetween`) | QueryDSL, 쿼리 1회 | `exercise_sessions` 한 표, `member_id + status=COMPLETED + startTime 범위` |
| B층 (`repCurveBetween`, `worstRepDistributionBetween`) | 네이티브 `JSON_TABLE` | `reports.detailed_analysis` JOIN `exercise_sessions`, 같은 범위 필터 |

**저장하지 않기로 이미 결정된 상태다** — `WeeklySummaryService` 주석: "세션 20~30행 집계이고, 같은 입력이면 같은 문장이 나온다... 저장을 만들면 `reports.session_id NOT NULL`을 풀어야 하는데, 그 벽은 LLM을 붙일 때 만나면 된다." 즉 **"사전집계 안 함"이 이미 한 번 내려진 결정**이고, 3순위 착수는 그 결정을 뒤집는 일이다 — 뒤집을 근거가 있어야 한다.

세션 완료 시점에 뭔가를 미리 계산해두는 선례는 이미 있다: `SessionCompletionTx.precomputeReport`가 세션 완료 트랜잭션 안에서 `reports.detailed_analysis`를 채운다. 사전집계를 이벤트 기반으로 할 경우 이 지점을 그대로 재사용할 수 있다.

**#629와 다른 대상이라는 점**: `AdminStatsService.countGroupedByStatus`(#629)는 **전체 회원 전체 기간**을 `GROUP BY`하는 관리자용 집계라 테이블 총 행수에 정직하게 비례해서 느려진다 — 그래서 그 이슈는 "1000만 행에서도 커버링 인덱스 플랜이 유지되는가"를 묻는다. 여기(3순위)는 **회원 1명 스코프**라 전체 테이블 크기와 무관하게 비용이 거의 고정이다 — "느려진다"는 이야기 자체가 성립하려면 다른 근거가 필요하다(§1).

## 1. 착수 전에 먼저 좁힐 것 — 이게 어떤 문제를 푸는가

로드맵 §1 원칙: *"순진한 CRUD가 볼륨/동시성에서 깨지는 지점을 측정해 고친 증거"*가 없으면 이건 CRUD고 DB 포폴 주장은 공허하다. 지금 라이브 쿼리는 회원 스코프라 **행수 자체는 안 깨진다.** 그럼 뭐가 깨지는가 — 후보 세 갈래가 서로 다른 처방으로 이어진다:

| 후보 | 정확한 문제 | 맞는 처방 | 이게 맞다는 증거가 있나 |
|---|---|---|---|
| **① 반복 계산 낭비** | 같은 회원이 리포트 페이지를 여러 번 열면 매번 같은 입력으로 같은 계산을 다시 한다 | **캐시**(Caffeine/Redis) — 계산 결과가 결정적이므로 사전집계보다 훨씬 싸게 해결됨 | 없음 — 방문 빈도 미측정 |
| **② 범위 확장 시 스캔 비용** | 월간(30일)으로 넓히면 B층 `JSON_TABLE`이 스캔하는 세션·리포트 행수가 주간의 ~4배, 그 이상으로 헤비유저는 더 클 수 있음 | **사전집계**(배치로 미리 롤업) — 계산 자체가 무거워졌을 때만 의미 | 없음 — 월간 뷰 자체가 아직 없다 |
| **③ 동시 읽기 QPS** | 리포트 페이지 접속이 몰리는 시간대(예: 저녁)에 회원 수만큼 동시 쿼리가 DB에 부하 | **사전집계 + 배치 갱신**(읽기를 인덱스 lookup으로 낮춤) — QPS 자체를 낮추는 유일한 후보 | 없음 — 동시 리포트 조회 부하 실험 없음 |

**①이 맞다면 사전집계는 과한 해법이다** — `redis-introduction.md`의 엄격 증명 프레임(A 정확성·B 성능한계·C 확장성강제) 중 아무것도 충족 안 한 상태에서 캐시보다 무거운 배치 인프라를 놓는 셈이다. **셋 다 확인 안 된 채로 스키마부터 그리면 "사전집계로 포장한 CRUD"가 된다** — 이 프로젝트가 다른 후보(활동 피드 팬아웃 등)에서 이미 경계했던 함정과 같다.

**➡ 제안(결정 아님): §2~4의 설계 질문에 답하기 전에, 먼저 월간 뷰의 B층 쿼리 비용을 합성 볼륨(헤비유저 = 세션 다다익선 시딩)으로 한 번 재보고, ②/③ 중 어느 쪽이 실제로 존재하는 문제인지부터 좁히는 편이 싸다.**

## 2. 스코프 — 뭘 사전집계 대상으로 하나 (미결정)

| 옵션 | 의미 | 비고 |
|---|---|---|
| a. A층만 | `totals`(세션수·회차수·두 가중평균·활동일수) | 이미 회원 스코프 단일 쿼리라 **가장 싸다** — 사전집계 이득이 작을 수 있음 |
| b. B층만 | rep curve·worst 분포(JSON_TABLE) | §1 ②/③의 진짜 타겟일 가능성 — 계산이 무거운 쪽 |
| c. A+B 둘 다 | 주간 요약 전체를 한 행으로 | 리포트 응답 자체를 캐시하는 것과 사실상 같아짐(§1 ①에 가까워짐) |

## 3. 트리거 — 언제 채우나 (미결정)

| 옵션 | 의미 | 트레이드오프 |
|---|---|---|
| a. `@Scheduled` 배치(예: 매일 새벽 증분) | 로드맵 표 문구 그대로("배치 집계테이블, `@Scheduled`") | 방금 끝낸 세션이 "이번 주" 요약에 안 보일 수 있음(§4) |
| b. 이벤트 기반(`precomputeReport`처럼 세션 완료 트랜잭션에서 해당 주 행 upsert) | 기존 트리거 재사용, 신선도 문제 없음 | 세션 완료 경로에 쓰기 하나 추가 — 그 경로는 이미 #598(gRPC 스레드풀)·#276(멱등 데드락) 등으로 부하에 예민한 자리라 추가 전 영향 확인 필요 |
| c. 하이브리드(이벤트로 즉시 upsert + 배치는 정합성 재검증용) | 신선도 + 드리프트 방지 둘 다 | 가장 복잡, 구현 비용 최대 |

## 4. 신선도 — "이번 주"(아직 안 끝난 주)를 사전집계 대상에 넣나 (미결정)

- 지난 주(완전히 끝난 주)만 사전집계하고 이번 주는 지금처럼 라이브 쿼리로 남기는 안 — 배치 트리거(§3-a)와 궁합이 좋음, 신선도 문제가 구조적으로 없음(어차피 안 끝난 주는 안 다룸)
- 이번 주도 포함(부분 갱신) — 이벤트 트리거(§3-b) 필요, "방금 한 운동이 왜 요약에 없나"라는 사용자 기대를 안 깨는 대신 트리거 선택이 §3과 묶임

## 5. 스키마 — 사전집계 테이블 형태 (미결정, §2 스코프에 종속)

- 회원 × 주(또는 월) 1행 롤업 테이블 — 컬럼은 `WeeklyTotalsDto`/`RepCurvePointDto`/`WorstRepFrequencyDto`를 얼마나 그대로 반영하나에 따라 갈림(B층 포함 시 JSON 컬럼으로 다시 뭉칠지, 정규화된 여러 표로 나눌지)
- 월간을 "주간 4~5개 롤업의 롤업"으로 만들지, 월간을 독립적으로 원본에서 다시 집계할지 — 전자는 쓰기 재사용, 후자는 정의 일관성(주 경계 걸친 월 말일 처리 등)이 더 단순

## 7. 실측 — 후보②·③ 기각 (2026-09-08)

**방법**: `WeeklySummaryMonthlyCostRaceTest`(실 MySQL, race 프로파일) — 헤비유저 1명(매일 1세션×30일=30세션, 세션당 30회차, 2026-09-08 사용자 확정 가정)을 시딩하고 B층 쿼리(`repCurveBetween`·`worstRepDistributionBetween`)를 7일 vs 30일 범위로 N=7 반복 최소값 비교. 1라운드는 `reports` 테이블이 이 30행뿐인 상태, 2라운드는 배경 노이즈 40만 행(`admin-page-scope.md` §4-5·§9가 이미 세운 "DAU 1,000 가정 트리거" 수치를 그대로 재사용 — 새 숫자 발명 안 함)을 추가한 상태.

**1라운드 결과(테이블 전체 30행)**: 월간이 주간보다 안 느림(배율 0.48x·0.86x, 잡음 수준). 그런데 EXPLAIN에서 `reports`가 `member_id` 인덱스를 두고도 `type=ALL`(풀스캔)로 잡혀, "회원 스코프 실험이 우연히 테이블 전체 볼륨과 같아져 진짜 위험(전체 회원 볼륨 증가 시 인덱스 미사용)을 못 갈랐다"는 confound가 드러남.

**2라운드 결과(배경 40만 행 추가 후)**: **계획이 스스로 바뀌었다** — `exercise_sessions`를 드라이빙 테이블로 삼아 `idx_session_starttime_member`로 29행만 골라낸 뒤, `reports`는 `uk_report_session`(세션 유니크 키)으로 eq_ref 조회. 절대 응답시간도 6~7ms대(7일=6ms/4ms, 30일=7ms/7ms)로 오히려 더 빠르고 안정적이다.

**판정**: §1의 후보②(월간 확장 시 무거워짐)와, 1라운드가 새로 제기한 "전체 볼륨 증가 시 인덱스 미사용" 우려(③에 가까운 변종) **둘 다 40만 행 volume에서 기각됐다.** 옵티마이저가 테이블 통계에 맞춰 계획을 올바르게 재선택한다 — 이 쿼리는 이 볼륨에서 CRUD가 깨지는 지점이 아니다. 사전집계를 정당화할 남은 후보는 **①(같은 회원의 반복 방문 → 재계산 낭비)뿐**이고, 그건 사전집계가 아니라 **캐시**로 푸는 문제다.

**한계**: 40만 행은 이 프로젝트가 이미 세운 한 지점(DAU 1,000·1년 시점 추정)일 뿐 상한이 아니다 — #629가 다루는 1000만 행대에서 다시 계획이 나빠질 가능성은 이 실측이 답하지 않는다. 다만 그 자릿수는 `AdminStatsService`(전체 회원 GROUP BY, 진짜 볼륨 비례)의 영역이지 이 회원 스코프 쿼리의 영역인지는 별개로 봐야 한다 — 여기서 재확인할지는 미결정.

**➡ 결론(추천, 결정 아님): 지금 상태로는 3순위(주간/월간 통계 사전집계) 착수 근거가 없다.** 착수하려면 후보①(캐시 문제)부터 다시 증명해야 하고, 그건 `redis-introduction.md`의 엄격 증명 프레임(A/B/C 중 하나 충족)을 통과해야 한다 — 지금은 셋 다 미충족.

측정 코드: `backend/src/test/java/com/shadowfit/repository/report/WeeklySummaryMonthlyCostRaceTest.java`

> 표기 주의(2026-09-12): 이 절의 `reports` 는 실측 당시 이름이다. 그 뒤 [#729](https://github.com/Shadowfit/init/pull/729)(V16) 가 `session_reports` 로 바꿨고, race 프로파일은 [#722](https://github.com/Shadowfit/init/pull/722) 로 Testcontainers 가 됐다. 측정 코드는 둘에 맞춰 손봤다(테이블명·베이스 클래스만, 시딩·반복 수·가정은 그대로). 2라운드의 배경 40만 행은 코드에 없고 수동으로 넣었다 — 그대로 다시 돌리면 1라운드(30행) 조건이다.
