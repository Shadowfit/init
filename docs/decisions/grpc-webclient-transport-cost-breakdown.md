## 1. 왜 또 재나 — 2차 결과가 「이진화」로 설명되지 않는다

2차 라운드는 프로덕션 클라이언트로 두 팔의 왕복을 쟀고 두 자리 다 갈렸다:

| RPC | 요청 크기 | webclient − grpc |
|---|---|--:|
| `StopAnalysis` | `session_id` 하나(수십 바이트) | **+1.8 ms** |
| `ReattachAnalysis` | 기준좌표 **97.6 KB** | **+3.0 ms** |

**직렬화(protobuf ↔ JSON)가 지배했다면 작은 요청의 델타는 0 에 가까워야 한다.** 그런데 1.8ms 다.
즉 이 차이는 대부분 **크기와 무관한 고정비**이고, 크기에 비례하는 몫은 나머지 **~1.2ms** 다.

> 🔴 그러므로 「gRPC 가 이진화라 빠르다」는 서사는 **이 데이터로 못 받친다.** 방향은 맞지만
> 기제가 다르다. 기제를 모른 채 «빠르다» 만 인용하면, 나중에 nginx 를 걷어내거나 클라이언트를
> 바꿨을 때 왜 값이 달라졌는지 설명할 수 없다.

**이 라운드가 답하려는 질문 하나**: *그 고정비 1.8ms 는 어디서 오나 — nginx 홉인가, 블로킹 브리지인가.*

후보 셋(2차 §4 에서 열어둔 것):

| # | 후보 | 왜 그럴듯한가 |
|---|---|---|
| ㄱ | **nginx 홉** | webclient 팔만 `ai-nginx` 를 거친다. gRPC 는 8585 직결이다. 1차 라운드가 같은 홉을 **0.1~0.8ms** 로 쟀다 — 크기는 맞지만 **1.8ms 를 다 설명하진 못한다** |
| ㄴ | **블로킹 브리지** | WebClient 는 `Mono` 를 `.block()` 으로 기다린다 — 이벤트루프 스레드로 넘겼다가 되받는 왕복이 낀다. gRPC 블로킹 스텁은 호출 스레드가 그대로 대기한다 |
| ㄷ | **커넥션 취급** | HTTP/1.1 커넥션 풀 ↔ 미리 세워둔 gRPC 채널. 워밍업 뒤라면 이미 상쇄됐을 수도 있다 |

## 2. 설계 — 팔 3개와 «뺄셈»

팔을 하나 더 만들어 **홉을 뺀 조건**을 세운다. 새 코드는 필요 없다 — `ai.webclient.base-url` 이
이미 `http://${AI_NGINX_HOST:ai-nginx}:${AI_NGINX_PORT:8000}` 라 **환경변수만 바꾸면** WebClient 가
nginx 를 건너뛰고 AI 워커를 직접 친다(`application.yml:152`).

| 팔 | 전송 | 경로 |
|---|---|---|
| **A. grpc** | grpc-java 블로킹 스텁 | Spring → `shadowfit-ai:8585` (직결) |
| **B. webclient-nginx** | Spring WebClient | Spring → `ai-nginx:8000` → 워커 |
| **C. webclient-direct** | Spring WebClient | Spring → `shadowfit-ai:8000` (**홉 없음**) |

**뺄셈이 답이다**:

- **(B − C) = nginx 홉 비용.** 같은 클라이언트·같은 직렬화라 도구 오프셋이 원리적으로 안 낀다.
- **(C − A) = 남은 고정비.** 홉을 뺀 뒤에도 남는 것 = 블로킹 브리지(ㄴ) + 커넥션 취급(ㄷ) + 직렬화.
- 이 둘을 **작은 요청(Stop)과 큰 요청(Reattach) 두 크기에서** 각각 재면, 「고정비」와 「크기 비례
  몫」이 같은 표에서 갈린다.

### 2-1. ㄷ(커넥션)은 뺄셈이 아니라 «증거» 로 좁힌다

팔을 하나 더 만드는 대신 **nginx 액세스 로그에 `$connection` 을 찍어** 커넥션 하나가 요청 몇 개를
나르는지 센다. 재사용률이 1:N 이면 ㄷ 는 워밍업 뒤에 이미 상쇄된 것이고, 1:1 이면 매 요청이 새
커넥션이라는 뜻이라 ㄷ 가 살아 있다. 같은 로그의 `$request_length` 로 **실제 요청 바이트 수**도
같이 남긴다 — 2차에서 「97.6KB」는 DB 원자료 기준 추정이었고 **전선 위 크기를 잰 적은 없다.**

## 3. 공정성 장치 (이게 없으면 다른 걸 재게 된다)

1. **전 팔 워커 0 고정** — `AI_CHANNEL_POOL_SIZE=1` 로 둔다. 그러면 gRPC 는 채널 0(8585)만 쓰고
   `X-AI-Worker` 헤더도 항상 `0` 이라 B·C 도 워커 0 으로 간다. 안 그러면 팔마다 **병렬도**가 달라
   프로토콜이 아니라 분산을 재게 된다(1차 rig 이 같은 장치를 썼다).
   ⚠️ 2차는 풀 3 이었다 — **조건이 다르므로 2차 절대값과 직접 비교하지 않는다.**
2. **같은 사이클** — 세션 시작 → 재부착(큰 요청) → 종료(작은 요청). 2차와 같은 rig 을 쓴다.
3. **팔 전환은 재기동** — `ai.client-type`·`AI_NGINX_HOST` 둘 다 스타트업 프로퍼티다. 전환 뒤
   `printenv` 게이트로 **팔이 실제로 바뀌었는지 확인**하고 넘어간다(2차에서 이 게이트가 조용한
   오염을 잡았다).
4. **배수 대기** — `stop` 은 아웃박스 발행기가 비동기로 보낸다. 블록 경계에서 stop 누적이 멎을
   때까지 기다린 뒤 스크레이프한다. 안 그러면 잔여가 다음 팔로 넘어간다.

## 4. 절차

- 팔 3개 × 블록 5 + **버림 블록 1라운드**. 팔 순서는 라틴 방격으로 돌린다 — `A→B→C`, `B→C→A`,
  `C→A→B` … (팔이 3개면 순서 반전만으로는 부족하다).
- 블록당 100 사이클, 블록 앞에 워밍업 10 사이클.
- 회수는 2차와 같다 — `shadowfit.ai.call` 버킷 차분(누적 타이머라 차분해야 블록이 갈린다).
- 예상 소요: 전환 16회 × ~1.5분 + 본판 ≈ **1시간 안팎**, 인스턴스 1대(`c7i.2xlarge`).

**판정 규칙(실행 전 고정)**: 2차와 같다 — 블록별 값의 **범위가 겹치지 않을 때만** 「효과」라고
부른다. 그리고 이 라운드는 승패가 아니라 **분해**가 목적이므로, 결론은 다음 세 문장 중 하나로만 쓴다:

- (B−C) 가 고정비의 대부분 → **기제는 홉이다.** nginx 를 거치는 구조가 비용의 주범.
- (C−A) 가 대부분 → **기제는 클라이언트 쪽이다**(블로킹 브리지·커넥션). 홉을 걷어내도 안 준다.
- 둘 다 겹쳐 판별 불가 → **이 무대에서는 못 가른다**(그대로 적는다).

## 5. 안 재는 것

- **동시성.** c=1 닫힌 루프다. 이벤트루프와 채널 풀의 차이는 동시 호출에서 다르게 나타날 수 있고,
  그건 별도 축이다.
- **채택 여부.** 이 라운드도 수치만 만든다.
- **직렬화 자체의 CPU.** 왕복 총합만 본다 — 인코딩 시간을 따로 재려면 클라이언트 안에 계기를
  더 넣어야 하고, 그건 이 라운드 범위 밖이다.
- **gRPC 쪽 홉.** gRPC 경로에는 nginx 가 없다(그게 §1 ㄱ 후보의 전제다).

## 6. 착수하려면 필요한 것 (아직 안 함)

| # | 무엇 | 크기 |
|---|---|---|
| 1 | rig 에 팔 3개 지원 — `ARMS="grpc webclient-nginx webclient-direct"`, 팔마다 `AI_CLIENT_TYPE`·`AI_NGINX_HOST` 조합을 세팅 | 중 (기존 `switch_arm` 확장) |
| 2 | 라틴 방격을 3팔로 — 지금은 2팔 순서 반전만 있다 | 소 |
| 3 | `nginx-ai/default.conf` 에 `log_format` 추가(`$connection`·`$request_length`) + 라운드 끝에 그 로그 회수 | 소 |
| 4 | 분석기에 3팔 뺄셈 표 추가((B−C)·(C−A) 를 블록별로) | 중 |
| 5 | 부트스트랩 `ROLE=client-ab` 에 `AI_CHANNEL_POOL_SIZE=1` 조건 명시 | 소 |

🔴 **로컬 스모크를 먼저 돌린다.** 2차 라운드는 EC2 를 네 번 띄워 셋을 헛돌렸고, 원인은 전부
「로컬에서 안 밟아본 코드를 EC2 에서 처음 밟은 것」이었다. 로컬 N=2·블록1 스모크 한 판이 그때
결함 넷을 잡았다 — 이번에는 그 순서를 먼저 지킨다.

## 7. 결정 로그

- 2026-09-10: 문서 신설. 2차가 「이진화로 설명 안 되는 고정비 1.8ms」를 남겨서, 그걸 홉(ㄱ)과
  클라이언트 쪽(ㄴ·ㄷ)으로 가르는 뺄셈 설계를 세웠다. **착수 여부·시점은 사용자 결정.**
- 2026-09-10: **실행 완료.** `RUN_ID=ec2-20260910-145300` · 본 측정 1,075초 · 팔 3 × 블록 5 × 100사이클.
  §4 가 정한 세 문장 중 **「기제는 클라이언트 쪽이다」** 로 닫혔다 — 두 RPC 다 홉과 잔여의
  범위가 안 겹친다(홉 최대 0.882ms < 잔여 최소 1.353ms).
  - **홉(B−C)**: Stop 0.013~0.409ms · Reattach 0.068~0.882ms. 1차 라운드가 **다른 방법으로**
    잰 0.1~0.8ms 와 같은 자리다 — 독립 두 판이 생겼다.
  - **잔여(C−A)**: Stop 1.353~1.906ms · Reattach 2.001~3.029ms. 크기 무관 몫 ~1.4ms +
    크기 따라 붙는 몫 ~0.6~1.1ms 로 갈린다(간접 논증).
  - **커넥션 후보(ㄷ)는 증거로 지웠다** — 요청 1,680건이 커넥션 17개를 탔고(재사용률 98.8,
    커넥션당 최대 126건), 매 요청 새 커넥션이 아니다. §2-1 이 팔 대신 로그로 좁히자고 한
    그대로 됐다.
  - **덤**: 전선 위 실제 요청 크기를 처음 쟀다 — Reattach **114,223 B**(DB 원자료 기준 추정
    97.6KB 보다 17KB 큼, JSON 봉투 몫) · Stop **279 B**.
  - 🔴 남은 것: **잔여의 내부 분해**(브리지 ↔ 직렬화)는 안 했다. 그러려면 클라이언트 안에
    계기가 더 필요하다. 그리고 **동시성 축은 그대로 미측정**이다.
