## 0. 왜 이 문서인가

목표 RTO(§6-3)는 «호스트 상실 → 구성 2 복구 **약 7분**» 위에 서 있다. 그런데 7분은 **서로 다른 실험 셋의 합**이다:

| 단계 | 값 | 어디서 | 그 실험의 무대 |
|---|---|---|---|
| 새 서버 준비 | 약 140초 | 새 서버 준비 실측 | 빈 EC2 → 빈 MySQL. 백업·binlog 없음 |
| 백업 붓기 (물리) | 약 174초 | 백업 복구 실측(08-13) | **1억 행** · S3 아님(로컬 파일) |
| binlog 재생 | 하루치 약 80~95초 | 재생 실측 | 재생만. 내려받기·백업과 이어 붙이지 않음 |

빠진 것:
- **이어 붙인 적이 없다** — 단계 사이의 손(파일 위치·GTID 시작점·권한·설정 차이)에서 막히는지 모른다
- **앱이 다시 붙는 것까지 간 적이 없다** — 사용자가 «다시 저장된다» 를 보는 시각이 목표 RTO 의 정의다(§6-3 · 페일오버 실측과 같은 정의)
- **절차가 문서로 없다** — 사람 시간 30·60분은 «알림 보고 복구를 시작» 까지고, 시작한 뒤 무엇을 치는지는 rig 안에만 있다

면접 질문 «복구 훈련 해 봤나요?» 에 지금은 «단계별로는 쟀다» 까지만 답할 수 있다.

## 1. 훈련 한 판의 모양 (후보와 무관한 뼈대)

```
[원본 박스]  운영과 같은 스택 + 가정 피크 쓰기 + 백업(XtraBackup → S3) + binlog 반출(N초 주기 → S3)
     │
     ▼  ⏱ t0 = 원본 인스턴스 강제 종료(terminate) — 진짜 호스트 상실. 알아채기·결정 = 0 (다른 실험과 같은 규칙)
[새 박스]   run-instances → bootstrap → S3 에서 백업 내려받기 → prepare·copy-back → 기동
            → S3 에서 binlog 내려받기 → 재생 → (앱 기동 · DB 주소 전환) → 쓰기 API 첫 성공  ⏱ t1
```

재는 것: **t1 − t0** 와 단계별 누적 시각 · 잃은 쓰기(«성공 응답 받았는데 새 DB 에 없는» 것 — 반출 주기 이하여야 한다) ·
데이터 정합(행 수 · 체크섬) · 막힌 곳과 손으로 고친 것(있으면 그것이 결과다).

## 2. 결정할 것

### D1. 어디까지 되살리나

| # | 끝 지점 | 장점 | 단점 |
|---|---|---|---|
| a | DB 가 쿼리를 받음 | 앞 실험들과 같은 끝 지점이라 7분과 바로 비교 | 사용자 기준 RTO 가 아니다 |
| **b** | **앱이 새 DB 로 쓰기 API 첫 성공** | §6-3 목표의 정의와 같다. 페일오버 실측(#849)의 «회복» 과 같은 정의 | 앱 기동·주소 전환이 더해진다(앱 기동 12~18초 실측, 주소 전환 방식은 아래 D2) |

**추천: b.** 목표 RTO 를 확인하는 훈련이라 끝 지점이 목표의 정의와 같아야 한다.

### D2. 앱은 어디 있나 (D1 = b 일 때)

| # | 구성 | 의미 |
|---|---|---|
| **a** | **앱 박스는 살아 있고 DB 박스만 잃는다** — 앱은 DB 주소를 바꾸고 재시작 | 운영에서 DB·앱을 다른 호스트에 둔다는 전제. 페일오버 실측의 A(주소 바꾸고 재시작)와 같은 방법 |
| b | 한 박스에 앱+DB — 박스를 잃으면 둘 다 새로 | 지금 운영 compose(한 호스트)에 더 가깝다. 대신 새 박스에서 앱 이미지 빌드·기동 시간이 더해진다 |

**추천: b.** 운영 배포가 한 호스트 compose(`docker-compose.prod.yml`)라서 «호스트를 잃었다» 면 앱도 같이 잃는다.
a 는 운영 구성을 바꾸자는 전제가 숨어 있다. b 는 새 박스에서 앱 이미지를 레지스트리(`ghcr.io/shadowfit/init/backend`,
`docker-compose.prod.yml:72`)에서 내려받는 시간이 더해진다 — 운영과 같은 경로라 그 시간도 RTO 의 일부다.

### D3. 데이터 크기와 «백업 이후 시간»

7분은 **1억 행 백업 + 하루치 binlog(0.6GB)** 가정이다.

| # | 크기 | 판당 비용 | 7분과 비교 |
|---|---|---|---|
| a | 1억 행 + 하루치 binlog | 시딩이 길다(1억 행 합성 — 08-13 은 수 시간). 디스크 2~3배 | **그대로 비교 가능** |
| **b** | **1,000만 행 + 하루치 binlog** | 시딩 약 14분(11-08 natpk 실측 822초) | 백업 붓기만 작아진다 → 붓기 칸은 1억 행 값(174초)으로 따로 둔다 |
| c | 1,000만 행 + 짧은 쓰기만 | 가장 싸다 | 재생 칸이 비어 7분의 절반을 확인 못 한다 |

**추천: b.** 이 훈련이 닫고 싶은 빈칸은 «이어 붙였을 때 막히는가 · 앱까지 몇 초 더 드는가» 이고, 각 칸의 크기 비례는
이미 따로 쟀다(붓기 1억 행 174초 · 재생 1GB 당 2분 15초). 하루치 binlog 0.6GB 는 원본에서 «가정 피크로 몇 시간 쓰기» 대신
**백업 직후 binlog 0.6GB 를 빠르게 쌓는 방식**으로 만든다(재생 실측과 같은 writer) — 쌓는 속도는 재생 시간에 영향이 없다고 보지만
확인하지 않았다(재생 실측은 속도를 바꿔 보지 않았다).

### D4. 누가 복구하나

| # | 방식 | 재는 것 |
|---|---|---|
| **a** | **복구 스크립트 한 개(`recover.sh`)를 만들고, 무인으로 실행** | 기술 시간. 반복 가능 |
| b | 사용자가 문서(런북)를 보며 손으로 | 사람이 실제로 치는 시간 — 진짜 «훈련» |

**추천: a 먼저, b 는 그 뒤 한 번.** a 로 막히는 곳을 없애고 스크립트를 만든 뒤, 사용자가 그 스크립트를 런북대로 한 번 쳐 보면
«알림 받고 → 노트북 열고 → `recover.sh` 실행» 의 사람 쪽이 확인된다(§6-3 의 사람 30분 안에 드는지). a 의 산출물이
곧 운영 런북이 된다.

### D5. 반복

**추천: 버림 1 + 본판 3.** 판마다 원본·새 박스 2대를 새로 띄운다(진짜 terminate 라서 재사용 불가). 판 하나는 시딩 14분 +
binlog 쌓기 + 복구 약 10분 남짓으로 예상 — 4판을 한 라운드에 순서대로 돌리면 약 2~3시간(추정).

## 3. 범위 밖

- 알아채기·결정 시간(감시·알림) — 0 으로 둔다. 알림은 별도 작업(§6-3 전제)
- 미리 구운 AMI · 이미지 레지스트리 경로 — 이번 결과로 «무엇이 길었나» 가 나오면 그때 후보
- 논리 사고 복구(PITR 로 사고 직전까지) — 끝 지점이 다르다(사고 시점 찾기). 목표 RTO 도 아직 미정
- 다른 리전 복구
- AI 서버 기동 — 끝 지점을 «백엔드 쓰기 API 첫 성공» 으로 잡아서 빠진다. 운동 분석까지 되살아나는 시각은 AI 이미지 내려받기·기동이 더해진다(안 잼)
