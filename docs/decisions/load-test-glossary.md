## 1. 테스트 모드 (ghz `-Mode`)

부하를 점점 키우는 3단계. `loadtest/ghz/run-save-pose-batch.ps1` 에 구현.

| 모드 | 동시성 | 양 | 목적 | 한 줄 |
|------|--------|----|------|-------|
| **smoke** | 1 | 5 call | 경로·인증 살아있나 | "연결 되나?" 연막탄 한 발 |
| **baseline** | 1 | 200 call | 방해 없는 순수 지연 | "혼자면 얼마나 빠른가?" 기준선(0점) |
| **ramp** | 5→100 step | 210초 | 한계·천장 탐색 | "어디서 무너지나?" 계단 상승 |

### baseline (베이스라인)
동시성 1로 요청을 **하나씩 순차** 호출 → 서버가 안 붐비는 이상적 상태의 처리 시간. 나중에 ramp 숫자가 좋은지 나쁜지 판단할 **비교의 0점**. 이게 없으면 "p99 500ms" 가 부하 탓인지 원래 느린 건지 알 수 없음.

### 스윕 (sweep)
**변수 하나를 여러 값으로 바꿔가며 같은 측정을 반복**하는 것. "pool 스윕"(`maximum-pool-size`를 5·10·15·20으로), "N스윕"(AI 프로세스 수를 1·2·3·4로), "워커 스윕"(#276 동시 삽입 워커 수), "커넥션 스윕"(ghz `--connections`)처럼 어떤 변수든 스윕할 수 있다. 스윕에서 바뀌는 값 하나하나가 [§3의 **팔**](#3-실험-설계-용어--팔판라운드)이고, 그래프로 그리면 어디서 천장/절벽이 꺾이는지 보인다. **ramp는 concurrency를 스윕하는 특정 방식**(계단식 점증)이라 스윕의 부분집합.

### ramp (램프)
동시 요청 수를 계단처럼 **점점 올리며**(이 프로젝트: 5→10→…→100, 5씩, 각 10초) 부하를 키운다. 두 가지를 본다:
1. **throughput 천장** — 동시성을 올려도 처리량이 더 안 늘고 평탄해지는 지점 = 백엔드 한계
2. 그 지점의 **p99 지연 / 에러율** — 한계 근처에서 얼마나 느려지고 깨지나

> 비유: baseline = "차 한 대 0→100 몇 초?", ramp = "도로에 차를 5대→100대 밀어넣으며 언제 막히나".

⚠️ ramp 은 session 801 에 **실제 row 를 누적 INSERT**. 측정 후 `DELETE FROM pose_data WHERE session_id = 801;` 로 정리(더미 세션 row 자체는 보존).

## 2. 측정 지표

### concurrency (동시성, `-c`)
동시에 날아가는 요청 수. 1이면 줄 서서 하나씩, 100이면 100개가 한꺼번에. ramp 은 이 값을 키우는 것.

### throughput / RPS (처리량, requests per second)
**초당 처리한 요청 수.** 부하를 키워도 더 안 오르고 평탄해지는 값 = 백엔드가 버틸 수 있는 천장. baseline RPS(이번 측정 12.9)는 동시성 1이라 낮음 — 천장이 아니라 단발 속도일 뿐.

### latency percentile — p50 / p90 / p95 / p99 (백분위 지연)
요청들의 응답 시간을 **느린 순으로 줄 세웠을 때 그 위치의 값**. 평균(average)은 소수의 느린 요청에 가려지므로 분포로 본다.

| 지표 | 뜻 | 읽는 법 |
|------|----|---------|
| **p50** (중앙값) | 절반이 이 시간 안에 끝남 | "보통의 사용자 경험" |
| **p95** | 95%가 이 안에 끝남 | "거의 다 이 정도" |
| **p99** | 99%가 이 안에 끝남 | "최악의 1% — 꼬리 지연" |

> 예: p50 60ms / p99 446ms = 보통은 빠른데 100명 중 1명은 446ms 까지 기다림(콜드스타트·GC·락 경합 등). **p99 가 시스템 안정성의 진짜 척도** — 평균이 멀쩡해도 p99 가 튀면 누군가는 매번 느림.

### SLO (Service Level Objective, 서비스 수준 목표)
"이 정도는 지키겠다"는 **성능 합격 기준**. 이 프로젝트 후보: "콜백 p99 < 20ms, 리포트 조회 p95 < X ms, 적재 누락 0"([strategy §10·§11](./load-test-strategy.md)). 측정값을 SLO 와 비교해 합격/불합격 판정.

### baseline / 판정선(Decision Line) / 운영 SLO — 셋을 섞으면 안 된다
[`slo-baseline.md`](./slo-baseline.md) §0·§5-1 이 세운 구분. 이 프로젝트는 이 셋을 자주 헷갈렸다.

| 용어 | 뜻 | 언제 쓰나 |
|---|---|---|
| **baseline** | 그냥 **관측된 값**(합격선 아님) | "지금 이 정도다"만 기록. 벗어나면 원인을 묻는 트리거 |
| **판정선(Decision Line)** | *"이 수치면 손대야 하나"*를 **실행 전에** 못박은 값 | 근거(🟢 실측·코드 유도·외부 앵커) 없이는 세우지 않는다. 근거 없는 자리는 값을 넣지 말고 **비운다**(🟡, [[feedback_no_arbitrary_threshold_values]]) — "임의라고 적어둔다"는 절충도 여기선 안 먹힌다(#87 이후 채택) |
| **운영 SLO** | 실서비스가 지키기로 한 약속 | 지금은 세울 재료(트래픽 규모·조직 합의)가 부족해 대부분 비어 있다 |

### 효과(effect)로 부르는 조건 — 델타 ≠ 효과
[`load-test-strategy.md` §2-1](./load-test-strategy.md)에서 확정(2026-08-23). 판 사이 자연 변동이 재려는 차이보다 클 수 있다는 사고(#87: 락을 "추가한" 판이 5판 중 38% 더 빨랐다)를 겪은 뒤 생긴 규칙.

- **인정 조건**: 교차 반복(before/after/before/after…)에서 얻은 두 분포가 **겹치지 않을 것**.
- **변동 폭을 모르면 델타를 "효과"라 부를 자격이 없다** — 폭부터 잰다.
- 배수(예: "2배 넘으면 효과")도 안 쓴다 — 배수 자체가 임의값이었다.
- 3.47배(fsync) 같은 큰 델타는 이 기준에서도 살아남지만, −35% 급 작은 델타는 재검증 전엔 "효과"로 인용하면 안 된다.

## 3. 실험 설계 용어 — 팔·판·라운드

이 프로젝트 실험 대부분이 A/B(또는 A/B/C…) 대조 + 반복 측정 구조라서, 아래 어휘가 없으면
설계 문서가 안 읽힌다. 계기는 [`commit-count-and-mysql-metrics.md`](./commit-count-and-mysql-metrics.md) §0-1
— 팔당 1판씩만 재고 순서를 뒤집었더니 "N 클수록 +32%"와 "N 작을수록 +36%"가 둘 다 나왔다.
**팔(조건)과 판 순서(시간 추세)가 같은 축에 겹치면 원리적으로 분리가 안 된다**는 걸 그때 배웠다
([[feedback_measure_design_needs_repeats]]).

### 팔 (arm)
비교하려는 **조건 하나**. "A팔 = 기본 설정, B팔 = 완화 설정" 식으로 부른다. A/B 테스트의 "그룹"과 같은 개념.

### 판 (trial)
한 팔을 **한 번** 실행해서 얻은 관측 하나. "A팔 3판"이면 같은 조건으로 세 번 쟀다는 뜻.

### 라운드 (round)
여러 팔을 한 번씩 순서대로 도는 **한 바퀴**. 라운드를 여러 번 반복해서 팔당 판 수를 채운다.

### 라틴 방격 (Latin square)
**팔 순서를 라운드마다 다르게 배열**해서, 시간에 따라 생기는 추세(버퍼풀 워밍업, 박스 발열,
디스크 예열 등)가 특정 팔에만 쏠리지 않게 하는 배치법. 팔이 3개면 `A→B→C`, `B→C→A`, `C→A→B`
처럼 순환시킨다. 팔이 2개면 순서 반전(`A→B`/`B→A`)만으로 충분하고, 라틴 방격이 성립하려면
**최소 팔 2개**가 있어야 한다(팔이 1개뿐이면 순서 효과 자체가 없으니 반복 횟수만 늘린다).
⚠️ 판 수는 **팔 수의 제곱**으로 늘어난다 — 팔이 4개에서 5개로만 늘어도 라운드가 17→26판이 된다.

### 버림판 (discard round / warm-up trial)
데이터를 기록에 넣지 않는 **워밍업 1판**. 캐시·커넥션 풀·JIT 등이 아직 안 데워진 첫 판을 통계에
섞으면 그 팔이 부당하게 불리해 보인다. 라틴 방격 라운드 앞에 관례적으로 1판 붙인다.

### 무대 (stage)
실험이 도는 **환경 조건 전체**(로컬 단일 컨테이너 / EC2 몇 대 · 어떤 인스턴스 타입 · 동거 여부 등).
같은 질문이라도 무대를 바꾸면 답의 절대값·심지어 방향까지 바뀔 수 있다(예: 유니크 키 대가가
"메모리 안" 무대에서는 −2.9%, "버퍼풀 초과+흩기" 무대에서는 −46%). **무대부터 정하고 질문을
맞추면 안 된다** — 질문이 먼저 서고, 그 질문이 요구하는 무대를 고른다.

### rig
실험을 자동으로 돌리는 **스크립트/하네스 전체**(부하 생성 + 계측 수집 + 결과 집계). "rig 결함"은
측정 로직 자체의 버그를 뜻하며, 이 프로젝트에서 결과보다 rig 결함 찾기에 시간이 더 든 경우가
여러 번 있었다(없는 카운터를 8판 내내 읽고 조용히 0을 찍는 식 — [#271](https://github.com/Shadowfit/init/issues/271) 계열).

### 계측 (instrumentation)
측정 대상에서 **관측값을 뽑아내는 경로**(메트릭 엔드포인트, 로그 파싱, `docker exec` 조회 등).
"현상"과 "계측"을 구분하는 게 중요했던 사례가 많다 — 예: 복제 지연이 08-17엔 안 잡혔는데
원인은 지연이 없어서가 아니라 계측 바닥이 +1초라서였다.

### calib축 (calibration axis)
비교 대상 두 박스/두 시점의 **개체차를 따로 재는 축**. 예: 순수 파이썬 루프 속도만 재는
"cpu축", MediaPipe 추론 속도만 재는 "infer축". 본 실험 델타를 calib축 델타로 나눠서 "환경차로
설명되는 몫"과 "설명 안 되는 몫"을 가른다.

## 4. 프로젝트 표기 컨벤션

`experiment-inventory.md`·`AWS-RIDE-ALONG.md`를 읽을 때 필요한 약어들. 전역으로 엄격히 정의된
번호 체계는 아니고, 각 문서 표 안에서 매기는 지역 번호다.

| 표기 | 뜻 |
|---|---|
| **P#** (P1, P4…) | `AWS-RIDE-ALONG.md`의 **우선순위 항목** 번호. "P4 = 복제 지연·반동기 대가" 식으로, EC2를 띄울 때 태울 후보에 매긴 번호 |
| **Q#** (Q1, Q2…) | 한 실험 설계 안에서 쪼갠 **개별 질문**. 예: "Q1 = 08-09 결론을 pose_data로 인용해도 되는가", "Q2 = 보존정책 비용이 삭제량에 의존하는가" |
| **H#** (H1, H2, H3…) | **가설(Hypothesis)**. 예: "H1 = 그룹 커밋 붕괴로 패딩이 낭비된다", "H3 = 캡이 옆 워크로드를 지켜준다" — 실험은 대개 이걸 반증하거나 확증하려고 짠다 |
| **R#** (R6, R10-a, R276…) | `AWS-RIDE-ALONG.md`에 등록된 **라운드/실험 실행 번호**. 이슈 번호를 그대로 딴 것(R276 = 이슈 #276 실험)도 있고 순차 번호도 있다 |
| **從 / 主** | 한 EC2 라운드 안에서 **主(주) = 그 박스를 띄운 이유가 된 실험**, **從(종) = 같은 박스에 얹혀 공짜로 회수하는 부수 실험**. "從 R6·R7도 같이 회수했다"처럼 쓴다. 從은 "등록"됐다고 "채택"된 건 아니다 — 얹을 자리가 없으면 그 라운드 자체가 안 선다 |
| **재고표** | `experiment-inventory.md` 자체를 가리키는 말. "무엇이 아직 안 재졌나"만 보는 **목록**이고, 개별 결함의 원본은 이슈, 탑승 판단의 원본은 `AWS-RIDE-ALONG.md`다 — 재고표는 원본이 아니라 **요약**이라 낡을 수 있다 |
| **정본** | 재고표가 가리키는 **결론이 실제로 확정돼 있는 설계/결정 문서**(예: `ai-process-ceiling-cause.md`). 재고표와 정본이 어긋나면 정본이 맞다 — 이 저장소에서 반복된 실패 패턴이 "정본은 갱신됐는데 재고표만 옛 문구를 들고 있는 것"([[project_doc_drift_pattern]]) |
| **문서 드리프트** | 코드/실험 결과는 바뀌었는데 그걸 가리키는 **다른 문서의 문구가 안 따라가는 현상**. 기능 표는 맞고 "보장·관측·운영" 설명이 뒤처지는 방향으로 주로 일어난다 |

## 5. AI 축 전용 용어

CPU 격리 실험(GIL 규명, N-프로세스 스윕)에서 쓰인 용어.

### GIL (Global Interpreter Lock)
CPython이 한 프로세스 안에서 **파이썬 바이트코드를 한 번에 한 스레드만** 돌리게 막는 락.
C++로 짜인 라이브러리(MediaPipe 추론 본체)는 이 락을 풀고 병렬로 돌 수 있지만, 그 앞뒤 파이썬
코드(프레임 수신·후처리 루프)는 못 푼다. 이 프로젝트의 "9.5 vCPU 천장" 원인이 결국 이거였다.

### rho (총 점유율)
GIL을 **어느 스레드든** 누가 쥐고 있는 시간 비율. `rho`≥0.939면 관측 시간의 94% 가까이
GIL이 항상 누군가에게 잡혀 있었다는 뜻 — 파이썬 경로가 병목이라는 직접 증거로 썼다.

### 천장 (ceiling)
동시성/부하를 올려도 처리량이 더 안 오르고 평탄해지는 지점(§1 ramp의 "throughput 천장"과
같은 개념이지만, AI 축에서는 **CPU 사용량(vCPU)** 기준으로도 따로 잰다 — "9.5 vCPU 천장",
"14.5 vCPU 두 번째 천장"처럼 쓴다).

### 코어레지던시 (co-residency)
여러 워크로드(예: AI 세션 처리 + 일반 HTTP 요청)가 **같은 박스의 CPU를 나눠 쓰는 상태**.
"코어레지던시 대가"는 옆 워크로드가 그 공유 때문에 느려지는 정도를 뜻한다.

### 스티키 라우팅 (sticky routing)
같은 세션의 요청을 **항상 같은 프로세스/인스턴스로** 보내는 라우팅 방식. 멀티프로세스로
쪼갤 때 세션 상태(검출기 등)를 프로세스 간에 옮기지 않으려고 필요하다.

---

## 6. 도구·인프라 용어

### ghz
gRPC 전용 부하 테스트 CLI. `SavePoseDataBatch` 같은 gRPC 메서드를 풀스로틀로 호출. **reflection** 켜져 있으면 proto 파일 없이 스키마 자동 인식.

### reflection (gRPC 리플렉션)
서버가 자기 스키마(메서드·메시지 구조)를 런타임에 알려주는 기능(`grpc.server.reflection-enabled: true`). 켜져 있으면 클라이언트(ghz)가 `.proto` 파일·import 경로 지정 없이 호출 가능.

### Locust
HTTP/E2E 부하 테스트 도구(Python). ③ E2E 트랙(실제 프레임 리플레이)용 — ② ghz 와 별개.

### R 값 (이 프로젝트 고유)
rep(반복 동작) 1회당 전송되는 **포즈 프레임 수**. PoseData 1행 = 분석 프레임 1개. 모든 시딩량 산정의 기준인데 아직 추정치(R≈20~30) — 실제 스쿼트 세션 1회 로그로 확정 필요([strategy §7](./load-test-strategy.md)).
