## 1. 왜 재나 — 세 라운드가 전부 c=1 이었다

3차까지의 결론은 「webclient 팔이 호출당 **1.4ms 안팎의 크기 무관 고정비**를 더 내고, 그것은 nginx
홉도 커넥션 수립도 아닌 **클라이언트 구조** 쪽」이다. 남은 후보는 **블로킹 브리지**(`Mono` 를
`.block()` 으로 기다리는 왕복)와 직렬화다.

그런데 세 라운드 다 **닫힌 루프 c=1** 이었다. 브리지가 기제라면 그 대가는 지연 1.4ms 보다
**동시 호출에서** 더 크게 나타날 수 있다 — 이벤트루프 스레드 몇 개가 호출 N 개의 인코딩·응답
처리를 나눠 맡는 구조이기 때문이다. 반대로 대가가 c 와 무관한 상수라면, 채택 판단은 c=1 의
숫자(+라우팅 이원화 논거)만으로 내려도 된다. **지금은 그 둘 중 무엇인지 모른다.**

**이 라운드가 답하려는 질문 하나**: *동시 호출 수 c 를 올릴 때, 두 팔의 (지연 델타·처리량·Spring
CPU) 는 어떻게 갈라지나 — 델타가 c 와 무관한 상수인가, c 에 따라 커지는가.*

> 🔴 이 라운드도 **채택을 결정하지 않는다.** 수치를 만들고, 결정은 [§11-4](./grpc-webclient-empirical-comparison.md#11-4-남은-선택지)
> 로 돌아가 사용자가 한다. 다만 §11-4 가 「ㄴ → 결정」이므로 **이 라운드가 마지막 측정**이다.

## 2. 무엇이 동시 호출에서 다르게 굽나 — 구조 목록 (가설, 실행 전 확인)

두 팔이 c=1 에서 같아 보여도 동시 호출에서 갈라질 수 있는 자리를 코드·라이브러리 기본값에서
전부 적는다. **숫자는 문서·코드 기본값이고, 라운드 시작 게이트에서 실측으로 확인한다**(§5-4) —
확인 전엔 근거로 안 쓴다.

### 2-1. 두 팔이 다른 자리

| 자리 | A. grpc (`GrpcAiAnalysisClient`) | B. webclient (`WebClientAiAnalysisClient`) | 동시성에서 왜 갈리나 |
|---|---|---|---|
| 블로킹 호출의 대기 방식 | 블로킹 스텁 = `ThreadlessExecutor` — **호출 스레드가 스스로 콜백을 실행**한다 | `.block()` = 래치 대기 — 응답 처리는 **이벤트루프 스레드**가 하고 호출 스레드를 깨운다 | B 는 호출 1건당 스레드 2개(호출자+루프)가 관여하고, 루프 스레드가 병목이면 c 개가 거기서 줄 선다 |
| 요청 직렬화가 도는 스레드 | 호출 스레드(`sendMessage` 에서 프레이밍) | 🟡 **가설**: Jackson 인코딩이 구독 시점 = 이벤트루프에서 돈다 | Reattach 는 전선 위 **114KB** — 그 인코딩이 루프 스레드 몇 개에 몰리면 c 와 함께 커진다 |
| I/O 스레드 수 | grpc-netty ELG 기본 = `cores×2` (🟡 확인 필요) | Reactor Netty 기본 = `max(cores, 4)` | 컨테이너 `cpus: 4` 라 JVM 이 보는 cores = **4** → A 8 · B 4 (게이트에서 확인) |
| 커넥션 | 채널당 HTTP/2 커넥션 1개, 스트림 다중화 | HTTP/1.1 풀 — `maxConnections = max(cores, 8)×2` = **16**, 대기열 32, 획득 타임아웃 45s | B 는 c > 16 에서 **풀 대기**가 생긴다. 호출 타임아웃(5s)이 획득 타임아웃(45s)보다 짧으므로 대기가 5s 를 넘기면 `TransientFailure` 로 잡힌다 |
| 서버 쪽 스레드(**혼입 요인**) | gRPC 서버 `ThreadPoolExecutor(max_workers=GRPC_MAX_WORKERS=10)` /프로세스 | FastAPI 동기 엔드포인트 → anyio 스레드풀 기본 **40** /프로세스 | 같은 프로세스·같은 GIL 인데 **상한이 4배 다르다.** c > 10 에서 A 만 서버 스레드 대기가 생기면 그건 클라이언트가 아니라 서버 설정 차이다 → §5-3 에서 같게 맞춘다 |

### 2-2. 두 팔에 똑같이 걸리는 병목 (측정 구간 밖이지만 c 의 상한을 정한다)

| 병목 | 값 | 어디서 | 이 라운드에 미치는 것 |
|---|---|---|---|
| Tomcat 요청 스레드 | 기본 200 | Spring | c ≤ 32 라 안 닿는다 |
| HikariCP | `maximum-pool-size: 15` (`application.yml:55`) | Spring, 재부착의 **AI 호출 전** 트랜잭션 | c > 15 에서 DB 커넥션 대기가 **타이머 밖에서** 생긴다 — 델타는 안 더럽히지만 AI 에 실제로 닿는 동시 수는 15 근처에서 눌린다 |
| AI 프로세스 = GIL | 워커 3 (풀 3) | ai-server | 서버 천장. 포화되면 두 팔의 지연이 모두 **큐잉 지배**가 돼 지연 판정력이 준다 → 그때는 §3 의 CPU/사이클 지표로 읽는다 |
| 아웃박스 발행기 | `batch-size: 20` · `poll-interval: 1000ms` · 단일 스레드 순차 | Spring | **Stop 은 이 축에서 잴 게 없다** — 어떤 c 에서든 발행기는 1건씩 순서대로 보내고, 초당 최대 20건으로 페이싱된다. 프로토콜 델타 1.8ms × 20 = 36ms/틱, 틱 1s 의 3.6%. §3-3 |
| **AI 검출기 풀 = 동시 활성 세션 상한** | 워커당 `int((한도/워커 − 708) / 106.74)` — 컨테이너 메모리에서 유도(`mediapipe_detector.py`, 상수는 EC2 실측 적합) | ai-server | client-ab 역할의 기본 `AI_MEM_LIMIT=2048m` 이면 **워커당 1개**. 넘치면 start·reattach 가 「풀 소진」으로 거절되는데 그 거절은 `success=false` 라 **타이머엔 성공으로 찍힌다**. 활성 세션 ≥ c 여야 하므로 라운드 동안 한도를 올린다(§5-3 ④). 로컬 스모크가 c=4 에서 이걸 밟았다(§9-1 5번) |
| 세션 status 전환 | `PATCH /end` 는 endTime 만 적고 status 는 **AI 콜백**이 바꾼다 | Spring | 같은 계정으로 바로 다시 start 하면 409. 드라이버가 계정을 칸마다 교대한다(§5-1) |
| JWT access 수명 | `JWT_EXPIRATION_TIME` 기본 1800s | Spring | 라운드 2시간 > 30분 — 32분째 칸부터 드라이버가 401 로 죽는다(§9-1 6번). 라운드 동안 phase 타임아웃과 같게(§5-3 ⑤) |

## 3. 무엇을 재나 — (팔, c) 한 칸마다 다섯 가지

| # | 지표 | 어디서 | 왜 |
|---|---|---|---|
| 1 | **Reattach 왕복 분포** (p50·p99, 버킷 차분) | `shadowfit.ai.call{rpc="reattach"}` — 2차와 같은 계기 | 주 판정 지표. 사용자가 실제로 기다리는 자리(요청 스레드) |
| 2 | Start 콜백 지연 분포 | `shadowfit.ai.call{rpc="start"}` | fire-and-forget 이라 사용자 응답엔 안 들어가지만, **콜백이 이벤트루프에서 오는** 자리라 B 의 루프 포화가 여기 먼저 보일 수 있다. 보조 |
| 3 | **처리량** — 재부착/초 | k6 `reattach_ok` ÷ 칸 벽시계 | 닫힌 루프라 c/지연의 함수지만, 두 팔이 같은 c 에서 다르면 그게 곧 대가 |
| 4 | **Spring CPU-초 / 재부착** | 백엔드 컨테이너 cgroup `cpu.stat usage_usec` 를 칸 시작·끝에서 차분 ÷ 재부착 건수 | 서버가 포화돼 지연·처리량이 둘 다 서버 지배가 돼도 **이 지표는 살아남는다** — 클라이언트 구조의 대가가 CPU 로 나타나는지 직접 본다. 같은 박스에 AI 가 사는 배포 형상에서 이 CPU 는 AI 코어 예산에서 빼는 것이다 |
| 5 | AI·nginx 컨테이너 CPU-초 / 사이클 | 같은 방법 | **혼입 확인용** — 서버가 포화했는지(AI 가 워커 3개 = 3코어 근처인지), 두 팔에서 서버 몫이 같은지 |

거기에 **실패 계수**를 칸마다 따로 적는다: `shadowfit.ai.call{outcome≠success}` 건수 ·
`resilience4j_circuitbreaker_state` 칸 시작/끝 · k6 `http_req_failed`. 2차의 블록 4 처럼 표본이
100 → 10 으로 줄어든 칸은 **평균에 섞지 않고 표시**한다.

### 3-1. 왜 지연만으론 부족한가

닫힌 루프에서 c 를 올리면 AI 프로세스(GIL)가 먼저 포화한다. 포화 뒤의 지연은 두 팔 다 **서버
큐잉**이 지배하고, 클라이언트 쪽 1~3ms 는 그 안에 묻힌다. 그래서 지표 4(CPU/사이클)를 같이 둔다
— 서버가 병목이어도 Spring 이 사이클당 CPU 를 얼마나 더 쓰는지는 그대로 보인다.

### 3-2. 잴 수 없는 것 — 이벤트루프·풀 내부

Reactor Netty 커넥션 풀의 대기 수·이벤트루프 지체는 `WebClient.builder().metrics(true)` 계기가
꺼져 있어 안 나온다. 켜는 것은 코드 변경이라 **이 라운드 범위 밖**으로 두고, 그 자리는
간접 신호(지표 2 의 start 콜백 지연, c=32 에서의 `TransientFailure` 건수)로 읽는다. 켤지는 §7 ⑥.

### 3-3. Stop 은 부산물로만

§2-2 대로 Stop 은 아웃박스가 c 와 무관하게 직렬화한다. 계기는 붙어 있어 값은 나오지만
**이 라운드의 판정에 안 쓴다.** 2·3차의 Stop 값(c=1)이 이미 그 RPC 의 답이다.

## 4. 팔과 c 수준

### 4-1. 팔 2개 — 배포 형상 그대로 (풀 3)

| 팔 | 전송 | 경로 | 워커 배분 |
|---|---|---|---|
| **A. grpc** | grpc-java 블로킹/비동기 스텁 | Spring → `shadowfit-ai:8585~8587` 직결 | `session_id % 3` → 채널 i |
| **B. webclient** | Spring WebClient | Spring → `ai-nginx:8000` → 워커 | `session_id % 3` → `X-AI-Worker: i` |

`AI_CHANNEL_POOL_SIZE=3` = 배포 기본값. 두 팔 다 같은 키로 같은 워커에 가므로 **병렬도는 같다.**

**3차의 팔 C(webclient-direct)는 안 세운다.** 직결은 base-url 포트가 하나라 풀 1(워커 0 만)이
전제인데, 그러면 AI 프로세스 하나가 c=4 부터 포화해 §3-1 의 문제가 앞당겨진다. 홉 비용은 3차가
이미 0.01~0.88ms 로 잰 값이고, 이 라운드의 질문(클라이언트 구조 × 동시성)에 홉은 변수가 아니다.
→ §7 ①.

### 4-2. c 수준 5개 — 전부 §2 의 구조 문턱이다

| c | 왜 이 값인가 | 기대되는 것 |
|--:|---|---|
| **1** | 2차(풀 3, c=1)와 연결하는 닻. 같은 조건이면 Reattach grpc 5.8~7.6 · webclient 8.6~9.1ms 근처여야 한다 | 재현 확인 |
| **4** | = 컨테이너 cores = **Reactor Netty 이벤트루프 수** (B 의 루프가 전부 바쁜 첫 지점) | B 의 델타가 여기부터 벌어지면 루프 포화 |
| **8** | = cores×2 = grpc-netty ELG 기본(🟡 확인) · gRPC 서버 스레드 10 바로 아래 | A 의 I/O 스레드가 전부 바쁜 지점 |
| **16** | = **B 의 HTTP/1.1 풀 상한** (`max(cores,8)×2`) · HikariCP 15 바로 위 | 풀이 꽉 찬 경계. DB 대기가 타이머 밖에서 시작 |
| **32** | 풀 상한의 2배 — B 는 **풀 대기열**(32)에 들어간다 | 풀 대기가 지연·실패(5s 타임아웃)로 보이는가 |

c=32 를 넘기지 않는다 — 그 위는 B 의 대기열(32)도 넘어 **거절**이 나오는 자리라 지연 비교가
아니라 실패 비교가 되고, HikariCP 15 에 눌려 AI 에 닿는 동시 수도 더 안 는다.

> 🔴 §2 의 기본값이 게이트(§5-4)에서 다르게 나오면 **c 수준을 그 실측값으로 바꾼다.** 값이
> 아니라 「문턱을 끼운다」가 설계다.

## 5. 절차

### 5-1. 드라이버 — k6 `per-vu-iterations`

2·3차의 bash 순차 루프는 c=1 전용이다. c 를 주려면 드라이버가 동시 호출을 만들어야 한다:

- **k6**, executor `per-vu-iterations`: `vus = c`, `iterations = N` (VU 당). **VU 하나 = 세션 하나**:
  첫 반복에서 세션을 열고(start), 매 반복 그 세션에 **재부착**을 보내고, 마지막 반복에서 종료(end).
  → 동시에 떠 있는 재부착 호출 ≈ **c**.
- 🔴 **왜 «사이클(시작→재부착→종료) 반복» 이 아닌가 (2026-09-11 변경, §9-1 7번).** 사이클 안에서
  AI 호출은 ~8ms 이고 사이클은 수백 ms 다. VU c 개가 사이클을 돌리면 동시에 떠 있는 재부착 호출은
  c × (8ms / 사이클) ≈ **c 의 3%** 뿐이라 §4-2 의 문턱(루프 4 · 풀 16 · 대기열 32)에 닿지 않는다.
  AI 쪽은 «이미 분석 중 — 상태 보존» 경로인데, **2·3차도 정확히 이 경로였다**(start 는
  fire-and-forget 이라 reattach 가 닿을 때 AI 에 이미 세션이 있다 — 스모크 로그로 확인) → 비교 가능.
- 표본은 칸당 재부착 **N × c** — c=1 이면 2차와 같은 100, c=32 면 3,200. start·stop 은 칸당 c 건.
  처리량은 `reattach_ok` ÷ 벽시계.
- VU i 는 계정 (i−1) + (칸 번호 mod 2)·c_max 를 쓴다 — 이웃 칸에서 같은 계정으로 다시 start 하면
  앞 칸 세션의 status 가 아직 IN_PROGRESS(콜백 전)라 409 다(§2-2). 묶음 2개 교대면 한 칸 걸러
  재사용이라 그 사이에 배수 + 콜백이 끝난다. 그래도 409 면 `start_409` 로 세고 그 칸을 뺀다(규칙 3).
  계정 = 2 × 32 = 64개.
- 계정 준비·팔 전환·배수·스크레이프는 `measure_ai_call_latency_ab.sh` 의 것을 그대로 쓴다
  (게이트 둘·`--force-recreate`·stop 배수 — 2차 로컬 스모크가 잡은 결함 넷이 거기 박혀 있다).
- 드라이버는 **같은 박스**에 산다(2차와 같은 이유 — 측정 구간이 Spring→AI 로 박스 안에 닫힌다).
  ⚠️ c=32 에서 k6 의 CPU 는 c=1 때보다 크다. 두 팔에 똑같이 걸리고 지표 4 는 컨테이너 cgroup
  이라 k6 몫이 안 섞인다. 별도 부하기는 §7 ④.

### 5-2. 블록·순서 — 재기동은 팔 전환에만

팔 전환 = 백엔드 재기동(~1.5분)이라 **c 전환에는 재기동을 안 쓴다**: 블록 = (팔 하나, c 5수준
전부). c 는 스타트업 프로퍼티가 아니라 드라이버 인자다.

```
버림:  A(c 5수준 × WARMUP)  B(같음)                      ← 기록 안 함
블록1: A [1 4 8 16 32]   B [4 8 16 32 1]
블록2: B [8 16 32 1 4]   A [16 32 1 4 8]
블록3: A [32 1 4 8 16]   B [1 4 8 16 32]
블록4: B [4 8 16 32 1]   A [8 16 32 1 4]
블록5: A [16 32 1 4 8]   B [32 1 4 8 16]
```

- 팔 순서는 블록마다 반전(A→B / B→A) — 2팔이라 이걸로 충분하다(용어집 §3).
- **c 순서는 칸마다 한 칸씩 회전**시킨다 — 「큰 c 뒤에 작은 c」(잔열·GC·버퍼) 효과가 특정 c 에만
  붙지 않게. 팔과 c 순서가 같은 축에 겹치면 분리가 안 된다([[feedback_measure_design_needs_repeats]]).
- 팔 전환 직후 워밍업(c=1 × WARMUP 재부착) → 배수 → 본판.
- **칸 경계마다 배수**(stop 누적이 멎을 때까지) — 안 그러면 앞 칸의 stop 이 다음 칸의 AI 부하에
  섞인다(≤20/s 라 작지만, c=1 칸에선 상대적으로 크다). 팔 경계 배수는 귀속 때문에 **필수**다.
- 칸마다 회수: `/actuator/prometheus` 스크레이프(전/후) · 컨테이너 4개 `cpu.stat`(전/후) ·
  k6 summary JSON.

**예상 소요**: 재기동 12회 × 1.5분 + 칸 50개 × (본판 ~1분 + 배수 ≥10초) ≈ **1.5시간 안팎**.
stop 은 칸당 c 건뿐이라 배수는 짧다. 인스턴스 1대(`c7i.2xlarge`, 8 vCPU — 백엔드 `cpus: 4` ·
AI `cpus: 4` 는 compose 기본, AI 메모리는 §5-3 ④). 계정 64개 준비 ≈ 1.5분.

### 5-3. 공정성 장치 — 이게 없으면 다른 걸 재게 된다

1. **서버 스레드 상한을 같게** — `GRPC_MAX_WORKERS=40` 으로 anyio 기본(40)과 맞춘다. 안 맞추면
   c > 10 에서 A 만 서버 대기가 생겨 「클라이언트」가 아니라 「서버 설정」을 잰다. compose 가 이
   변수를 안 넘기므로 **측정용 오버레이**(`compose.ai-ab.yml` 과 같은 방식)로 실어보낸다. 본
   compose 는 안 고친다 — 10 vs 40 이 배포 형상의 사실이고, 그 비대칭 자체는 별도 기록으로 남긴다.
2. **전 팔 풀 3** — `AI_CHANNEL_POOL_SIZE=3`. 게이트가 확인한다.
3. **아웃박스 배치를 라운드 동안만 200** — `OUTBOX_PUBLISHER_BATCH_SIZE=200`(relaxed binding).
   배수 시간을 10배 줄인다. Stop 은 판정에 안 쓰고(§3-3), 발행기가 1건씩 순차인 것은 그대로라
   Stop 의 호출당 지연 자체는 안 바뀐다. → §7 ③.
4. **AI 메모리 한도를 라운드 동안만 6000m** — 검출기 풀이 곧 동시 세션 상한이고(§2-2) 한도에서
   유도되므로, c=32 를 워커 3 이 나눠 받으려면 워커당 ≥11 이 필요하다. 여유 1 을 둬 12:
   `3 × (708 + 12 × 106.74) = 5,967 MiB → 6000m`. 공식은 저장소 것 그대로다. 게이트가 유도 풀을
   계산해 `풀 합 ≥ c_max` 를 확인한다. ⚠️ 절대 지연에 메모리 한도 자체는 안 들어간다 — 풀
   크기만 바뀐다. c7i.2xlarge 16GiB: mysql 3 + backend 2 + AI 6.
5. **JWT access 수명을 라운드 동안만 14400s** — 기본 30분인데 라운드가 2시간이라 드라이버가
   중간에 401 로 죽는다(§9-1 6번). 값은 phase 타임아웃(4h)과 같게. 측정 구간(Spring→AI) 밖이다.
6. **팔 전환 게이트** — `printenv` 로 `AI_CLIENT_TYPE`·`AI_CHANNEL_POOL_SIZE` + 위 ①③④⑤ 를 확인.
7. **같은 코드** — 커밋 SHA 고정, main rebase 안 함(2차 §8 의 조건과 같다). 값을 다른 라운드와
   비교할 때 이 차이를 조건으로 센다.

### 5-4. 구조 확인 게이트 — §2 의 기본값을 라운드 시작 때 실측한다

버림 블록이 끝난 직후 **한 번**, 백엔드 컨테이너에서:

| 확인 | 방법 | 기대(§2) |
|---|---|---|
| Reactor Netty 이벤트루프 수 | `jcmd 1 Thread.print \| grep -c reactor-http-nio` | 4 |
| grpc-netty ELG 수 | `... \| grep -c grpc-default-worker-ELG` | 8 (🟡) |
| JVM 이 보는 cores | `/actuator/metrics/system.cpu.count` | 4 |
| AI 서버 gRPC 스레드 상한 | ai 컨테이너 `printenv GRPC_MAX_WORKERS` | 40 (오버레이 뒤) |
| 아웃박스 배치 | 백엔드 `printenv OUTBOX_PUBLISHER_BATCH_SIZE` | 200 |

기대와 다르면 **c 수준을 실측 문턱으로 바꾸고 로그에 남긴다**(§4-2). 문턱을 모른 채 돌린 라운드는
「c=16 에서 꺾였다」를 해석할 수 없다.

## 6. 판정 규칙 (실행 전 고정)

같은 규칙 두 겹 — [`load-test-strategy.md` §2-1](./load-test-strategy.md) 의 **겹침 판정**만 쓰고
배수·판정선은 안 쓴다([[feedback_no_arbitrary_threshold_values]]).

1. **칸 안(같은 c)**: 두 팔의 Reattach p50 이 블록 5개에서 **범위가 안 겹칠 때만** 「그 c 에서
   차이가 있다」. 델타 = webclient − grpc, 블록별로 5개.
2. **c 사이(기울기)**: 어떤 c 의 델타 범위(블록 5개)가 **c=1 의 델타 범위와 안 겹치면**
   「델타가 c 에 따라 변한다」. 겹치면 「이 무대에서 c 와 무관」. 같은 규칙을 지표 3(처리량)·
   4(CPU/사이클)에 각각 적용한다.
3. **실패가 있는 칸**은 규칙 1·2 에 안 넣고 따로 적는다 — 표본이 준 칸을 평균에 섞으면 2차
   블록 4 가 재현된다.

결론은 승패가 아니라 **모양**이므로 다음 세 문장 중 하나로만 닫는다:

- 델타·CPU/사이클 둘 다 c=1 범위와 겹침 → **클라이언트 쪽 대가는 c 와 무관한 상수다.** 채택
  판단은 c=1 의 숫자와 라우팅 논거로 내려도 된다.
- 어느 c 부터 안 겹침 → **클라이언트 구조에 동시성 대가가 있고, 꺾이는 자리는 c=X 다.** 그 X 를
  §2 의 어느 문턱과 겹치는지 적는다(루프 수 4 / ELG 8 / 풀 16 / 대기열 32). 문턱과 안 맞으면
  「자리는 잡았지만 기제는 못 붙였다」로 적는다.
- 서버 포화로 지연·처리량이 판별 불가인데 CPU/사이클만 갈림 → **지연으론 못 가르지만 CPU
  대가는 있다.** 그대로 적는다.

**이 라운드가 답할 수 없는 것**(미리 적는다): 잔여의 내부 분해(브리지 ↔ 직렬화, §11-4 ㄷ) ·
배포 구성의 절대값(동거 박스) · 개방 루프(도착률 고정)에서의 거동 — 닫힌 루프는 c 가 곧 부하라
「초당 λ 건에서 얼마」는 못 말한다 · 채택.

## 8. 안 재는 것

- **잔여의 내부 분해**(ㄷ). 클라이언트 안 계기가 필요하고, 채택 판단을 안 바꾼다(§11-4).
- **Stop 의 동시성** — 아웃박스가 직렬화한다(§2-2). 「발행기 처리량」은 배치·틱 설정의 함수지
  프로토콜의 함수가 아니다.
- **개방 루프.** 「초당 λ 건」은 닫힌 루프로 못 만든다. 서버 포화 아래에서의 지연이 꼭 필요하면
  후속 라운드에서 `constant-arrival-rate` 로 λ 를 이 라운드가 잰 천장의 분수로 준다 — 그 분수는
  이 라운드가 있어야 근거가 생긴다.
- **콜백 3개(AI→Spring)** — REST 미러가 없다.
- **채택.**
