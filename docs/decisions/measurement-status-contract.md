# 측정 상태 계약 — 0회 세션의 «왜 0 인가»

작성일: 2026-11-21
상태: ✅ **결정·구현됨** (사용자 단독 결정 — AI 서버 담당과의 합의를 기다리지 않기로 함, 2026-11-21)
연관: 안건 문서 «AI 서버 합의 안건 — 0점 세션 계약·정확도 검증» 안건 A · [`counted-reps-vs-scored-attempts.md`](./counted-reps-vs-scored-attempts.md)

## 문제

`total_reps = 0` 이라는 값만으로는 «사람이 화면에 없었다» 와 «사람은 있었는데 동작이 반복으로 인정되지 않았다» 가 같아 보인다.
그러면 앱이 «전신이 보이게 다시 찍어 보세요» 와 «동작을 끝까지 해 보세요» 를 가를 수 없다.

## 결정

1. **완료 통보에 측정 상태를 싣는다** — `SessionCompleteRequest.measurement_status`(8번, enum `MeasurementStatus`).
2. **판정은 임계값 없이 AI 가 이미 세는 카운터로만 한다**(`SessionState.measurement_status`, 순서가 의미):

   | 조건 | 상태 |
   |---|---|
   | 인정 반복 또는 미인정 시도가 하나라도 있다 | `OK` |
   | 수락된 프레임이 하나도 없다 | `NO_POSE` — 사람을 못 찾았거나 프레임이 오지 않았다 |
   | 수락됐지만 판정에 쓸 프레임이 하나도 없다 | `NOT_FULLY_VISIBLE` — 하체 등이 화면 밖 |
   | 판정된 프레임은 있으나 반복·시도가 0 | `NO_REP` |

   «사람이 잡힌 프레임이 N% 미만» 같은 기준값은 **쓰지 않았다** — 근거 없는 숫자가 되기 때문이다.
3. **기본값 0 = `OK`(측정됨)** — 이 필드를 모르는 구버전 AI 의 메시지는 0 으로 읽혀 «측정됨» 이 된다. AI·Spring 어느 쪽이 먼저 배포돼도 안 깨지고, 구버전을 «측정 불가» 로 오분류하지 않는다.
4. **Spring 은 자기 기록과 맞을 때만 사유를 저장한다** — AI 는 0 이라는데 `total_reps` 가 양수이거나 `pose_data`·미인정 시도에 기록이 있으면(재부착·구버전 AI 등) 사유를 남기지 않는다. 저장은 `exercise_sessions.measurement_status`(V37, `VARCHAR(30) NULL`, `NULL` = 측정됨·구세션)이고 완료 전이 때 한 번만 기록한다(멱등 재전송이 덮어쓰지 않는다).
5. **응답에 실린다** — 일일·주간 목록(`ExerciseSessionDto.measurementStatus`)과 세션 리포트(`SessionReportResponseDto.measurementStatus`). 사유가 없으면 `null`. 앱은 사유별 안내 문구를 보인다(`utils/unmeasuredMessage.ts`) — 모르는 값은 일반 안내로 떨어진다.

## 이 결정이 하지 않는 것

- **연속 기록(streak)·출석 정책은 이 문서 범위 밖이다**(사용자 결정은 «측정된 것이 없는 세션은 제외», 별도 PR).
- `NO_POSE` 는 «사람을 못 찾음» 과 «프레임이 오지 않음»(앱이 프레임을 안 보냄) 을 구분하지 않는다 — 수락된 프레임 0 이라는 같은 관측이다.
- 실기기에서 실제로 각 사유가 어떻게 나오는지는 **확인하지 못했다**(카운터 → 상태 번역은 단위 시험으로, 앱 문구는 순수 함수 시험으로만).
- 사유 값이 늘면(예: 조명 부족) proto enum·Java enum·앱 문구를 함께 늘린다. 모르는 값은 모든 층에서 «일반 안내» 로 안전하게 떨어진다.
