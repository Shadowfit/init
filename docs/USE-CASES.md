## 3. 핵심 유스케이스 상세

흐름 옆 `→ W-nn` 은 §4 의 판단 근거 번호다.

### B-01. 운동 세션 시작 ~ 종료

- **액터**: 회원, AI 서버
- **사전조건**: 로그인·온보딩 완료, 대상 운동이 `analysis_supported=TRUE` 이고 `ExerciseReference`(기준 좌표) 존재. 현재 스쿼트만
- **기본 흐름**
  1. 회원이 운동 화면에서 시작 → `POST /exercises/sessions`(선택: `targetRepsPerSet`·`targetSets`, B-07).
  2. Spring 이 `Session(IN_PROGRESS)` 을 만들고 `sessionId`·`sessionNonce`·`aiWorkerIndex`·`startTime` 을 **202 로 바로 돌려준다**. gRPC `StartAnalysis` 는 커밋 뒤 `@Async` 로 보낸다. → W-01
  3. 앱이 카메라 프레임을 `ai-nginx` 경유 **AI 서버 `POST /api/v1/pose` 로 직접** 보낸다. `X-AI-Worker` 헤더로 같은 워커에 고정되고, nonce 가 없거나 틀린 프레임은 «세션 없음» 과 같은 응답으로 버려진다. AI 가 rep 을 감지하면 싱크로율·자세 오류를 응답에 싣는다(B-04). → W-02·W-03·W-04
  4. rep 이 완성될 때마다 AI → Spring gRPC `SavePoseDataBatch` → `pose_data` 저장, `lastActiveAt` 갱신. → W-05
  5. 회원이 종료 → `PATCH /sessions/{id}/end`. 결과값 없이 종료 신호만 보내고, 다시 불러도 같다(멱등). → W-06
  6. Spring 이 `endTime` 을 찍는 **같은 트랜잭션**에 아웃박스 `STOP_ANALYSIS` 행을 넣는다. 발행기가 gRPC `StopAnalysis` 송신. → W-07
  7. AI 가 `CompleteAnalysis` 로 rep 수를 돌려준다. Spring 은 싱크 통계(평균·최고·최저)와 세트 요약을 **`pose_data` 에서 직접 집계**해 `Session(COMPLETED)` 으로 갱신하고, 세션 리포트를 같은 트랜잭션에서 미리 계산해 둔다(C-01). 회원이 ACTIVE 모임에 하나라도 있으면 아웃박스 `SESSION_COMPLETED` 적재(→ E-07). → W-08·W-14·W-28
- **대안/예외 흐름**
  - 2a. 시작 시점에 그 워커 서킷이 OPEN → `StartAnalysis` 를 보내지 않고 세션을 바로 `FAILED`(`circuit-open`). gRPC 오류면 `FAILED` + `STOP_ANALYSIS` 적재.
  - 2b. 진행 중에 워커가 죽어 서킷이 OPEN 으로 **전이** → 그 워커의 진행 중 세션에 `REATTACH_ANALYSIS` 적재(S-04). → W-09
  - 3a. 앱 백그라운드·네트워크 단절로 종료 요청이 안 옴 → B-03 타임아웃.
  - 3b. AI 컨테이너 재시작으로 `SessionState` 소실 → B-02 재부착. → W-12
  - 6a. `StopAnalysis` 송신 실패 → 발행기 재시도. 같은 Stop 이 두 번 가도 AI 가 66초 동안 종료한 id 를 기억해 «이미 처리함» 으로 답한다. → W-13
  - 7a. 타임아웃 스케줄러가 먼저 `FAILED` 로 바꾼 뒤 콜백 도착 → `complete()` 가 `FAILED` 를 `COMPLETED` 로 덮는다. 둘이 동시면 `@Version` 충돌에서 스케줄러가 양보하고 콜백이 최대 3회 재시도한다. 어느 쪽이든 **AI 결과가 이긴다**. → W-10
  - 7b. `CompleteAnalysis` 콜백 자체는 아웃박스가 아니다. AI 쪽이 3회(최대 약 19초) 시도한 뒤 로그만 남기고 포기한다. 이때 세션은 타임아웃이 `FAILED` 로 정리한다(§6 알려진 결함).
- **사후조건**: `Session.status ∈ {COMPLETED, FAILED}`, `pose_data` 에 rep 기록. COMPLETED 면 그날 출석 1일(C-06·E-05·E-09 의 입력). → W-15

### B-03. 세션 타임아웃 정리

- **액터**: 스케줄러 · **트리거**: 1분 주기
- **흐름**: `IN_PROGRESS` 세션 중 기준을 넘긴 것을 `FAILED` 로 바꾸고, `endTime` 이 비어 있으면 `STOP_ANALYSIS` 도 적재한다. 기준은 rep 이 하나라도 있으면 `lastActiveAt + 10분`, 없으면(자세 잡는 중) `startTime + 예상시간 + 30분`. AI 콜백과 겹치면 양보한다. → W-11
- **사후조건**: 영구 `IN_PROGRESS` 가 남지 않는다. `FAILED` 는 출석으로 안 세지만 종착 상태는 아니다. 늦게 온 `CompleteAnalysis` 가 `COMPLETED` 로 덮는다.

### E-06 → F-01/F-02. 재촉·응원

- **액터**: 회원(보내는 쪽·받는 쪽), 아웃박스 발행기, Expo Push
- **사전조건**: 두 회원이 같은 모임에 둘 다 ACTIVE. «받는 쪽이 오늘 안 했다» 는 서버가 검사하지 않는다. 재촉 버튼을 안 한 사람에게만 띄우는 것은 프론트 규칙이다. → W-16
- **기본 흐름**
  1. 친구 현황(E-05)에서 재촉 `POST /friends/{id}/nudge` 또는 응원 `POST /friends/{id}/cheer {message}`.
  2. Spring 이 `notifications` 행을 만들고, 받는 쪽에 푸시 토큰이 있으면 같은 트랜잭션에 아웃박스 `PUSH_NOTIFICATION` 적재. → W-18
  3. 커밋 뒤 받는 쪽이 모임 WebSocket 에 붙어 있으면 `NotificationRelay` 가 `NOTIFICATION` 프레임을 민다. 푸시는 접속 여부와 상관없이 발행기가 따로 보낸다. → W-19
  4. 받는 쪽이 알림함(F-01)에서 확인 → `PATCH /notifications/{id}/read`.
- **대안/예외 흐름**
  - 1a. 같은 상대·같은 날·같은 종류 두 번째 → 409(재촉 N002, 응원 N004). 재촉 한 번과 응원 한 번은 같은 날 둘 다 된다. → W-17
  - 1b. 같은 모임 아님(탈퇴 포함) 403 · 없는 회원 404 · 자기 자신 400.
  - 3a. Expo 티켓이 `DeviceNotRegistered` → 그 토큰을 지운다. 다른 기기에 갔으면 SENT, 전부 죽었으면 TERMINAL. 나머지 오류는 재시도(전송 실패·5xx·429)와 종결(자격 증명·크기 초과 등)로 갈린다. → W-20
  - 3b. 푸시 토큰이 없음(A-06 화면 미구현) → 아웃박스 행을 만들지 않는다. 알림함에만 남고, 그래도 기능은 성립한다.

### E-07. 모임 피드 — 완료 자동 글

- **액터**: 아웃박스 발행기 · **트리거**: B-01 의 7(세션 COMPLETED, 모임 소속 회원)
- **흐름**: 발행기가 `SESSION_COMPLETED` 를 집어 회원이 속한 ACTIVE 모임마다 `group_events` 에 완료 이벤트 1건씩 팬아웃한다. 한 트랜잭션에서 `group_id` 오름차순으로 잠근다. 서버는 문장이 아니라 `{sessionId, memberId, username, exerciseName}` payload 를 저장하고, «OO님이 스쿼트 완료» 문구는 프론트가 만든다. 재발행돼도 `(group_id, event_type, source_id)` UNIQUE 로 중복이 없다. 모임원은 `GET /groups/{id}/feed` 에서 보고 리액션한다(E-08). → W-21·W-22·W-23

## 4. 판단 근거 — 왜 3단

형식: **왜** → **그건 왜** → **그건 왜**, 그리고 버린 대안과 대가. 근거는 코드 파일·클래스, 결정 문서 §, 커밋·이슈 번호다. 근거가 없는 단은 «근거 없음» 으로 적고 멈췄다.

### 4-1. 운동 세션

**W-01. 세션 시작은 AI 응답을 기다리지 않는다** (B-01 ②)
- 왜: 클라는 응답을 받으면 프레임을 보내기 시작하면 된다. AI 의 준비 완료가 응답의 조건이 아니다. (`ExerciseAnalysisService` startAnalysis 주석)
  - 그건 왜: 재부착(W-12)은 반대로 동기다. 성공/실패가 클라의 분기 조건이라서다. 시작에는 그런 분기가 없다. (`architecture/ai-backend-integration.md`)
    - 그건 왜: 비동기 송신은 커밋 뒤로 미룬다. 커밋 전에 비동기 작업이 먼저 돌면 실패 처리가 아직 없는 행을 건드려 아무 일도 안 하는 레이스가 있었다(07-24 리뷰 지적). nonce·세트 목표도 같은 트랜잭션에서 확정해, 클라가 받은 값과 AI 가 받은 값이 갈리지 않게 한다(#787).
- 버린 대안: 시작도 아웃박스로 보내기. 송신이 늦어져도 클라가 프레임을 먼저 보내면 되므로 보장 전달의 이득이 작다고 봤다(`decisions/outbox-reliable-messaging.md` §4-2-1). 동기 대기는 근거 없음.
- 대가: AI 가 멈춰 있어도 API 는 202 다. AI 가 검출기 풀이 모자라 `success=false` 를 돌려줘도 Spring 이 그 값을 읽지 않는다(§6).

**W-02. 카메라 프레임은 Spring 을 거치지 않고 앱에서 AI 로 직접 간다** (분기 H2)
- 왜: 05-24 결정의 사유는 넷이다. PPT 아키텍처(사용자 의도), 한 홉 절감, 프레임당 약 40KB base64 가 백엔드 메모리·GC 를 안 거친다는 점, 보안 후퇴는 AI 인증 미들웨어로 막는다는 점. (`decisions/ai-backend-coupling.md` §11)
  - 그건 왜: 실시간 판정(DTW·싱크·rep 감지)이 전부 AI 에서 끝나고, Spring 이 필요한 건 rep 단위 사후 데이터뿐이다. (`decisions/pose-ingest-downsampling.md` §1)
    - 그건 왜: 근거 없음. 한 홉의 지연과 백엔드 부하는 추정치이고, Spring 이 프레임 경로에 설 때의 비용은 잰 적이 없다(`decisions/redesign-from-scratch-2026-09-11.md` §A1 이 스스로 적었다).
- 버린 대안: H1 백엔드 프록시(처음 추천이었다가 번복), H3 백엔드 자체 MediaPipe, H4 WebSocket/gRPC 스트리밍.
- 대가: 공개 표면이 둘이 됐고, 그 뒤의 여러 장치가 전부 이 결정에서 나왔다. 앱 번들 토큰(#134), 세션 nonce(W-04), `X-AI-Worker`·`ai-nginx`(W-03), CORS·문서 노출 설정이 두 서비스에 복제, `/pose` 입력 크기가 DoS 면이 됨. (redesign 문서 §A1 표)

**W-03. `X-AI-Worker` 헤더로 세션을 한 워커에 고정한다**
- 왜: `SessionState` 와 MediaPipe 검출기가 프로세스 메모리에 있다. `SO_REUSEPORT` 로 흩어 보내자 세션 6개 중 4개가 `NO_LEASE` 로 거절됐다. (`decisions/ai-multiprocess-frame-routing.md` §1)
  - 그건 왜: AI 를 멀티프로세스로 띄운 이유가 GIL 이다. 한 프로세스가 약 1 vCPU 에서 막히고, 워커 3개가 최적이었다(2026-08-24 EC2 실측, `decisions/per-process-ceiling-cause.md`).
    - 그건 왜: 상태를 Redis 로 뺄 수 없다. 검출기는 직렬화가 안 되고, rep 안의 프레임 버퍼는 프레임마다 바뀌어 외부화하면 프레임마다 왕복과 분산 락이 붙는다. 상태를 못 옮기면 세션을 못 옮기고, 남는 답이 스티키 라우팅이다. (`decisions/ai-sticky-routing.md` §4)
- 버린 대안: nginx 가 session_id 로 해시(Spring 이 이미 워커 인덱스를 계산하므로 로직 이원화, `nginx-ai/default.conf` 주석), 전송을 gRPC/WS 로 바꾸기(차이 +0.86% 로 잡음 안, ai-sticky-routing §10-3), Redis 외부화.
- 대가: 헤더 책임이 클라에 있다. 헤더가 빠지면 0번 워커로 간다.

**W-04. nonce 가 없거나 틀린 프레임은 «세션 없음» 과 같은 응답으로 버린다**
- 왜: AI 호출 토큰은 앱 번들에 들어가는 사실상 공개값이고, session_id 는 AUTO_INCREMENT 라 추측된다. 토큰만 있으면 남의 세션에 프레임을 넣을 수 있고 그 데이터가 Spring DB 까지 간다. 08-12 에 실제로 재현했다. (`decisions/ai-session-ownership-verification.md` §1)
  - 그건 왜: Spring 쪽 대조로는 못 막는다. 콜백에 실려 오는 건 진짜 세션 번호뿐이라 대조할 주장된 신원이 없다. 신원은 프레임이 들어오는 입구에서 잡아야 한다. (같은 문서 §2)
    - 그건 왜: 단기 토큰 대신 nonce 를 골랐다. AI 에는 JWT 를 검증할 수단이 없고, nonce 는 수명이 세션과 같아 «만료 몇 분» 이라는 근거 없는 숫자를 정하지 않아도 된다(§3·§4). 거절을 다른 모양으로 답하면 살아 있는 세션을 열거할 수 있어 «세션 없음» 과 같게 했다(#605).
- 버린 대안: 세션 단위 단기 토큰, 콜백 대조만 하기(심층 방어로만 가치), 위험 감수.
- 대가: proto 가 바뀌어 양쪽을 같이 배포해야 했다. 평문 구간에서는 도청에 무력하다(#148). nonce 가 NULL 인 옛 세션은 통과한다.

**W-05. 관절 데이터는 프레임마다가 아니라 rep 이 끝날 때마다 Spring 으로 보낸다**
- 왜: 분기 F 에서 rep 단위 push(F1)를 골랐다. INSERT 가 고르게 흩어지고, 콜백이 실패해도 그 rep 만 잃는다. (`decisions/ai-backend-coupling.md` §5-α)
  - 그건 왜: 종료 때 한 번에 가져오는 F2 는 AI 컨테이너가 죽으면 전부 잃는다. rep 단위라서 AI 가 죽어도 앞 rep 이 남고, 재부착이 `MAX(rep_number)` 로 rep 수를 복원한다. (`decisions/session-resume-and-ai-state.md` §3-2)
    - 그건 왜: 싱크로율은 rep 이 끝나야 정해지는 값이다. 그래서 Spring 이 받는 가장 촘촘한 활동 신호도 rep 이고, 타임아웃(W-11)도 이걸로 판단한다. 프레임 단위 전송을 명시적으로 기각한 기록은 없다.
- 버린 대안: F2 종료 시 pull, F3 push + pull 안전망(유실이 실제로 관찰될 때 재검토), F4 저장 안 함.
- 대가: 저장은 여전히 프레임당 1행(rep 당 약 5~30행). 재전송 멱등이 파티션 PK 와 부딪치는 문제가 따로 생겼다(`decisions/pose-batch-idempotency-vs-partition.md`).

**W-06. 종료 API 는 결과값 없이 종료 신호만 받고, 멱등이다**
- 왜: 예전 `PUT /exercises/sessions/{id}/complete` 는 인증 없이 아무 세션이나 원하는 값으로 완료시킬 수 있었다(`23c8953b`, 07-11 보안 수정).
  - 그건 왜: 운동 통계의 원천을 하나로 둔다. 프론트가 계산한 값과 서버 값이 부딪치는 권위 충돌을 없앴다. (`architecture/ai-backend-changelog.md` 143a2e4)
    - 그건 왜: 종료 트리거는 «클라는 Spring 하나만 부르고 Spring 이 AI 에 전한다»(ET-H)로 정했다. 클라가 Spring·AI 를 둘 다 부르는 ET-A 는 AI 에 엔드포인트가 새로 필요하고 부분 실패를 클라가 떠안으며, 안전망(스케줄러)은 이미 Spring 에 있었다. (`decisions/session-end-trigger.md` §4·§5)
- 대가: 멱등 가드 때문에 타임아웃이 먼저 `endTime` 을 찍으면 사용자가 종료해도 AI 에 통보가 안 가던 결함이 있었다(#98, 수정됨).

**W-07. 종료 통보(`STOP_ANALYSIS`)는 `endTime` 과 같은 트랜잭션의 아웃박스로 보낸다**
- 왜: 예전에는 커밋 뒤 gRPC 를 쏘는 dual-write 였다. 커밋 뒤 gRPC 가 실패하면 되살릴 방법이 없었다. (`decisions/outbox-reliable-messaging.md` §1)
  - 그건 왜: 유실 경로가 둘이었다. 오류 콜백이 로그만 남겼고, 서킷이 OPEN 이면 송신을 아예 버렸다. 하필 AI 가 죽어 통보가 가장 많이 쌓이는 구간이다. (§1-2)
    - 그건 왜: `StopAnalysis` 가 `CompleteAnalysis` 의 유일한 방아쇠이고 AI 에는 TTL 이 없다. 통보 하나를 잃으면 결과 영구 유실, `FAILED` 오분류, AI 메모리 잔류가 한꺼번에 온다. (§1-1)
- 버린 대안: 동기 재시도(프로세스가 죽으면 증발), 상태 기반 리컨실리에이션(2순위), 메시지 브로커(브로커에 쓰는 것 자체가 다시 dual-write), 2PC.
- 대가: 폴링 간격(1초)만큼 늦는다. AI 재시작으로 상태가 사라지는 건 못 고친다(그건 W-12). 요청 스레드에서 외부 호출이 빠지면서 `SessionService` ↔ `ExerciseAnalysisService` 순환 의존도 끊겼다(`993dfa10`).

**W-08. 싱크 통계는 AI 가 보낸 값이 아니라 Spring 이 `pose_data` 에서 집계한다**
- 왜: 재부착하면 AI 의 rep 목록이 비어 후반 구간만 평균에 들어갔다. 최고·최저는 저장되지 않았고, rep 이 없으면 0.0 이 들어갔다(#75).
  - 그건 왜: 데이터를 다 가진 쪽이 계산해야 한다. 재부착을 거친 세션 전체의 rep 은 AI 메모리가 아니라 `pose_data` 에만 온전히 있다. (`SessionCompletionTx.resolveSyncStats` 주석)
    - 그건 왜: rep 수는 여전히 AI 값을 쓴다. rep 을 세는 상태기계가 AI 에만 있고 Spring 은 프레임을 받지 않는다. rep_number 가 없는 구버전 AI 가 보낸 통계는 Spring 이 더 잘 계산할 수 없어서 그대로 쓴다.
- 대가: 칼로리는 AI 가 0.0 을 보내고 있어 의미가 없다.

**W-09. 워커별 서킷이 OPEN 으로 전이하면 그 워커의 세션을 자동 재부착한다** (S-04)
- 왜: 워커 하나가 죽으면 거기 붙은 세션이 갇혔다. 서킷의 OPEN 전이 자체를 장애 감지 신호로 쓴다(#581).
  - 그건 왜: «살아 있는 다른 워커로 옮기기» 는 실측으로 틀렸다. 워커 하나를 죽이면 `entrypoint.sh` 의 `wait -n` 때문에 컨테이너 전체가 재기동되고, 다운타임은 7회 평균 25.3초였다. 옮길 곳이 없다. (`decisions/ai-channel-pool-hardening.md` §2-4)
    - 그건 왜: 새 메커니즘이 필요 없었다. 재부착 요청이 Spring DB 값만으로 AI 상태를 다시 만들도록 이미 설계돼 있었다. 서킷을 워커별로 나눈 이유도 있다. 워커 1개가 멈춰도 전체 실패율은 33% 라 50% 기준 서킷이 영영 안 열린다(`decisions/circuit-breaker-worker-aggregation.md`).
- 버린 대안: 현상 유지(사용자가 앱을 다시 열어야 복구), 프론트 재연결 확장.
- 대가: 진행 중이던 rep 의 프레임은 복구되지 않는다. 서킷은 gRPC 호출만 세고(프레임은 HTTP), 최소 호출 수가 5라 트래픽이 적으면 워커가 죽어도 OPEN 이 안 될 수 있다(미검증).

**W-10. 타임아웃과 AI 완료 콜백이 겹치면 AI 결과가 이긴다**
- 왜: 사용자가 실제로 운동한 데이터(rep·싱크로율)는 어떤 경우에도 잃으면 안 된다. (`SessionService`, `SessionTimeoutScheduler` 주석)
  - 그건 왜: 스케줄러의 `FAILED` 는 정의상 «분석 결과를 못 받은 세션» 이다. 결과가 도착하면 그 전제가 사라진다. 그래서 `FAILED` → `COMPLETED` 덮어쓰기는 의도된 동작이다(#98).
    - 그건 왜: 비관락이 아니라 낙관락(`@Version`)이다. 서로 다른 세션이 대부분이라 경합이 낮고(DAU 1,000 가정), 상시 블로킹이 아깝다. `FOR UPDATE` 로 바꾼 반사실 실험에서는 2.8초 뒤 락 대기 타임아웃(ERROR 1205)이 났다. (`portfolio/realmysql-experiments.md`)
- 대가: 콜백 재시도 3회를 다 쓰면 예외로 끝나고 지표만 남는다.

**W-11. 타임아웃은 «시작 후 경과 시간» 이 아니라 «마지막 rep 이후 10분» 으로 판단한다**
- 왜: 시작 기준 식(시작 + 예상 15분 + 버퍼 30분 = 45분)에 결함이 셋 있었다. 이탈한 세션을 45분 방치하고, 45분 넘게 운동 중인 세션은 걷어가고, 10분 운동이 통계에 46분으로 잡혔다. (`decisions/session-liveness-vs-elapsed-time.md` §3)
  - 그건 왜: 살아 있는지는 경과 시간이 아니라 활동으로 판단해야 한다. rep 저장(W-05)이 곧 활동 신호다.
    - 그건 왜: 10분의 하한 근거는 세트 사이 휴식이 90초까지 관측된 것이다(#91). 그동안은 rep 이 없으니 그보다 넉넉해야 한다. **상한 근거는 재보지 않았다**(같은 문서 §7). rep 이 하나도 없는 세션에만 옛 식(30분 버퍼)을 남긴 이유는 자세를 잡는 준비 구간에 짧은 기준을 걸면 시작하자마자 걷어가기 때문이다. 30분과 스케줄러 1분 주기 자체는 근거 없음(`docs/15-session-timeout-guide.md` 의 일반론뿐).
- 버린 대안: 통계에서 `FAILED` 제외, `pose_data` 로 종료 시각 역산, 현행 유지.

**W-12. 재부착은 시작과 다른 RPC(`ReattachAnalysis`)다**
- 왜: 시작은 새 상태를 만들고 기존 상태를 덮는다. 재부착은 살아 있는 상태를 절대 덮으면 안 된다. 한 핸들러에 섞으면 둘 중 하나가 조용히 틀린다. (`exercise_servicer.py` 주석)
  - 그건 왜: 덮어쓰면 중복 호출이나 빠른 이탈/복귀만으로 진행 중인 rep 과 스무딩 이력이 날아간다. 재부착이 필요 없는 상황에서 피해를 주게 된다. 초판은 이걸 장점으로 적었다가 리뷰로 정정했다. (`decisions/session-resume-and-ai-state.md` §4-B)
    - 그건 왜: 실패 정책도 반대다. 시작은 실패하면 바로 `FAILED` 지만, 재부착 실패로 세션을 `FAILED` 로 만들면 재부착이 지키려던 세션을 재부착이 없애게 된다. (§6-1)
- 대가: rep 상태·프레임 번호·스무딩 이력은 복원되지 않는다. 응답의 `analyzerStateReset` 으로 알린다.

**W-13. AI 는 종료한 세션 id 를 66초 동안 기억해 같은 `StopAnalysis` 를 멱등하게 받는다**
- 왜: 아웃박스는 at-least-once 라 같은 Stop 이 두 번 올 수 있다. 첫 호출이 상태를 지우므로 두 번째는 원래 무조건 `success=false` 였다(#152).
  - 그건 왜: 응답만으로 «이미 처리함» 과 «세션을 정말 잃음» 을 못 가르면, 정상 세션이 `FAILED` 로 뒤집히거나 거짓 실패 지표가 오른다(#191).
    - 그건 왜: 66초 = lease 60초 + 폴링 1초 + 데드라인 5초. Spring 이 회수한 행을 다시 보낼 수 있는 가장 이른 시점에서 유도했다. (`session_state.py` 주석)
- 대가: 멱등은 66초 창 안에서만 성립한다. 창 밖 재송신은 Spring 쪽 보수 분기에 기댄다.

**W-14. 세트 경계는 «세트당 목표 rep 도달» 하나뿐이고, 세트 요약은 Spring 이 `pose_data` 에서 역산한다** (B-07)
- 왜: 세트 경계가 목표 도달 하나라서 저장본만으로 `ceil(rep_number / T)` 로 결정적으로 재현된다. (`decisions/lunge-and-set-backend.md` §7 3-D-ⅱ)
  - 그건 왜: W-08 과 같은 원칙이다. AI 가 보낸 값 대신 저장본을 쓰면 proto 에 `SetResult` 가 필요 없고, 이 작업이 AI 구현을 기다리지 않는다.
    - 그건 왜: `pose_data` 에 `set_index` 를 더하지 않는다. 파티션 표 ALTER 를 피하고, 파티션은 보존 기간이 지나면 DROP 되므로(W-39) 세트 요약은 별도 표(`exercise_session_sets`)에 남긴다.
- 버린 대안: AI 가 세트 결과를 채워 보내기(09-22 ③ 착수 때 변경), 백엔드가 휴식 간격으로 세트를 자르기(휴식 임계값에 근거가 없음, §3-D).
- 대가: 운동 도중 세트 목표를 바꿀 수 없다. 역산이 흔들리기 때문이다.

### 4-2. 소셜·알림

**W-15. 출석은 «그날 COMPLETED 세션 1건 이상» 이고, 스트릭·친구 현황·모임 캘린더가 같은 정의를 쓴다**
- 왜: «오늘 했나», «N일째», «월 출석» 은 같은 원천에서 나오는 같은 계산이다. 따로 만들면 정의가 세 군데로 갈린다. 계산은 `AttendanceService` 하나에 모았다. (`decisions/social-cheer-and-group-feed.md` §2)
  - 그건 왜: 원래 스트릭만 상태를 안 봤다(취소·실패 포함). 의미상 이유가 아니라 인덱스 사정 때문이었다. 주간 요약·목표·패턴·리포트는 이미 COMPLETED 만 센다. 새 정의가 아니라 나머지와 맞춘 것이다. (§1, §3-B)
    - 그건 왜: 인덱스 `(member_id, status, start_time)` 은 status 등치 조건이 없으면 seek 하지 못하고 회원 이력 전체를 읽는다. COMPLETED 등치를 넣으면 여러 회원 IN 과 날짜 범위도 커버링으로 seek 한다(#541 실측).
- 버린 대안: `daily_logs` 로 통일(처음 추천했다가 철회. 세션을 지워도 daily_logs 가 안 되돌아가고 1분 미만 세션이 0분으로 남는다, #718), 상태 무관 유지, 사전집계(daily_logs 가 이미 그 역할).
- 대가: 파생값이 없어 드리프트·백필 관리가 필요 없다. 대신 읽는 행이 상수배 많고, 취소 세션만 있던 날이 빠져 기존 사용자의 스트릭 숫자가 바뀐다는 걸 알고 정했다.

**W-16. 친구는 «같은 모임에 둘 다 ACTIVE» 로 정의하고, 아니면 403**
- 왜: 권한 규칙이 이 조인 하나다. URL 이 `/friends/{id}/nudge` 인 것도 URL 이 하는 말과 권한 규칙을 같게 하려는 것이다. (`FriendController` 주석, 09-12 사용자 confirm)
  - 그건 왜: 친구 관계를 따로 두지 않았다. 모임을 떠나면 친구도 사라진다.
    - 그건 왜: 참고한 레퍼런스 화면 6장에 친구 신청·수락 화면이 없다. 가입 경로가 «모임 만들기 / 코드로 참여» 둘뿐이다. (§3-A, 결정 로그 (3))
- 버린 대안: `friendships` 상태머신(대칭 저장·차단·탈퇴 정리), 지표별 공개 설정.
- 대가: 1:1 친구는 2인 모임으로만 표현된다. «모임 가입 = 내 운동 여부 공개에 동의» 라는 고지가 필요하다. 탈퇴한 뒤 살아 있는 소켓으로 발행하던 권한 우회를 막으려고 발행할 때마다 ACTIVE 를 다시 확인한다(`8962acd0`).

**W-17. 같은 사람에게 같은 종류는 하루 한 번, DB UNIQUE 로 막고 409**
- 왜: `UNIQUE(sender_id, recipient_id, type, target_date)`. 앱에서 먼저 존재를 확인해 409 로 막고, 그 틈으로 들어온 더블탭은 제약이 막는다. (`V17__add_notifications.sql`, `NotificationService`)
  - 그건 왜: «하루» 는 임의값이 아니다. 재촉의 근거인 «오늘 했나» 가 하루 단위로 바뀐다. `target_date` 도 출석과 같은 서버 날짜다. (§3-C)
    - 그건 왜: UNIQUE 위반을 같은 트랜잭션 안에서 잡으면 Hibernate 세션이 망가진다(`DailyLogRepository` 에서 겪었다). 그래서 INSERT 만 별도 빈(`NotificationWriter`)의 트랜잭션에 두고, 트랜잭션 밖에서 409 로 바꾼다.
- 버린 대안: 제한 없음, N회 제한(«규칙 자체는 근거가 있어야 정한다»), 리액션처럼 멱등 200(리액션은 토글이라 200, 재촉은 규칙 위반이라 409 로 구분, §4-5).
- 대가: 재촉과 응원은 종류가 달라 같은 날 둘 다 보낼 수 있다(`f8fc8514`). 응원을 따로 만든 이유는 코드 주석(«완료한 친구에게 보내는 게 정상 경로라 재촉과 반대») 외에 결정 문서가 없다.

**W-18. 알림은 피드와 따로 `notifications` 표에 두고, 푸시 통보는 같은 트랜잭션의 아웃박스로 적재한다**
- 왜: 모임 채널(`group_events`)에 실으면 1:1 재촉이 모임 전원에게 보인다. (§3-C ①)
  - 그건 왜: 재촉에는 모임도 순번도 없다. 하루 1회 UNIQUE 에 필요한 sender·recipient·target_date 열도 `group_events` 에 없다.
    - 그건 왜: 알림이 커밋되면 통보 행도 반드시 있고, 알림이 롤백되면(UNIQUE 위반) 통보도 없어야 한다. 이게 아웃박스의 정의라 따로 고민할 분기가 아니었다(§4-3 ②). 이 프로젝트는 dual-write 로 통보를 잃은 적이 있다(W-07).
- 버린 대안: 토큰마다 아웃박스 행(적재 시점과 송신 시점의 토큰 불일치), 기기가 없을 때 SENT/FAILED/새 상태로 기록(거짓이거나 지표 소음) → 기기가 없으면 행을 안 만든다.
- 대가: 알림 1건 = 행 1개라 일부 기기만 재시도할 때 나머지 기기에 두 번 갈 수 있다. at-least-once 로 문서화했고, 두 번 울리는 게 안 울리는 것보다 낫다는 제품 판단이다(§4-3 ⑨).

**W-19. 알림함 저장이 원천이고, 소켓과 푸시는 둘 다 «추가» 전달이다**
- 왜: 저장이 원천이고 소켓·푸시는 수단이다. 소켓 전달이 실패해도 삼킨다. (`NotificationRelay` 주석)
  - 그건 왜: 알림용 새 소켓(`/ws/me`)을 열지 않고 기존 모임 소켓을 재사용해 `memberId → 세션` 으로만 민다(`c4083f81`).
    - 그건 왜: 재촉 대상은 정의상 «오늘 안 한 사람» 이라 앱을 안 켠 경우가 대부분이다. 어느 안이든 실제로 닿는 건 푸시이고, 연결 하나에 스레드 하나인 구조에서 회원당 연결을 하나 더 열 근거가 없다(결정 로그 (13)).
- 버린 대안: 새 연결 `/ws/me`, 소켓만(기능이 거의 안 보임).
- 대가: «접속 중» 은 모임 화면을 보고 있을 때뿐이다. 프론트에 WS 클라이언트가 아직 없어 지금 소켓 전달은 실제로 타지 않는다. 푸시 없이는 앱을 연 사람에게만 닿는다.

**W-20. Expo 오류는 문서 분류를 그대로 따른다 — 죽은 토큰은 지우고, 재시도할 가치가 있는 것만 재시도**
- 왜: `DeviceNotRegistered` 는 토큰이 죽었다는 뜻이라 재시도가 무의미하다. (§4-3 ③, `PushDispatchService`)
  - 그건 왜: 이 응답이 죽은 토큰을 정확히 알려주므로 «N일 미갱신 토큰 삭제» 같은 만료 규칙을 두지 않았다. 근거 없는 임계값이 된다. (§4-2 ③)
    - 그건 왜: 자격 증명 오류를 재시도로 두면 10회 돈 뒤 어차피 `FAILED` 다. 결과는 같고 로그만 10배라 즉시 종결로 분류했다.
- 대가: 기기가 전부 등록 해제됐으면 Expo 가 받았어도 `TERMINAL_FAILED` 다(«아무 데도 안 감»). 서킷과 5초 타임아웃은 «배치 20 × 5초 > lease 60초면 자기 행을 회수해 중복 송신» 이라는 제약에서 나왔다.

**W-21. 피드 자동 글은 완료 트랜잭션에서 바로 쓰지 않고 `SESSION_COMPLETED` 아웃박스로 팬아웃한다**
- 왜: 애그리거트 경계. 완료 트랜잭션이 모임 규칙(행 잠금·순번 채번·멤버십)을 알아야 하고, 모임 N행의 락을 리포트 계산이 끝날 때까지 쥐게 된다. (§3-D 정정)
  - 그건 왜: 피드 글은 «완료와 어긋나면 안 되는 불변식» 이 아니라 «있어야 하는 결과» 라서 1초 늦어도 깨지는 게 없다. 아웃박스가 이미 두 번째 용처(푸시)를 열어 세 번째는 타입 하나만 추가하면 됐다(`5a02259e`).
    - 그건 왜: 한 트랜잭션이 모임을 둘 이상 잠그는 경로가 이게 처음이다. 완료 트랜잭션에 넣으면 이미 낙관락 재시도가 있는 곳에 다중 락이 겹친다(§4-4). 완료 트랜잭션에 부수 작업을 섞었다가 모든 세션이 `FAILED` 로 수렴한 사고(#66)와의 연결은 추정이다. 결정 문서가 #66 을 직접 인용하지 않는다.
- 버린 대안: 09-11 원결정 «같은 트랜잭션에서 INSERT, 아웃박스 불필요»(철회).
- 대가: 피드가 1초 늦다. at-least-once 라 중복 방지 키(W-23)와 팬아웃 트랜잭션·데드락 테스트가 새로 필요해졌다. 완료 트랜잭션에 더해진 건 INSERT 1행과 exists 1회뿐이다.

**W-22. 팬아웃은 한 트랜잭션에서, `group_id` 오름차순으로 잠근다**
- 왜: 모임마다 따로 커밋하면 중간에 실패했을 때 앞 모임에만 글이 있는 채로 재시도되어 앞 모임에 중복이 생긴다. (§4-4 ③)
  - 그건 왜: 발행이 모임 행을 `PESSIMISTIC_WRITE` 로 잠그고 순번을 채번한다. 두 팬아웃이 반대 순서로 잠그면 데드락이다.
    - 그건 왜: 가입·소켓 발행·탈퇴·위임 같은 다른 경로는 모임 1개만 잠근다. 여러 개를 잠그는 유일한 경로가 오름차순을 지키면 순환이 생길 수 없다. `SessionCompletedFeedFanoutRaceTest` 가 실 MySQL 에서 확인한다(CI).
- 대가: 모임 N개의 락을 한 트랜잭션이 동시에 쥔다. 회원당 모임 수 분포는 시드가 단일 템플릿이라 재지 못했다.

**W-23. 재발행 중복은 `source_id` UNIQUE 로 막는다**
- 왜: 아웃박스는 lease 를 잃으면 같은 행을 두 번 발행할 수 있다. AI 쪽 수신자는 멱등하게 만들었지만(W-13) `group_events` 는 아니었다. (§4-4)
  - 그건 왜: `UNIQUE(group_id, event_type, source_id)`(V19). 발행 전 exists 로 거르고, 제약은 동시 재발행의 마지막 방어선이다.
    - 그건 왜: «어느 세션의 글인가» 를 스키마가 말하게 한다. NULL 은 여러 개 허용되므로 가입 이벤트 같은 다른 종류는 영향이 없다.
- 버린 대안: 중복 허용(사용자 눈에 보이는 중복 글), `payload LIKE` 검사(payload 필드 순서가 바뀌면 조용히 깨짐).

**W-24. 모임 출석 캘린더는 날짜별 인원수와 활성 인원만 주고, 칸 농도는 프론트가 정한다**
- 왜: 레퍼런스 화면에 칸 농도의 의미가 없다. 비율인지, 전원 출석인지, 나 기준인지 해석이 셋인데 서버 응답은 셋 다 같고 색 매핑만 다르다. (§3-E)
  - 그건 왜: 분모·분자 모두 현재 ACTIVE 멤버다. `group_members` 에 `left_at` 이 없어 그날의 인원은 못 구하고, 그 정확도를 요구하는 화면도 없다. 인원수로만 합치니 개인별 날짜가 드러나지 않는다(§3-G).
    - 그건 왜: 사전집계·캐시를 둘 근거가 없다. 실측에서 seek 는 인원 수, 읽는 행은 인원 × 월 세션(커버링), 1,622행에 4.3 ms 였다. 인원 × 월 세션이 수만 행이 되면 다시 본다.
- 대가: 탈퇴한 멤버의 과거 출석이 캘린더에서 사라진다. 날짜 그룹핑은 filesort(행 수에 선형)다.

**W-25. 참여 코드는 8자리, 탈퇴했던 회원은 새 행 대신 되살린다**
- 왜(8자리): 헷갈리는 글자(0/O·1/I)를 뺀 32자로 32⁸ ≈ 1.1×10¹² 라 충돌을 무시할 수 있고, 입력란이 손으로 치는 것을 전제한다(`f04632b4`).
- 왜(되살리기): 탈퇴가 행을 `LEFT` 로 남기므로 새 행을 넣으면 `UNIQUE(group_id, member_id)` 위반으로 500 이 났다(`8962acd0`).
  - 그건 왜: 초대 수락과 코드 참여가 가입 경로 `admit()` 하나를 공유한다. 모임 행 `FOR UPDATE` 로 더블탭을 줄 세워 두 번째 요청은 409 로 끝난다.
    - 그건 왜: 잡고 재시도하는 방식은 Hibernate 세션이 망가져서 못 쓴다(W-17 과 같은 이유). 뒤에서 잡는 대신 앞에서 줄을 세운다. 탈퇴를 DELETE 가 아니라 `LEFT` 로 남기는 이유 자체는 근거 없음.
- 버린 대안: 만료·횟수 제한 코드(레퍼런스에 만료 UI 가 없어 근거 없는 기능).
- 대가: 코드가 모임당 하나로 고정돼, 유출되면 그룹장의 재발급뿐이다.

**W-26. 다른 멤버가 있는 그룹장은 위임해야 나갈 수 있고, 혼자면 모임이 삭제된다**
- 왜: 그룹장이 나갔다 다시 들어오면 `rejoin()` 이 일반 멤버로 덮어써 그룹장 없는 모임이 생겼다. 그러면 초대 코드를 아무도 재발급할 수 없다(#721).
  - 그건 왜: 혼자 남은 그룹장을 막으면 영영 못 나가고, `LEFT` 로 남기면 코드를 아는 사람이 들어와 그룹장 없는 모임이 다시 생긴다.
    - 그건 왜: 근거 없음. «그룹장 없는 모임은 허용하지 않는다» 는 불변식 자체를 왜 두는지(초대 코드 재발급 외에 그룹장이 꼭 필요한 기능이 있는지)는 적혀 있지 않다. 구현 쪽 사실만 있다. 판정은 모임 행 `FOR UPDATE` 안에서 해 가입·위임과 순서를 맞춘다.
- 버린 대안: 가장 오래된 멤버 자동 승계(규칙 근거 필요), `rejoin()` 에서 역할 보존(그룹장이 둘이 될 수 있음).
- 대가: 위임 API 가 새로 생겼다.

**W-27. 소켓은 핸드셰이크에서 쿼리 파라미터 JWT 로 인증하고, 놓친 이벤트는 모임 내 순번(`seq`)으로 회수한다**
- 왜(인증): 브라우저 WebSocket 핸드셰이크는 Authorization 헤더를 싣지 못한다. `/ws/**` 는 보안 필터를 통과시키고 인터셉터가 JWT 와 ACTIVE 멤버 여부를 맡는다. (`JwtHandshakeInterceptor`)
- 왜(seq): `(group_id, seq)` UNIQUE 가 재연결 백필과 중복 판정의 유일한 기준이다. (`V12` 주석)
  - 그건 왜: 여러 사람이 같이 보는 채널에서 순서·중복을 잘못 설계하면 참여자마다 다른 화면을 본다. 재연결 뒤 상태 복구가 설계 초기부터 위험 항목이었다(`decisions/multiuser-realtime-sync.md` §3).
    - 그건 왜: 타임스탬프나 전역 AUTO_INCREMENT id 대신 모임별 seq 를 고른 이유는 문서에 없다. 확인되는 사실은 둘이다. `created_at` 은 초 단위라 같은 시각이 겹치고, seq 는 모임 행 락 안에서 채번돼 모임 안 커밋 순서와 일치한다. 추정: 같은 시각과 커밋 순서가 뒤집힌 id 때문에 백필이 행을 건너뛰는 걸 피하려는 것.
- 대가: 순번 채번이 DB 행 락이라 단일 인스턴스를 전제한다(여러 대로 가면 Redis INCR 자리, `Group` 주석). 백필은 근거 없는 limit 을 두지 않아 페이지가 없다.

### 4-3. 기록·리포트·목표

**W-28. 세션 리포트는 조회할 때마다 계산하지 않고 COMPLETED 전이 때 한 번 계산해 저장한다**
- 왜: 조회마다 worst 구간을 `pose_data` 에서 다시 계산했고, 완료 콜백이 리포트 행을 안 만들어 실제 세션은 404 였다. (`decisions/report-read-path.md` §2)
  - 그건 왜: 리포트가 느린 원인은 인덱스 밖에 있었다. 큰 JSON 과다 조회, 재계산, 버퍼풀 오염, 무제한 프레임. 미리 계산 하나가 여섯 중 넷을 푼다. (§3·§6)
    - 그건 왜: 요약이 영속 표에 남아야 원본(`pose_data`)을 짧게 보관하고 지울 수 있다(W-39). 주간 LLM 집계도 이 저장본을 입력으로 쓴다.
- 대가: 리포트 계산이 완료 트랜잭션 안에 들어왔다. 컬럼 하나가 빠진 것만으로 모든 세션이 `FAILED` 로 수렴한 사고가 실제로 있었다(#66). 좌표는 저장하지 않아 파티션이 지워지면 worst 프레임 좌표가 null 이 된다.

**W-29. 주간 AI 총평은 끝난 주만, 첫 조회 때 만든다. 응답은 기다리지 않고 템플릿으로 먼저 준다**
- 왜: 진행 중인 주에 LLM 문장을 붙이면 세션이 끝날 때마다 낡는다. 끝난 주에 한 번 만들고 바꾸지 않는다. (`decisions/report-generation-llm.md` §14-2)
  - 그건 왜: 합격 조건이 «LLM 은 필수 경로에 없다, 사용자는 '리포트 없음' 을 겪지 않는다» 다. 조회 시 멱등 발행이 그 모양이다. (§9)
    - 그건 왜: 트랜잭션 안의 부수 작업이 세션까지 실패시킨 #66 이 있었다. 템플릿 문장은 1단계에서 이미 폴백용으로 만들어져 있었다. (§1·§13)
- 버린 대안: 이번 주도 세션마다 다시 생성(호출 수 = 세션 수, 무료 한도 소진, 문장이 계속 바뀜), 월요일 새벽 일괄 생성(안 보는 리포트에도 호출, 사용자 테스트 규모 5~10명에서는 «첫 조회부터 LLM» 의 이점이 작음).
- 대가: 첫 조회는 항상 템플릿이다.

**W-30. LLM 호출은 기존 아웃박스와 다른 발행기(5초 차선)에서 돈다**
- 왜: 기존 발행기는 모든 타입을 한 tick 에 차례로 보낸다. LLM 이 끼면 느린 타입이 `STOP_ANALYSIS` 의 lease 를 잡아먹는다. (§5-1, `AbstractOutboxPublisher`)
  - 그건 왜: #66 이 트랜잭션 수준에서 가르친 사고를 tick·스레드 수준에서 되풀이하게 된다. 설정도 섞인다. lease 60초·재시도 10회는 유료 호출에서 중복 호출과 최악 10배 청구가 된다. (§5)
    - 그건 왜: 폴링 쿼리에 타입 조건을 얹으면 07-29 실측으로 맞춘 `idx_outbox_dispatch` 가 무너진다. 그래서 선두 컬럼이 다른 인덱스를 따로 둔다(V21). 5초는 사용자를 막는 이벤트가 아니라서(첫 조회는 이미 템플릿), 배치 3은 «HTTP 몫 = lease 의 절반 = 3 × 10초» 에서 나왔다.
- 버린 대안: 발행기 하나에 타입별 설정(같은 tick 에서 순차라 격리가 안 됨).
- 대가: 클래스와 인덱스가 하나씩 늘었다. 차선 분리 결정(08-27)은 모델 선정 전이었고 근거는 다른 모델의 39초 꼬리였다. 지금 모델(최대 1.66초)이면 같은 차선에도 들어간다.

**W-31. LLM 출력이 검증에 걸리면 재호출하지 않고 템플릿으로 폴백한다. 검증에는 «집계에 없는 숫자» 가 들어간다**
- 왜(폴백): 재호출은 유료·한도 호출의 비용을 곱한다. 재시도는 «다시 보내면 될 수 있는» 429·503·타임아웃에만 한다. (`WeeklyReportOutputValidator`, `WeeklyReportGenerationService`)
  - 그건 왜: 폴백 비율 자체를 품질 지표로 본다. 그래서 원인별로 `fallback_reason` 을 남긴다.
    - 그건 왜: 근거 없음. 같은 입력으로 다시 부르면 같은 위반이 나올 것이라는 추정(temperature 0.2)은 잰 적이 없다.
- 왜(숫자 검증): 경계 원칙이 «숫자는 전부 SQL, LLM 은 문장만» 이고 그 경계를 코드로 강제한다. (§3)
  - 그건 왜: 평균 같은 정의를 LLM 이 문장으로 만들면 그럴듯하게 틀리고, LLM 출력이라 틀린 걸 알아채기가 더 어렵다. (§4)
    - 그건 왜: 실측 30회에서 숫자 위반은 0 이었다. «지금 모델이 통과한다» 일 뿐 검증이 필요 없다는 뜻은 아니다. 한국어 검증은 초기 라운드에 필드명(`totalReps`)이 문장에 새어 나온 실측에서 나왔다.
- 대가: 검증 실패 1건이면 그 주는 영구히 템플릿이다(행을 바꾸지 않음).

**W-32. 회원·주당 1행, 다시 봐도 LLM 을 다시 부르지 않는다. 프롬프트를 바꾸면 VERSION 을 올린다**
- 왜: `UNIQUE(member_id, period_start)` 가 멱등의 원천이다. 동시에 처음 조회해도 INSERT 는 한 번만 성공한다. (V21)
  - 그건 왜: 주간 통계는 저장하지 않지만 LLM 문장은 같은 입력에도 매번 다르고, 초 단위이며 한도를 쓴다. 한 번 만들어 읽는다.
    - 그건 왜: 같은 입력에서 다른 문장이 나왔을 때 «프롬프트가 바뀌어서» 와 «모델이 흔들려서» 를 가르려고 VERSION 을 남긴다. 모델명도 설정값이다. 쓰던 모델이 404 로 사라진 적이 있다.
- 대가: VERSION 을 올려도 기존 행은 재생성되지 않는다. 버전은 새 행에 붙는 꼬리표다.

**W-33. LLM 은 Gemini flash-lite**
- 왜: 세 회사 중 무료 API 가 있는 곳이 Gemini 뿐이었다. (§7)
  - 그건 왜: 무료 티어는 레이트리밋이 있어 «큐를 왜 넣었나» 에 실제 이유가 생긴다. 가정 물량은 DAU 1,000 기준 하루 약 140건이다.
    - 그건 왜: flash-lite 실측 p95 1.66초, thinking 없음, 검증 3종 10/10. 상위 모델은 최대 39초에 thinking 토큰 7배였고, 다른 하나는 11회 전부 503 이었다. 숫자 십수 개로 세 문장을 쓰는 데 thinking 은 필요 없다. (`loadtest/results/gemini-latency-2026-09-14/`)
- 버린 대안: OpenAI(사실상 3 RPM), Anthropic(무료 없음).
- 대가: 무료 티어는 입력이 검토·학습에 쓰일 수 있다. 보내는 데이터를 집계 숫자로만 줄여 면적을 좁혔다.

**W-34. 목표 진척은 저장하지 않고 조회할 때 최근 N일로 계산한다**
- 왜: 세션 완료 때 재집계해 저장하면 마지막 운동 뒤 7일이 지나도 값이 굳는다(`dabf4b2b`).
  - 그건 왜: 스케줄러 롤오버와 수동 기간 설정을 버리면 스케줄러·컬럼·롤오버 로직이 통째로 사라진다. 상태도 조회 때 비교로 계산하니 배치가 필요 없다. (`decisions/goal-domain-design.md` §4·§5)
    - 그건 왜: 근거 없음. 추정 예산(5시간)과 새 스케줄러 회피 외의 이유는 적혀 있지 않다. goalType 당 1개인 이유도 근거 없음(기간 컬럼이 없어 같은 종류 두 개는 같은 창을 잰다는 추정).
- 대가: 목표가 «이번 주(월~일)» 가 아니라 «최근 7일» 이 됐다. 원 스펙과 뜻이 다르다.

**W-35. 추천은 규칙 기반, 다음 세션 1건**
- 왜: 원안 «3개 운동 루틴» 은 분석할 수 없는 종목을 추천하게 된다. 다음 세션의 강도·볼륨 1건으로 좁혔다. (`decisions/recommendation-algorithm.md` §2·§3)
  - 그건 왜: 분석기와 기준 좌표가 스쿼트 전용이다.
    - 그건 왜: 협업 필터링은 사용자가 거의 없어 인위적이고, LLM 은 결정적이어야 할 강도 추천에 비결정적이며 LLM 자리는 이미 주간 총평이 쓴다. (§5)
- 대가: 임계값 85/60·최근 3세션은 «미검증 잠정치» 로 코드에 들어갔다(§9). 세트 목표의 기본값도 이 공식을 쓴다(W-14).

### 4-4. 관리자·보안·데이터 수명

**W-36. 기준 영상 mp4 는 공유 볼륨에 두고 gRPC 로 경로만 넘기며, 추출은 비동기(202)다**
- 왜(비동기): 전에는 AI 가 추출을 끝내고 응답했다. Spring 데드라인 5초에 데모 영상(308프레임)조차 `DEADLINE_EXCEEDED` 였다. (`exercise_servicer.py` 주석)
  - 그건 왜: 성공한 추출이 서킷 실패로 집계돼, 업로드 5번이면 그 워커의 라이브 세션까지 거부됐다. (`architecture/ai-backend-integration.md` §3-3 ②)
    - 그건 왜: 추출은 수십 초~분 걸리는 작업이라 동기로 매달면 안 된다고 미리 적어 두었다. (`decisions/reference-style-and-caching.md`)
- 왜(경로 전달): 결정 기록은 «공유 볼륨» 이라는 09-17 사용자 confirm 뿐이다(PR #772). 업로드 상한 50MB 와 gRPC 메시지 4MB 한도가 정황이지만, 바이트 전송과 비교한 기록은 없다. 그 이상은 근거 없음.
- 대가: 같은 호스트가 전제다. 호스트를 나누면 오브젝트 스토리지로 바꿔야 한다. proto 밖 계약이라 CI 가 못 지킨다. 추출이 같은 워커에서 GIL 을 나눠 라이브 세션을 느리게 한다.

**W-37. 로그아웃용 토큰 블랙리스트를 없애고 access 수명을 30분으로 줄였다**
- 왜: 재발급(#135)이 들어오자 블랙리스트의 가치가 access 수명의 함수가 됐다. 수명을 줄이면 저장소를 고민할 대상이 사라진다. (`decisions/token-lifecycle.md` §3-0)
  - 그건 왜: 힙 블랙리스트는 재기동하면 부활하고, 여러 인스턴스에서 동기화가 안 되며, 매 요청 맵을 조회했다(#137). 문제를 푸는 대신 없앴다.
    - 그건 왜: DB 블랙리스트는 인증된 모든 요청에 쿼리 1회를 붙이고, Redis 는 새 인프라라 근거 없이 단 것으로 읽힐 위험이 있었다. (§3-2)
- 대가: 로그아웃한 access 가 남은 수명(최대 30분) 동안 유효하다. 로그아웃의 뜻이 «즉시 끊김» 에서 «갱신이 끊기고 곧 만료» 로 바뀌었다. 30분은 측정값이 아니라 약속이다.

**W-38. 트레이너 모니터링은 SSE, 담당 관계를 따로 검증하고, 전송이 실패하면 버린다**
- 왜(별도 검증): `@PreAuthorize` 는 역할(TRAINER)까지만 본다. «이 트레이너가 이 회원 담당인가» 는 역할로 못 잡는다. (`CoachingStreamController`)
  - 그건 왜: 배정 모델이 «회원당 담당 1명, 트레이너는 N명 담당» 이다. 원래 없던 건 역할이 아니라 배정 관계였다. (`decisions/trainer-live-monitoring.md`)
    - 그건 왜: 근거 없음. 기능 정의가 «담당 회원의 세션을 본다» 는 전문가 연계형이라는 것까지만 있고(§1), 왜 트레이너 1명으로 제한했는지(공동 담당을 막은 이유)는 적혀 있지 않다.
- 왜(버림): 저장 커밋 뒤 한 번 더 중계하는 구조다. 트레이너 화면 갱신이 실패해도 저장된 데이터에는 영향이 없어야 해서 큐 없이 버린다. (`TrainerConnectionRegistry`)
  - 그건 왜: 설계 원칙이 «AI·기존 경로는 한 줄도 안 바꾸고 저장과 별개로 한 번 더 중계» 다. 그 이상은 근거 없음.
- 왜(타임아웃 무제한): 유한값이면 프론트 재연결 로직이 새로 필요한데 범위 밖이었다(08-30 사용자 확인). 좀비 연결은 30초 하트비트로 치운다. 30초는 실측이 아니라 관행값이다.
- 버린 대안: gRPC-Web(브라우저 미지원·프록시 필요), WebSocket(단방향에 과함), WebFlux(스택 전환 이득 없음).
- 대가: 연결 목록이 프로세스 메모리라 여러 인스턴스에서 못 찾는다. 느린 소비자 격리는 없다(실험 설계만 있음, `decisions/sse-capacity-deep-dive.md` §1-3).

**W-39. `pose_data` 는 월별 파티션으로 나누고 오래된 달은 DELETE 대신 DROP 한다**
- 왜: DROP PARTITION 이 DELETE 보다 625배 빨랐다(로컬·더미 조건). (`portfolio/realmysql-experiments.md`)
  - 그건 왜: 대량 DELETE 는 830만 행에 18.6분이 걸렸고, 쌓일수록 만료 비용이 누적된다. (`decisions/pose-data-partition-fk-tradeoff.md`)
    - 그건 왜: 짧은 보존(이번 달 + 1개월)과 아카이빙 없음은 두 근거에서 나왔다. 요약이 리포트에 남는다는 것(W-28), 그리고 개인정보보호법 제21조 «지체 없이 파기» 취지. 매일 1회는 월 단위 작업이고 멱등이라서, 04:00 이라는 시각 자체는 근거 없음.
- 대가: FK 를 잃었다(W-40). PK 가 `(id, created_at)` 복합키가 됐고, 월보다 잘게는 지울 수 없다.

**W-40. 고아 `pose_data` 는 지우지 않고 매일 세기만 한다**
- 왜: MySQL 은 FK 와 파티션을 같이 못 쓴다(ERROR 1506). 파티션을 걸려고 `pose_data → exercise_sessions` FK 를 뗐다. (`pose-data-partition-fk-tradeoff.md` §1)
  - 그건 왜: 대신 탈퇴 즉시 비동기로 지운다. 그런데 «세션 존재 확인 → INSERT» 사이에 탈퇴가 커밋되면 정리가 지나간 뒤 INSERT 가 착지해 고아가 남고, DB 도 막지 않는다. (`PoseDataOrphanMonitor`)
    - 그건 왜: 고칠 방법이 셋(비관락·주기 삭제·감수)인데 어느 게 맞는지는 발생 빈도에 달렸고, 그 숫자가 없다. 락은 비용이 확실하고 이득이 불확실하다. 04:30 은 04:00 DROP 뒤에 세야 값이 부풀지 않아서다.
- 버린 대안: 동기 삭제(탈퇴 API 가 분 단위로 느려짐), 정기 배치(«지체 없이» 와 충돌), 파티션 만료에 위임.

**W-41. 아웃박스는 재시도 10회 뒤 `FAILED`**
- 왜: 독 메시지를 따로 리컨실리에이션 잡 없이 «내장 FAILED + 지표» 로 처리한다. (`decisions/outbox-reliable-messaging.md` §3)
  - 그건 왜: 빠른 실패는 서킷브레이커가 맡으므로 발행기는 느긋한 지수 백오프(1초에서 두 배씩, 상한 5분)가 맞다(07-29 사용자 confirm).
    - 그건 왜: 근거 없음. 10이라는 숫자는 기준값도 제약 유도도 없다. 백오프를 더하면 약 13.5분(첫 송신 포함 11회)이고, 컨테이너 재기동(17~35초)은 다섯 번째 시도 안에 덮인다는 것은 사후 계산일 뿐이다. 주간 리포트 차선의 12회는 «누적 약 68분» 이라는 뜻을 설정 주석에 적어 두었다.
