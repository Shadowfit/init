# 관리자 세션 조회 인덱스 — SQL Server에서 같은 실험 (2026-11-23)

원 실험: [`../admin-selectivity-sweep-2026-09-10/README.md`](../admin-selectivity-sweep-2026-09-10/README.md) (MySQL 8.0.46, EC2 m6i.xlarge)
이 문서의 목적: 같은 인덱스·데이터·쿼리를 다른 DBMS에서도 재 봤는지에 **근거 자료**를 남긴다(원 실험은 MySQL만 쟀다).
재현: 이 폴더에서 `bash run.sh` → `python -I summarize.py raw/raw.csv` → `python -I gen_plans.py` (약 20분, SQL Server LocalDB와 `sqlcmd` 필요)

---

## 0. 한 줄

**MySQL에서는 관리자 인덱스 `(status, start_time)`가 "기간 제한 없음 + 흔한 상태"의 목록 조회에서 최대 33배 졌는데,
SQL Server에서는 목록 조회가 어느 조건에서도 지지 않았다**(최저 0.98배 = 동률). 총건수 조회는 두 엔진 모두 크게 이겼다
(SQL Server 19~2,663배, MySQL 1.2~191배). **같은 인덱스, 같은 데이터, 같은 쿼리인데 DBMS(옵티마이저·저장 구조)에 따라
결과가 갈린다.**

**같은 데이터인지 확인했다.** 시딩이 MySQL과 같은 레시피(소금이 다른 MD5)라 상태 분포가 결정적으로 같아야 하고, 실제로 그랬다.

| 상태 | SQL Server | MySQL(원 실험 실측) |
|---|--:|--:|
| COMPLETED | 69.972% | 69.97% |
| IN_PROGRESS | 20.098% | 20.10% |
| CANCELLED | 7.953% | 7.95% |
| FAILED | 1.977% | 1.98% |

**시딩 검증 7개를 통과해야만 측정이 시작된다**(원 rig의 결함 #5·#6 교훈): 행 수, 상태 분포(5σ), 회원당 단일 상태 비율
**17.46%**(종속 시딩이면 ~100%), 상태별·회원 버킷별 start_time 독립, 중복 쌍 **3**, 기간 **365일** — 7개 모두 통과
(`raw/seed_gate.log`).

## 2. 결과 — A1 / B 중앙값 배수 (1보다 크면 관리자 인덱스가 이긴 것)

괄호는 MySQL 원 실험의 같은 칸.

### 2-1. 목록 쿼리 (`TOP 20 … ORDER BY start_time DESC`)

| 기간 \ 상태 | FAILED 2% | CANCELLED 8% | IN_PROGRESS 20% | COMPLETED 70% |
|---|--:|--:|--:|--:|
| 1일 | **22.96x** (8.93x) | **6.73x** (2.33x) | **3.67x** (2.28x) | **1.17x** (1.24x) |
| 7일 | **19.16x** (21.62x) | **6.43x** (14.94x) | **5.76x** (6.32x) | **0.98x** (1.10x) |
| 30일 | **18.43x** (14.33x) | **6.17x** (3.75x) | **4.22x** (🔴0.89x) | **1.25x** (🔴0.91x) |
| 전체 | **19.96x** (🔴0.26x) | **6.93x** (🔴0.10x) | **3.84x** (🔴0.07x) | **1.05x** (🔴**0.03x**) |

SQL Server는 **1 미만이 하나**(7일·COMPLETED 0.98x — 아래 4절 잡음 한계 안의 동률)이고, MySQL에서 가장 크게 졌던
"기간 전체 · COMPLETED"(0.03x, 33배 짐)가 SQL Server에서는 **1.05x**다.

### 2-2. 총건수 쿼리 (`COUNT_BIG(*)`)

| 기간 \ 상태 | FAILED | CANCELLED | IN_PROGRESS | COMPLETED |
|---|--:|--:|--:|--:|
| 1일 | **2,663x** (85.0x) | **1,779x** (40.0x) | **1,329x** (18.3x) | **521x** (6.14x) |
| 7일 | **1,598x** (183.6x) | **564x** (47.6x) | **296x** (18.4x) | **76x** (5.78x) |
| 30일 | **597x** (191.0x) | **153x** (45.7x) | **73x** (17.8x) | **19.4x** (5.49x) |
| 전체 | **1,734x** (31.8x) | **468x** (8.17x) | **82x** (3.25x) | **75x** (1.24x) |

**방향은 같고(총건수는 관리자 인덱스가 거의 항상 이김) 크기가 훨씬 크다.** 이유는 A1의 총건수 계획이 매번 인덱스 전체(5,152쪽)를
훑기 때문이다(아래 3절). 이 배수의 절대 크기는 "SQL Server가 MySQL보다 인덱스를 더 잘 쓴다"가 아니라 **A1(대조군)이 더 나쁘게
도는 것**이 섞여 있어 그대로 비교하면 안 된다.

### 2-3. 절대값 (이 노트북의 값 — **MySQL의 ms와 비교 금지**)

| | 목록 | 총건수 |
|---|--:|--:|
| A0 | 111 ~ 502 ms | 103 ~ 128 ms |
| A1 | 0.15 ~ 3.2 ms | 106 ~ 153 ms |
| B | **0.12 ~ 0.16 ms** | 0.05 ~ 7.3 ms |

"기간 전체 · COMPLETED"(MySQL에서 가장 크게 졌던 칸)의 중앙값: 목록 A0 502 · A1 0.147 · **B 0.140 ms**,
총건수 A0 112 · A1 129 · **B 1.71 ms**.

**B의 목록 비용이 모든 셀에서 0.12~0.16ms로 거의 일정**하다(MySQL README가 B를 "선택도와 무관하게 일정, 대신 고정비가 더 크다"고
쓴 성질). SQL Server에서는 그 고정비가 작다.

## 3. 실행 계획 — 두 엔진이 **같은 모양의 선택**을 한다

(`SET SHOWPLAN_TEXT`, 추정 계획. `raw/plans_summary.md`, 원문 `raw/plans_A1.txt`·`plans_B.txt`)

| 팔 | 목록 쿼리 | 총건수 쿼리 |
|---|---|---|
| A1 | `ix_st_m (start_time, member_id)`를 seek/scan으로 최신순 탐색 + 키 조회(clustered seek)로 상태 확인 | 인덱스 `ix_m_s_st` **전체 스캔**(5,152쪽, 기간과 무관) |
| B | `ix_s_st (status, start_time)` seek + 키 조회 | `ix_s_st` seek만(커버링) |

- 정렬(Sort) 연산자는 목록 계획 어디에도 없다 — 두 팔 모두 인덱스 순서를 그대로 쓴다.
- 논리 읽기(쪽 수) 중앙값: 기간 전체·COMPLETED 목록 A1 **96** vs B **66**; FAILED(2%) 목록 A1 **2,318~2,320**(기간 30일·전체) vs B **66**.
  흔한 상태에서는 A1도 96쪽에서 멈추고, 드문 상태에서는 A1이 수천 쪽을 걷는다 — MySQL README §4의 "A1은 비용이 선택도에
  반비례, B는 일정"과 같은 구도다.
- **MySQL과 다른 점은 B의 고정비다.** MySQL에서는 같은 계획 모양이 B 4.34ms ↔ A1 0.116ms(37배)였고, SQL Server에서는
  B 0.140 ↔ A1 0.147ms(동률)다. **왜 MySQL의 B만 비싼지는 이 실험이 규명하지 않았다**(원 README도 "접근당 비용이 왜 10배
  차이인지 규명 못함"으로 남겼다). 이번 결과는 그 질문에 **"계획 모양 때문이 아니라 엔진의 접근 비용 쪽일 가능성"** 이라는
  단서만 추가한다 — 추정이다.

## 4. 한계 · 인용 조건

| | |
|---|---|
| **무엇의 값인가** | 관리자 **세션 목록(B 화면)** 조회와 총건수. 회원 목록(A 화면)은 안 쟀다 |
| **언제·어디서** | 2026-11-23 · 노트북 · SQL Server 2019 LocalDB(Express). **단발 1회 실행** |
| **인용 금지** | 절대 ms를 "SQL Server에서 N ms". 노트북 + 다른 프로그램 동시 실행 + EC2와 다른 장비. **배수와 방향만** 쓴다 |
| **엔진·스키마 차이** | `status`가 SQL Server는 `VARCHAR(12)`, MySQL은 ENUM(1바이트). PK가 클러스터드인 점은 같다. 인덱스 크기가 다르다 |
| **측정 방식 차이** | SQL Server는 `dm_exec_query_stats.last_elapsed_time`(마이크로초, 계획 캐시된 뒤의 실행만, 결과는 출력 변수로 받아 전송 제외). MySQL은 `EXPLAIN ANALYZE` 루트 노드 actual time. 둘 다 컴파일·파싱을 뺀 서버 내부 시간이라 의도는 같지만 **같은 시계는 아니다** |
| **타이머 함정(고친 것)** | 처음에는 `SYSDATETIME()`을 썼다가 스모크에서 샘플의 213/256이 0으로 나왔다. 윈도우 시스템 틱이 15.6ms라 0.1ms대 쿼리를 못 쟀다. 위 방식으로 바꿔 **본 측정은 통계 누락 0건**(3,360행 전부 값 있음) |
| **잡음** | 0.1~0.2ms대 셀은 사분위 범위/중앙값이 최대 100%를 넘는다(A1 목록 108%, B 목록 104%, B 총건수 142%). **"7일·COMPLETED 0.98x"는 잡음 안의 동률**이지 "졌다"가 아니다. 판정은 "MySQL처럼 1 미만으로 크게 가라앉는 구간이 없다"까지만 |
| **계획** | 추정 계획이라 실행 중 통계 변화는 반영 안 됨. 그래서 시간은 위 2절의 실측, 계획은 모양 설명용으로만 썼다 |
| **분포** | 70/20/8/2는 원 실험과 같은 **가정**이다 |
| **안 잰 것** | 회원 목록(A 화면) · 쓰기 대가 · 메모리를 넘는 규모(디스크 I/O) · SQL Server 정식 에디션/다른 버전 · 정렬키를 바꾼 조합 |
