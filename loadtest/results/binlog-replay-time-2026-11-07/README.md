# binlog 재생 시간 — 백업 이후 쌓인 binlog 를 되살리는 데 얼마 걸리나 (2026-11-08, EC2)

설계 문서: [`../../../docs/decisions/rpo-rto-targets.md`](../../../docs/decisions/rpo-rto-targets.md) §5 구성 2 · §6-2
짝 실험: [`../hostloss-rpo-2026-11-07/`](../hostloss-rpo-2026-11-07/README.md) (호스트 상실 RPO)
무대: **EC2 `m6i.xlarge`**(4 vCPU · 15GB) · gp3 200GB · `ap-northeast-2d` · MySQL **8.0.46** · 버퍼풀 2GB ·
`flush_log_at_trx_commit=1` · `sync_binlog=1`(재생하는 복구 서버도 같음) · 기준 1,000만 행 ·
RUN_ID `replay-ec2-20261107-173709` · 커밋 `7c5e4900` · 19판 전부 검증 일치(COUNT·MAX(id)·CHECKSUM)

## 0. 한 줄

**표준 방법(mysqlbinlog | mysql)은 binlog 1GB 를 되살리는 데 약 2분 15초(135~141초)가 걸리고, 양에 거의 정비례했다.**
병렬 방법(릴레이 로그 + 복제 SQL 스레드 4개)은 적용만 보면 **약 2배 빨랐다**(65~70초/GB). 파일을 릴레이 로그로
옮기는 준비 시간을 넣어도 1.6~1.9배다.

## 1. 결과 (본판 3판씩)

| 단계 | 실제 binlog | 행 수 | DAU 1,000 가정이면 | 표준 M1 | 병렬 M2 (적용) | 병렬 M2 (준비 포함) |
|---|---:|---:|---|---:|---:|---:|
| 512MB | 0.67GB | 31만 | 약 1.1일치 | **93~95초** | 45~46초 | 54~58초 |
| 2048MB | 2.33GB | 108만 | 약 4.0일치 | **318~322초** | 147~156초 | 173~182초 |
| 8192MB | 8.89GB | 413만 | 약 15일치 | **1,187~1,212초** (약 20분) | 620~621초 | 745~751초 |

- **양에 비례한다** — M1 은 GB 당 141 → 137 → 135초로 거의 일정하다. 그래서 «백업 간격 × 하루 binlog 양 × 135~141초/GB»
  로 다른 간격도 환산할 수 있다(이 무대·이 페이로드 조건에서)
- **판 간 흔들림이 작다** — 같은 칸 안 차이가 M1 1.3~2.0%, M2 0.3~5.8%. 단계·방법 차이보다 한참 작다
- 「DAU 1,000 가정이면」 열은 **추정**이다 — 연 1억 행(이 프로젝트의 DAU 1,000 합성 가정) ÷ 365 = 하루 약 27만 행으로
  나눈 값이고, 실제 하루 쓰기량을 잰 게 아니다

### 1-1. 쓰기보다 재생이 느리다

같은 binlog 를 만드는 데 걸린 시간(15개 연결로 동시에 씀)은 0.67GB 41초 · 8.89GB 635초였다(`ec2/levels.tsv`, 누적).
표준 재생은 한 줄로 순서대로 적용하니 **원래 쓰는 데 걸린 시간의 약 2배**가 걸린다. 병렬 재생은 거의 원래 속도를 따라간다.

## 2. 이걸로 RTO(복구 시간)를 어떻게 읽나

구성 2(백업 + binlog 를 서버 밖에)의 복구 시간 ≈ **새 서버 준비 + 백업 붓기 + binlog 재생**.

| 항목 | 값 | 출처·조건 |
|---|---|---|
| 백업 붓기 | 물리(XtraBackup) 약 174초 · 논리 약 21분 | 08-13 백업 라운드 — **1억 행**(합성), m6i.xlarge |
| 백업 붓기 (작은 무대) | 내려받기 2.4~2.6초 + prepare·copy-back 53~57초 | 짝 실험(호스트 상실) — **1,000만 행** |
| binlog 재생 | 위 표 — 1GB 당 약 2분 15초(M1) | 이 실험 |
| 새 서버 준비 | ⬜ 안 쟀다 | — |

예) DAU 1,000 가정에서 **백업을 하루 한 번** 뜨면, 최악(백업 직전 상실)의 재생 몫은 하루치(약 0.6GB) ≈ **약 1분 20초~1분 35초(M1)**
(잰 칸은 1.1일치 93~95초), **일주일에 한 번**이면 약 7일치 ≈ 4.1GB ≈ **약 9~10분(M1, 환산)** 이다. 여기에 백업 붓기(1억 행이면 약 3분)와 새 서버
준비 시간이 더해진다. ⚠️ 일주일치는 **잰 단계(1·4·15일치) 사이를 직선으로 환산한 값**이다.

## 3. 조건 — 인용할 때 떼면 안 되는 것

1. **writer 페이로드는 실제 33 랜드마크 JSON(≈2KB/행)** 이다(사용자 결정, 2026-11-07). `'{}'` 로 재면 같은 GB 에 행이 수십 배라
   재생 시간이 부풀어 나온다 — 08-22 복제 라운드의 writer 와 **페이로드가 다르다**
2. **기준 테이블(1,000만 행)은 `'{}'` 페이로드**다. 재생이 얹히는 테이블의 크기·인덱스 깊이는 1,000만 행 기준이고, 1억 행이면
   다를 수 있다(안 쟀다)
3. **복구 서버도 커밋마다 디스크에 확실히 기록하는 설정**(`flush=1`·`sync_binlog=1`, binlog 켜짐)으로 재생했다. 복구 중에만 이걸
   늦추면 빨라질 수 있다 — §5
4. M2 는 `replica_parallel_workers=4` · `LOGICAL_CLOCK` · `preserve_commit_order=ON`. 소스의 의존성 추적은 `COMMIT_ORDER`
   (8.0 기본)다 — `WRITESET` 이면 병렬 여지가 더 커질 수 있다(안 쟀다)
5. 판마다 같은 기준 datadir 사본에서 복구 서버를 새로 띄웠다 — 사본 붓기 시간은 이 표에 없다(§2 의 «백업 붓기» 가 그 자리)
6. 절대 시간은 하드웨어 종속이다(m6i.xlarge · gp3 기본 125MB/s·3,000 IOPS) — «운영에서 N분» 으로 인용 금지

## 4. 로컬 스모크가 걸러낸 rig 결함

EC2 에서 몇 시간 돌린 뒤에야 만났을 것들 — 커밋 `7c5e4900` 메시지에 전부 적었다. 이 rig 에 해당하는 것만:

- 헬퍼 컨테이너가 root 가 아니라 datadir 를 못 읽음 → `--user 0`
- M2 의 «끝났다» 판정을 릴레이 파일 이름으로 해서 영영 안 끝남 — 적용이 끝난 릴레이 파일은 MySQL 이 지운다 → 원본 binlog 좌표 +
  워커가 다 놀고 있는지로 판정
- `SELECT 1` 대기가 MySQL 초기화용 임시 서버에 붙어 «떴다» 고 착각 → `skip_networking=0` 이 될 때까지 대기
- 윈도의 `python3` 가 스토어 안내만 찍는 가짜라 템플릿 생성 실패 → 실제로 도는 파이썬을 고른다

## 5. 다음에 잴 것

- **복구 서버의 디스크 기록을 늦춘 표준 재생** — 재생하는 동안만 `innodb_flush_log_at_trx_commit=2` · `sync_binlog=0` 으로 띄우는 팔.
  다른 세션(«AWS 실측 체크»)의 로컬 리허설에서 더 빨랐지만 판 간 흔들림이 커 크기는 판정하지 못했다(그 rig 는 폐기). 단서 둘:
  ① 재생 중 서버가 죽으면 처음부터 다시 해야 한다 ② 끝나고 설정을 되돌려 운영으로 넘기는 시간은 이 값에 안 들어간다.
  M1 이 트랜잭션당 약 7.6ms(31만 행 ÷ 25행 ÷ 94초)라 «커밋마다 fsync» 만으로 설명되는지는 이 데이터로 갈리지 않는다
- 기준 1억 행에서 같은 재생 — 조건 2
- 새 서버 준비 시간 — §2 의 빈칸
