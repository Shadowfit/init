## 0. 한 줄

**webclient − grpc 델타(Reattach)는 c=1 의 1.2~3.9ms 에서 c=32 의 9.7~29.0ms 로 커진다**(규칙 2, c≥8 부터 안 겹침).
그러나 **꺾이는 자리는 설계가 걸어둔 클라이언트 문턱(루프 4·풀 16)이 아니라 AI 가 포화하는 자리(c=8, AI CPU ≈ 3코어)** 이고,
같은 c 에서 **AI 컨테이너가 재부착 1건에 쓰는 CPU 가 webclient 팔에서 1~3ms 더 많다**(5수준 전부 안 겹침).
즉 기울기는 «블로킹 브리지» 가 아니라 **REST 미러의 서버 쪽 처리 비용이 포화 구간에서 큐로 증폭된 것**으로 읽힌다 —
그 비용은 형식의 우열이 아니라 **미러가 gRPC 경로를 감싼 겹(JSON→pydantic→proto→같은 서비서)의 대가**다(§4-2).
Spring 컨테이너의 CPU/호출은 이 라운드로 못 가른다(칸이 1~14초라 cgroup 차분이 JIT·백그라운드에 묻힌다).

같은 논리 요청(114,223 B)을 받는 **AI 프로세스가 REST 미러 경로에서 호출당 1~3 cpu-ms 를 더 쓴다.** 기울기(규칙 2)는 c 와
무관 — 즉 이건 **호출당 고정 서버 비용**이고, 서버가 포화한 구간(c≥8)에서 큐 길이만큼 지연 델타로 증폭된다. §2 의 기울기와
§3 의 처리량 차이가 이 하나로 설명된다.

⚠️ 이 값에는 AI→Spring 콜백·stop 처리도 섞여 있지만 두 팔에 같이 걸린다. 무엇이 1~3ms 인지(JSON 파싱 · pydantic 검증 ·
uvicorn 스레드풀 전환)는 **이 라운드가 안 가른다.**

🔴 **이 차이를 「protobuf 가 JSON 보다 빠르다」로 읽으면 안 된다 — 미러의 구조가 «B = A + α» 다.**
`ai-server/app/api/endpoints/internal_analysis.py:87-106` 의 REST 경로는 JSON 파싱 → pydantic 검증(`ReattachCommand`, 프레임 37개)
→ **다시 protobuf 메시지를 조립**(`_to_pose_data_requests`) → **같은 gRPC 서비서**(`_servicer.ReattachAnalysis`)를 부른다.
즉 webclient 팔의 AI 는 grpc 팔이 하는 일을 전부 하고 그 앞에 파싱·검증·조립을 **더** 한다. 형식 A 와 B 의 대결이 아니라
«A 를 감싼 겹의 대가» 라, 미러를 이렇게 만든 이상 이 방향의 차이는 구조적으로 예정돼 있었다. 게다가 114KB 의 대부분은
`joint_coordinates` **문자열 필드 하나**다(`exercise.proto:143`, pydantic 도 `str`) — 이진 인코딩의 이점이 생길 숫자 배열이
애초에 없고, protobuf 는 그 문자열을 복사하고 JSON 은 이스케이프를 풀며 읽는다. 어느 쪽 «인코딩» 이 더 비싼지는
Spring 쪽(§4-1 판별 불가)에서도 AI 쪽에서도 **이 라운드가 재지 않았다.** 배포 형상이 이 미러를 그대로 쓸 것이므로 채택
판단에는 «겹의 대가» 가 그대로 유효하지만, 서사로 옮길 때는 «형식» 이 아니라 «구조» 라고 적어야 한다.

### 4-3. nginx — webclient 팔만, 호출당 **0.50 ~ 0.73 cpu-ms**, c 와 무관

3차가 지연으로 잰 홉 0.01~0.88ms 와 같은 자리. 덤: 액세스 로그에 `a client request body is buffered to a temporary file` 경고가
**31,388건** — 114KB 본문이 `client_body_buffer_size` 기본(16k)을 넘어 **요청마다 디스크 임시파일**을 거친다. 홉이 싼 건
맞지만 이 경로는 디스크를 만진다(→ 이슈). 커넥션 재사용은 331개에 95.9 요청/커넥션(최대 266) — 3차와 같이 매 요청 새 커넥션은 아니다.

## 6. 실패 칸 — b2/grpc/c32 (규칙 3 으로 제외)

32건 `TransientFailure`(VU 32개의 첫 재부착이 전부, 벽시계 5.48초 = 데드라인 5초) → 이후 3,081건이 서킷 거절. 같은 칸에서 **AI 컨테이너의

## 7. 이 결과가 바꾸는 서사

1. **3차의 「잔여 1.4ms = 클라이언트 쪽」은 절반만 맞았다.** 3차의 뺄셈 (C−A) 는 webclient-direct 와 grpc 를 뺐는데, 그 둘은 Spring
   클라이언트만 다른 게 아니라 **AI 쪽 경로(REST 미러 ↔ gRPC 서비서)도 다르다.** 이번에 AI CPU/호출이 c=1 에서 0.1~1.9ms 갈렸으니
   3차의 잔여에는 **서버 쪽 몫이 들어 있다.** 「기제는 클라이언트 구조」라는 3차 결론은 «클라이언트 + 서버 처리 경로» 로 고쳐 읽어야 한다.
2. **설계 §6 의 세 문장 중 어느 것도 그대로는 안 맞는다.** 형식적으로는 2번(「c=8 부터 델타가 커진다」)인데, 문턱은 §2 의 클라이언트
   문턱이 아니라 **서버 포화 지점**과 겹치고, Spring CPU 는 판별 불가다. 정직한 한 문장: *델타는 c 와 함께 커지지만 그 기울기는
   AI 쪽 호출당 고정 비용(1~3 cpu-ms)이 포화 구간에서 큐로 증폭된 것이고, Spring 클라이언트 구조(브리지·루프)의 동시성 대가는
   이 무대에서 **검출되지 않았다**(없다는 뜻이 아니다).*
3. **채택 판단에 쓰일 것**: 포화 구간 처리량 −15%(webclient) · 호출당 서버 CPU +1~3ms · 홉 0.5 cpu-ms + 디스크 버퍼링. 지연 절대값은 이
   동거 무대의 값이다. **채택은 여전히 미결** — 설계 문서 §10 · empirical-comparison §11 로.

## 8. 안 한 것 · 못 하는 말

- **Spring 클라이언트의 CPU 대가는 못 쟀다**(§4-1). 잰다면 칸을 길게(N ≥ 1,000) 하고 팔 전환 직후 몇 칸을 더 버려야 한다.
- **AI 쪽 1~3ms 의 내부**(JSON 파싱 ↔ pydantic ↔ 스레드풀)는 안 갈랐다.
- **Start 의 풀 대기 가설**은 계기 없이 자리만 맞춘 것이다.
- **개방 루프**(초당 λ)는 안 했다 — 이 라운드가 잰 천장(3워커 ≈ 275~283 / 234~241 재부착/초)이 λ 의 근거가 될 수 있다.
- **재시작 원인**(§6) 미검증.
- Stop 은 부산물이다 — 어느 c 에서도 안 겹치지 않는다(아웃박스가 직렬화, 설계 §3-3).
- nginx 액세스 로그는 이미지 기본 `access_log` 와 라운드용 `ab` 포맷이 **둘 다** 켜져 요청이 두 번 찍힌다(17MB) — 저장소엔 안 넣고
  S3 에만 둔다(`s3://shadowfit-measure-055447613012/shadowfit/ec2-20260911-134811/clientconc/nginx-access.log`). §4-3 의 수치는 `ab` 줄만 센 것.
- 로컬 결과 파일 중 `tokens.txt` 는 뺐다(만료된 테스트 계정 토큰이지만 저장소에 둘 이유가 없다).
