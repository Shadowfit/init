## 0. 한 줄

**binlog 를 N초마다 S3 로 내보내면, 서버를 통째로 잃었을 때 잃는 것은 «마지막으로 내보낸 뒤 쌓인 만큼» 이고, 그 최대치가 거의
N초였다** — 60초 주기에서 6~51초, 300초 주기에서 109~300초. 언제 잃느냐(주기 안의 어느 시점)에 따라 0 부터 N 사이를 오간다.

## 1. 결과 (본판)

| 반출 주기 | 잃은 시점 (주기 안) | **잃은 시간 (RPO)** | 복구된 / 커밋 성공 받은 트랜잭션 |
|---|---|---:|---|
| 60초 | 0.18 | **6.3초** | 57,744 / 59,849 |
| 60초 | 0.74 | **37.7초** | 59,024 / 71,343 |
| 60초 | 0.90 | **51.0초** | 58,509 / 75,140 |
| 300초 | 0.32 | **108.9초** | 199,082 / 223,869 |
| 300초 | 0.60 | **193.4초** | 199,310 / 251,619 |
| 300초 | 0.95 | **299.5초** | 198,875 / 285,360 |

(버림판: 60초 · 0.66 → 32.7초)

- **잃은 시간 ≈ «주기 안에서 잃은 시점» × 주기** — 주기 끝 무렵에 잃을수록 많이 잃는다. 최악은 주기 하나만큼이다
- 🔴 **300초 주기의 최악(299.5초)은 주기에 바짝 붙었다.** 반출은 «닫고 → 올리기» 라서 올리는 동안 쌓인 몫이 더해질 수 있다 —
  주기를 «최대 손실» 로 약속하려면 **주기 + 업로드 시간** 으로 잡아야 한다(이 무대의 업로드 시간은 따로 안 쟀다)
- 잃은 «시간» 은 쓰기 속도와 무관하지만, 잃은 «행 수» 는 쓰기 속도에 비례한다 — 이 실험의 writer 는 최대 속도(15개 연결,
  초당 수천 행)라 행 수는 DAU 1,000 가정보다 훨씬 크다. **인용은 «초» 로 한다**
- 「커밋 성공 받은」 = writer 클라이언트(소스 밖 컨테이너)가 COMMIT 응답을 받은 것. 서버가 사라져도 이 기록은 남는다

## 2. 복구에 걸린 시간 (판별 범위)

| 단계 | 60초 주기 | 300초 주기 |
|---|---|---|
| S3 에서 백업 내려받기 | 2.4~2.6초 | 2.5~2.6초 |
| prepare + copy-back | 54~56초 | 53~56초 |
| 서버 기동 | 1.4~2.5초 | 2.4~2.5초 |
| S3 에서 binlog 내려받기 | 6.9~7.6초 | 62.9~63.3초 |
| **binlog 재생** | **437~448초** | **1,449~1,467초** |

⚠️ 재생 시간이 큰 건 writer 가 최대 속도로 쓴 탓이다(백업 뒤 2~15분 동안 초당 수천 행). **실제 쓰기량 기준의 재생 시간은 짝 실험
표를 쓴다**(1GB 당 약 2분 15초). 이 표에서 쓸 값은 «백업 붓기 단계가 1,000만 행에서 1분 남짓» 정도다.

백업 시도: 7판 모두 **1회 만에 성공**(EC2). 로컬 스모크에서는 쓰기 중 XtraBackup 이 redo 를 못 따라가 실패한 판이 있었다(§4).

## 3. 조건 — 인용할 때 떼면 안 되는 것

1. **«상실» 은 소스 컨테이너와 볼륨(데이터·binlog)을 통째로 지운 것**이다. 반출기는 같은 호스트에 있다고 보고 같이 멈췄다.
   ⚠️ 이미 시작된 업로드 한 건은 끝까지 갔을 수 있다 — 실제 호스트 죽음보다 아주 조금 낙관적이다
2. 반출 = `FLUSH BINARY LOGS` 로 지금 파일을 닫고, 닫힌 파일을 `aws s3 cp` 로 올린다. 반출기는 판 시작부터 상시로 돈다
3. 판마다 «잃는 시점» 을 주기 안에서 다르게 두었다(0.18~0.95). 본판이 주기당 3판이라 **최악이 299.5초보다 클 가능성을 배제하지 못한다**
4. writer 페이로드는 실제 JSON(≈2KB/행) — 짝 실험과 같은 writer(`../binlog-replay-time-2026-11-07/_writer_common.sh`)
5. 같은 리전 S3 · m6i.xlarge 네트워크 — 다른 리전으로 내보내면 업로드 시간이 늘고, 그만큼 최악이 늘 수 있다

## 4. 로컬 스모크가 걸러낸 rig 결함

- 쓰기 중 XtraBackup 이 «could not find redo log file with LSN» 으로 실패 → redo 용량 2GB + 3회 재시도, 시도 횟수를 결과 칸으로.
  redo 를 늘린 뒤에도 로컬에서 한 번 났다 — XtraBackup 8.0 계열 마지막(8.0.35)과 서버(8.0.46)의 버전 차이로 인한 경합으로
  **추정**(검증 안 함). EC2 7판에선 안 났다
- 기준 사본에 남은 시딩 binlog 를 반출기가 먼저 올리느라 정작 백업 이후 파일을 못 올림 → `RESET MASTER` + 판 시작 파일부터
- **writer 를 소스 컨테이너 안에서 돌려, 상실 때 «커밋 성공» 기록도 같이 사라짐**(받은 수 1,800 < 복구된 수 1,915 로 잡힘) → 소스 밖 클라이언트
- 반출기를 백업 뒤에 켜서 첫 파일이 커지고, 그걸 올리는 도중 상실이 나 백업 이후를 통째로 잃음 → 판 시작부터 상시
- 볼륨 삭제 순간 업로드 helper 가 볼륨을 잡고 있어 삭제 거부 → 반출기 먼저 멈추고 재시도
