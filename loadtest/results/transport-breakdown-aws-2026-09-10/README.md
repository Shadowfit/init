# 전송 비용 분해 — 고정비는 nginx 홉이 아니라 클라이언트 쪽이다

설계: [`docs/decisions/grpc-webclient-transport-cost-breakdown.md`](../../../docs/decisions/grpc-webclient-transport-cost-breakdown.md)
선행: [2차 라운드](../ai-call-latency-ab-aws-2026-09-10/README.md)(프로덕션 클라이언트로 왕복을 처음 잼) ·
[1차 라운드](../../../docs/decisions/grpc-webclient-empirical-comparison.md) §10(도구가 AI 를 직접 침)
실행: 2026-09-10 · `RUN_ID=ec2-20260910-145300` · 본 측정 1,075초 · 팔 3 × 블록 5 × 100사이클(+버림)

---

## 0. 한 줄

**2차가 남긴 고정비는 nginx 홉이 아니었다.** 홉은 0.01~0.88ms 뿐이고, 나머지 **1.35~3.03ms 가
클라이언트 쪽**에서 온다. 커넥션 수립도 아니다(재사용률 98.8).

---

## 1. 왜 이 라운드가 필요했나

2차는 「webclient 가 호출당 1.8ms(작은 요청)·3.0ms(큰 요청) 느리다」까지 냈는데, **작은 요청에서도
1.8ms** 라 「protobuf 가 JSON 보다 작아서」로는 설명이 안 됐다. 직렬화가 지배했다면 작은 요청의
델타는 0 에 가까워야 한다. 그래서 팔을 하나 더 세워 **뺄셈**으로 갈랐다:

| 팔 | 경로 |
|---|---|
| **A. grpc** | Spring → `shadowfit-ai:8585` (직결) |
| **B. webclient-nginx** | Spring → `ai-nginx:8000` → 워커 |
| **C. webclient-direct** | Spring → `shadowfit-ai:8000` (**홉 없음**) |

**(B−C) = nginx 홉** · **(C−A) = 홉을 뺀 나머지**. 같은 클라이언트·같은 직렬화끼리 빼므로 도구
오프셋이 원리적으로 안 낀다.

잔여 최소 1.353). ➡ **기제는 홉이 아니라 클라이언트 쪽이다.**

## 3. 커넥션 후보(ㄷ)는 증거로 지웠다

nginx 로그(`$connection`·`$connection_requests`·`$request_length`)를 이 라운드에서 처음 켰다:

| | |
|---|---|
| `internal/analysis` 요청 | **1,680건** |
| 서로 다른 커넥션 | **17개** |
| 커넥션당 최대 요청 | **126건** |
| 재사용률 | **98.8 요청/커넥션** |

즉 **매 요청마다 커넥션을 새로 세우는 게 아니다.** 후보 ㄷ(커넥션 취급)은 이 무대에서 배제된다.
남은 것은 **ㄴ(블로킹 브리지 — `.block()` + 이벤트루프 왕복)** 과 직렬화다.

**크기 축이 그 둘을 한 겹 더 가른다**: 잔여가 279B 에서 **1.35~1.91ms**, 111.5KiB 에서
**2.00~3.03ms** 다. 즉 **크기와 무관한 몫이 ~1.4ms**, 크기에 따라 붙는 몫이 **~0.6~1.1ms**.
전자가 브리지 후보의 크기이고, 후자가 JSON 직렬화/파싱의 크기다 — 다만 **이 라운드는 그 둘을
직접 분리하지 않았다**(§5).

---

## 4. 1차 라운드와의 교차 검증

1차는 **다른 방법으로**(k6 로 nginx 경유 ↔ 워커 직결) 같은 홉을 **0.1~0.8ms** 로 쟀다.
이번 뺄셈은 **0.01~0.88ms** 다 — 방법도 도구도 클라이언트도 다른데 같은 자리가 나왔다.
홉 비용에 대해서는 이제 **독립 두 판**이 있다.

---

## 5. 안 한 것 · 못 하는 말

- **잔여의 내부 분해를 안 했다.** 「브리지 vs 직렬화」를 직접 가르려면 클라이언트 안에 계기를
  더 넣어야 한다(예: 요청 인코딩 완료 시점·응답 도착 시점). §3 의 크기 축 논증은 **간접**이다.
- **동시성은 그대로 미측정.** c=1 닫힌 루프다. 블로킹 브리지가 원인이라면 그 대가는 지연보다
  **스레드 점유·처리량**에서 더 크게 나타날 수 있고, 그건 별도 축이다.
- **팔 비교의 고전적 유의성**: 블록 5개는 부호검정으로 양측 p=0.0625 라 「통계적으로 유의」라고
  쓰면 과장이다. 다만 이 라운드의 판정(홉 ↔ 잔여)은 두 범위가 **자릿수로 벌어져 있어**
  그 논쟁에 덜 민감하다.
- **무대**: mysql+backend+ai 동거 `c7i.2xlarge` 1대. 절대값은 이 무대의 값이다.
- **채택 결정 아님.** 이 라운드는 기제만 만든다.

---

## 6. 이 결과가 바꾸는 서사

- 🔴 **「gRPC 가 이진화라 빠르다」는 이 데이터로 못 받친다.** 작은 요청(279B)에서도 1.7ms 차이가
  나고, 그 대부분이 크기와 무관한 몫이다. 직렬화 형식이 아니라 **클라이언트 구조**가 델타를 만든다.
- ✅ **「검증된 nginx 라우팅을 재사용하는 비용」은 작다** — 0.01~0.88ms. 라우팅 이원화를 없애자는
  논거(`grpc-webclient-empirical-comparison.md` §2)가 이 라운드로 **더 강해졌다**: 홉은 싸고,
  webclient 가 느린 이유는 홉이 아니다.
- 따라서 「지연 때문에 gRPC 를 유지한다」는 근거는 **더 얇아졌다**. 남은 근거는 여전히 duplex
  스트리밍 수요(확인된 바 없음)뿐이다.
