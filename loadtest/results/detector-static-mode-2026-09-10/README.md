## 0. 왜 쟀나

`session-detector-ownership.md` 는 검출기 소유 4안 중 ㄱ안을 이렇게 닫았다:

> | ㄱ. `static_image_mode=True` | ❌ **탈락.** 트래킹을 버리면 매 프레임 탐지기가 돈다 — 프레임당 비용이 오르는데, 이 시스템의 병목이 바로 그 비용이다 |

같은 표의 ㄹ안은 **41~63%p** 라는 숫자로 닫혔는데 **ㄱ안만 숫자가 없다.** 확인해보니
`calibrate_box.py:107`·`measure_ai_concurrency.py`·`thread-collision` rig 가 전부
`static_image_mode=False` 로 돌았다 — **True 의 비용은 한 번도 측정되지 않았다.**

판돈: True 면 트래킹 상태가 **애초에 없어서** #164 의 교차오염(검출기를 세션 간에 돌려쓰면
20/20 → 11/20)이 구조적으로 불가능해진다. 그러면 검출기가 세션에 묶일 이유가 사라지고
**sticky routing · `ReattachAnalysis` · `X-AI-Worker` 공개가 함께 없어진다.**

## 1. 결과

| | k 중앙값 | IQR | 범위 | A p50 | B p50 |
|---|---:|---:|---|---:|---:|
| **본 측정** (A=False vs B=**True**) | **1.762** | 0.258 (1.719~1.977) | 1.37~2.57 | 29.7ms | 54.8ms |
| **음성대조군** (A=False vs B=False) | **1.010** | 0.164 (0.895~1.059) | 0.67~1.32 | 33.4ms | 34.0ms |

**`static_image_mode=True` 는 프레임당 약 1.76배 비싸다.**

검출률은 **양쪽 다 100%** 였다(블록 20 × 10프레임 × 2팔). True 가 검출을 더/덜 하지 않는다 —
차이는 순수하게 시간이다.

## 2. 왜 이 값을 믿을 수 있나

1. **음성대조군이 통과했다.** 두 팔을 같은 설정으로 돌리면 k=1.010, IQR 0.164. 팔 간 차
   (1.762 − 1.010 = **0.75**)가 양쪽 IQR보다 3배 이상 크다 → 이 박스가 이 크기의 차이를 분해한다.
   🔴 이 대조군이 없으면 «1.76» 은 박스 노이즈와 구분이 안 된다.
2. **독립 교차검증.** 대조군의 A p50 = **33.4ms** 가
   [`../ai-path-profile-2026-08-17`](../ai-path-profile-2026-08-17/README.md) §1 의 같은 박스
   MediaPipe `process()` 실측 **33.08ms** 와 맞는다. 다른 사람이 다른 rig 로 잰 값이다.
3. **팔을 10프레임 블록으로 교차**시켜 두 팔이 겪는 배경 조건을 ~1초 단위로 같게 만들었고,
   블록쌍마다 순서를 반전했다. k 는 블록쌍 안에서 짝지어 계산하므로 공통 드리프트가 상쇄된다.
4. **중앙값 통계.** 평균은 배경 스파이크 하나에 먹힌다(§3).

## 3. v1 이 왜 실패했나 — 기록으로 남긴다

첫 rig 는 팔 하나를 150프레임 **통째로** 돌린 뒤 다음 팔로 넘어갔다. 한 팔이 도는 ~10초 동안
배경 부하가 변하면 그 변화가 통째로 그 팔에 얹힌다:

```
round 2  B  mean=111.42  p50=58.76  max=7106.57   ← 프레임 하나가 7.1초
round 3  B  mean=117.88  p50=75.05  max=6557.80
cpu_load: 시작 26% → 종료 100%
```

k(mean) 이 판마다 1.33~3.53 으로 튀었고 **「판 간 산포 < 팔 간 차」 검산이 떨어졌다.**
평균을 p50 으로 바꾸면 1.17~2.13 으로 좁아지지만 여전히 넓다 — **통계가 아니라 설계가 문제였다.**
v2 의 교차 + 대조군이 그걸 고쳤다. ([[feedback_measure_design_needs_repeats]])

## 4. 그래서 무엇이 갈리나 (⚠️ 유도값 — 이 rig 가 잰 것이 아니다)

[`../ai-recalibrate-2026-08-11`](../ai-recalibrate-2026-08-11/README.md) 의 c7i.2xlarge 실측을
`k=1.762` 로 나눈 **산술**이다. k 의 하드웨어 이식성은 §5 에서 열려 있다.

| | 현행 (ㄴ안) | ㄱ안 적용 시 |
|---|---:|---:|
| 물리코어당 동시 세션 (클라 3fps) | 16.39 | **9.30** |
| c7i.2xlarge(물리 4코어) 동시 세션 | 65.5 | **37.2** |
| 가정 피크 67세션에 필요한 물리코어 | 4.09 | **7.20** |

**대가는 CPU 1.76배.** 얻는 것:

- 세션↔검출기 결속 해제 → 세션당 98.7MB 상주가 사라지고 풀 크기가 «동시 세션» 이 아니라
  «동시 in-flight 프레임» 기준이 된다 (3fps 에서 검출기 duty cycle 은 `3 × 17.6ms = 5.3%`)
- sticky routing(`nginx-ai`) · `ReattachAnalysis` · `X-AI-Worker` API 노출이 **함께** 없어진다
- `ai-backend-integration.md` §9 「단일 AI 인스턴스 가정」 해소 → 수평 확장 가능
- #164 교차오염이 구조적으로 불가능 (트래킹 상태가 없다)

⚠️ 메모리 축은 **c7i.2xlarge 에선 이득이 아니다** — 65.5세션 × 98.7MB ≈ 6.5GB 로 16GB 안에
들어가 CPU 가 먼저 막힌다. 메모리 이득은 메모리가 먼저 막히는 박스에서만 유효하다.

## 5. 🔴 열린 것 — 인용 전에 알아야 할 것

1. **k 의 하드웨어 이식성이 미확인.** 이 박스는 i3-6100 이다. `ai-recalibrate` §2[B] 에서
   유사한 성격의 비(깨진 트래킹 비용)가 i3 1.19x → Xeon 1.26x 로 **약 6% 움직였다.**
   k 도 c7i 에서 다를 수 있다. → `AWS-RIDE-ALONG.md` 탑승 후보(팔 2개, 수 분).
2. **합성 프레임이다.** `frames.json` meta 가 「실사진 아님」을 명시한다. 재탐지 비용은
   피사체·배경 복잡도에 의존할 수 있고, 그 방향으로 k 가 움직일지는 안 쟀다.
3. **동시성 없는 순차 측정이다.** GIL·스레드풀 아래에서 k 가 유지되는지는 별개 질문이다
   ([`../ceiling-cause-stage2-2026-08-24`](../ceiling-cause-stage2-2026-08-24/README.md) 축).
4. **이 문서는 ㄱ안을 채택하지 않는다.** 숫자만 만들었다 — 채택은 사용자 결정이다.
