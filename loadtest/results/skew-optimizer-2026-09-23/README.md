# 치우친 분포에서 옵티마이저 추정·계획 선택 (2026-09-23)

설계: [`docs/decisions/skewed-distribution-optimizer-estimates.md`](../../../docs/decisions/skewed-distribution-optimizer-estimates.md) · 시더: [`loadtest/seed/gen_skew_seed.py`](../../seed/gen_skew_seed.py) · 하니스: [`loadtest/measure_skew_optimizer.py`](../../measure_skew_optimizer.py)
무대: 로컬 i3-6100 · Docker Desktop · MySQL 8.0.46 · 버퍼풀 2GB(표가 통째로 들어감) · `innodb_stats_persistent=1` · `auto_recalc=1` · 표본 20페이지 · `eq_range_index_dive_limit=200` (`env.txt`)
데이터: 데이터셋 8개 × 약 10만 세션 · 평균 F=7 · R=30 (자기검증 `seed/*.log`) · 통계 팔 S0~S3 · M3 5회
원본: `raw/` (팔별 EXPLAIN ANALYZE + Handler + 통계 스냅샷) · 요약: `summary.tsv`(688행) · `m3.tsv`

> **판정은 «계획이 바뀌었나」와 «바뀐 계획이 Handler 를 더 읽나」로만 한다.** 시간은 기록만 했다(반복·라틴 방격 없음, 로컬). q-error 는 보고만 한다.

## 0. 한 줄

**쿼리 모양 62개(T1 12 · T3·T4 50) 중 통계 팔에 따라 계획이 바뀐 것은 0개다.** 분포 사이에서 달라진 것은 ㄴ-3 이 두 회원 인덱스 중 무엇을 고르느냐뿐이고 Handler 차이는 0~3 이다. 치우침은 추정 오차를 키웠지만(최대 26.5배) 선택을 뒤집지 못했고, `ANALYZE`·히스토그램·표본 확대는 추정도 계획도 거의 못 바꿨다. 원인은 두 가지로 설명된다. 대상 쿼리의 조건이 **전부 인덱스 컬럼**이라 추정이 index dive 로 가고, **히스토그램은 인덱스 있는 컬럼에 쓰이지 않는다.** 그리고 넓은 범위의 추정은 **표 행 수의 절반에 상한**이 걸려 통계를 바꿔도 안 움직인다.

## 1. T1 주간 JSON_TABLE — ㄴ-3 은 치우침에도 견고하다

| 쿼리 | 드라이빙 (전 셀) | 헤비 회원 q-error (균일 → 강함) | 헤비 회원 Handler (강함·치우친 상태) |
|---|---|---|---|
| ㄴ-3 이전 (`r.member_id`) | 늘 `r(member_id)` | 2.0 → 3.0 → **26.5** (상태 균일) / 2.0 → 3.2 → **21.7** (상태 치우침) | 918 |
| **ㄴ-3 현행** (`s.member_id + status`) | 늘 `s` 쪽 회원 인덱스 | **1.0 ~ 1.7** | **410** |

- **계획은 한 번도 안 바뀌었다.** 헤비(F=365)·중간·라이트 회원, 세 치우침, 네 통계 팔 모두 같은 드라이빙이다. «평균이 같은데 회원마다 계획이 갈리나」의 답은 **아니오**다.
- ㄴ-3 이전 모양의 오차는 **헤비 회원의 F 에 비례해 커진다**(26.5배). 그래도 계획은 이미 r 드라이빙이라 바뀔 게 없다. 비용은 Handler 로 드러난다: 같은 회원에서 918 vs 410.
- ㄴ-3 은 `(member_id, status, start_time)` 한 범위에 조건이 다 들어가 **추정이 index dive 하나로 끝난다** — 그래서 치우침과 무관하게 정확하다. 09-15 채택 결론(«F 와 무관」)이 분포를 바꿔도 유지된다.
- 참고: ㄴ-3 의 s 쪽은 두 회원 인덱스(`…member_status_start` / `…member_exercise_status_start`)를 셀에 따라 번갈아 골랐지만 Handler 차이는 0~3 이다(종목이 전부 1 이라 두 인덱스가 사실상 같다).

### 1-1. 오차 21.7배의 정체 — 독립 가정 + 절반 상한

ㄴ-3 이전 모양의 오차는 `s.start_time` **필터** 노드에서 난다. 추정 선택도가 모든 셀에서 정확히 **0.5** 였다.

| 셀 | 필터 추정 (루프당) | 실제 (루프당) |
|---|--:|--:|
| 균일 F=7 | 0.5 | 1 |
| 강함 F=365 · 치우친 상태 | 0.5 | 0.0231 |

- 그 0.5 는 `start_time` 인덱스의 **표 전체** 범위 추정이다. 대상 주의 실제 세션은 76,662건(77%)인데 추정은 **49,997 = 전체 99,995 ÷ 2** 였다(`EXPLAIN … FORCE INDEX(idx_session_starttime_member)`, 09-23 재확인). **넓은 범위는 표의 절반으로 상한이 걸린다**(관측. InnoDB 소스로 확인하지는 않았다).
- 그리고 옵티마이저는 그 **표 전체의 비율을 회원 한 명에게 그대로 곱한다.** 회원과 시각이 독립이라고 가정하는 것이다. 헤비 회원은 365건 중 7건만 그 주라 실제 2%인데 50% 로 봤다.
- ⚠️ **크기는 시드가 만든 것이다.** 평균 F = W = 7 이라 세션 대부분이 대상 주에 몰렸다(설계 문서 §6-1 의 «읽을 점 2»). 실사용처럼 한 주가 전체의 1/52 쯤이면 표 전체 비율도 2% 근처라 헤비 회원의 오차는 줄고, 대신 그 주에 몰아서 한 회원 쪽이 틀린다. **메커니즘(독립 가정 + 절반 상한)은 진짜고, 21.7 이라는 숫자는 이 시드의 것이다.**

## 2. 히스토그램은 인덱스 있는 컬럼에 쓰이지 않았다

S2(히스토그램 추가)는 S1 대비 **계획을 하나도 바꾸지 않았고**, 추정이 달라진 것은 62개 중 5개뿐이다. 그 5개도 `ANALYZE` 를 다시 돌리며 표본이 바뀐 수준(예: 2,498 → 2,495)이다. 대상 쿼리의 필터 컬럼(`status`·`start_time`·`member_id`)이 전부 인덱스가 있는 컬럼이었기 때문이다. 따로 확인했다(`skew_t34_skew`):

| | COMPLETED 비율 |
|---|--:|
| 실제 | 69.94% |
| 히스토그램(singleton) 버킷 | **69.94%** — 정확히 알고 있다 |
| 옵티마이저 추정, 인덱스 사용 (`ref`) | 49,997행 = **50%** (절반 상한) |
| 옵티마이저 추정, 세 인덱스 `IGNORE INDEX` (`ALL`, filtered) | **25%** — 여전히 히스토그램을 안 쓴다 |

→ «인덱스는 있지만 이 쿼리에선 필터로만 쓰이는 컬럼」에도 히스토그램은 쓰이지 않았다. 인덱스 힌트로 인덱스를 빼도 마찬가지였다. 이 MySQL 8.0.46 에서 히스토그램이 일하는 자리는 **인덱스가 아예 없는 컬럼**뿐이다. 25% 가 어디서 왔는지(인덱스 통계의 값 종류 4 에서 1/4 로 추정)는 확인하지 않았다.

## 3. T3 대시보드 — 41.7배는 이미 없다 (설계 문서 정정)

| 쿼리 | 계획 | 추정 / 실제 |
|---|---|---|
| a «오늘 세션 수」 | `idx_session_starttime_member` range | **275 / 275** (전 팔·두 분포) |
| b «상태별 분포」 | `idx_session_status_starttime` 커버링 전수 | 그룹 수 3 / 4 (S3 에서만 4/4) |

- 설계 문서 §1 이 «균일 데이터에서도 41.7배 과대」를 현재 문제로 인용했는데, **그건 08-07 인덱스 통합 전의 skip scan 이야기다.** `admin-page-scope.md` §4-5-2(08-09)가 이미 «통합 후 사라졌다」고 적었다. 이번 측정은 그 기록을 재확인했다. 인용할 때 §4-5-2 를 안 읽은 쪽의 실수다.
- b 의 «그룹 3개로 추정」은 `status` 인덱스의 카디널리티가 표본으로 3 이 나오기 때문이다(M3 에서 5회 모두 3). S3(표본 최대)에서만 4 로 맞았다. 계획은 안 바뀐다.

## 4. T4 관리자 목록·총건수 — 옵티마이저는 Handler 기준으로 늘 옳았다

| | 선택 인덱스 (전 셀·전 팔) | Handler (선택 / `start_time` 강제) |
|---|---|---|
| 목록 `LIMIT 20` | 늘 `(status, start_time)` | **20** / 28 ~ 896 |
| 총건수 | 늘 `(status, start_time)` | 조건에 맞는 행 수 그대로 |

- 목록은 **모든 셀에서 선택한 쪽이 덜 읽었다.** `(status, start_time)` 은 상태 구획으로 들어가 뒤에서부터 20개만 읽는다.
- ⚠️ **09-10 의 «흔한 상태·전체 기간에서 37배 느리다」는 이 판정 기준으로는 안 보인다.** 09-10 README §4 가 스스로 적었듯 그때도 Handler 는 거의 같았다(24 vs 19) — 차이는 행 수가 아니라 **행당 비용**이었다. 이 라운드는 시간을 판정에 안 쓰므로 그 현상을 재지 못했다. 재려면 M4(시간, 반복·라틴 방격, 가능하면 EC2)가 필요하다.
- 총건수의 «기간 전체」 셀은 추정이 **표의 절반(≈49,960)** 에 붙는다. 실제 25%(균일)·70%(COMPLETED 치우침) 어느 쪽이든 50% 로 본다(q 1.4~2.3). §1-1 과 같은 절반 상한이다. 계획은 안 바뀐다.
- 목록 쿼리의 q-error(최대 2,500)는 `LIMIT 20` 이 범위를 일찍 끊어서 생긴 것이라 **추정 오차가 아니다.** 판단에서 뺀다.

## 5. M3 — 통계 표본은 흔들리지만 계획은 안 흔들린다

| 데이터셋 | 회원 인덱스 카디널리티 (5회 ANALYZE) | 실제 회원 | 계획 뒤집힘 |
|---|--:|--:|---|
| 균일 F7 · 상태 균일 | 13,441 ~ 16,999 | 14,285 | 없음 |
| 강함 F365 · 상태 치우침 | 12,642 ~ 16,449 | 14,285 | 없음 |
| (8개 전체) | 최저 11,568 · 최고 16,999 | 14,285 | **8개 모두 없음** |

- 기본 표본 20페이지로는 카디널리티가 **실제의 −19% ~ +19%** 사이에서 흔들린다. `status` 카디널리티는 5회 모두 3 으로 틀린 채 고정이다(실제 4).
- 그래도 대상 쿼리의 계획은 한 번도 안 뒤집혔다 — 추정이 카디널리티 평균이 아니라 index dive 로 가기 때문이다.

## 6. 무엇을 말할 수 있고 무엇을 못 하나

**말할 수 있다**
- 주간 쿼리 ㄴ-3 은 회원별 활동량이 치우쳐도(최대 F 365, 평균 7) 계획·추정이 흔들리지 않는다. 조건을 인덱스 범위 안으로 끌어들인 효과다.
- 이 스키마의 대상 쿼리들은 추정이 index dive 로 가서 `ANALYZE`·히스토그램·표본 크기가 계획에 영향을 주지 못했다.
- 히스토그램은 인덱스가 있는 컬럼에는 쓰이지 않았다(인덱스를 힌트로 빼도).
- 넓은 범위 추정에는 표의 절반 상한이 관측된다.

**못 한다**
- 실서비스 분포에서의 크기. 합성 데이터이고 치우침·상태 비율은 가정이다. 1-1 의 21.7배는 시드의 대상 주 몰림에서 커진 값이다.
- 09-10 의 «행당 비용」 현상. 시간을 판정에 안 썼다.
- 절반 상한의 소스 수준 확인. 관측만 했다.
- 인덱스 없는 컬럼에서의 히스토그램 효과. 대상 쿼리에 그런 조건이 없었다.
