## 0. 한 줄

**Spring 안에서 클라이언트 경로(Tomcat 요청 스레드 + Reactor 루프 + gRPC netty ELG)가 쓰는 CPU 는 gRPC 2.59~2.64 · WebClient 2.99~3.13 cpu-ms/재부착 —
델타 +0.37~0.53(블록 5 전부 안 겹침).** 자리는 **Reactor 이벤트루프(0.74~0.88)** 이고, gRPC 팔에서 그 역할을 하는 netty ELG 는 0.31~0.32 다.
**호출 스레드(Tomcat) 몫은 두 팔이 같다**(2.22~2.34, 겹침) — 「스텁 프레이밍을 호출 스레드가 직접 한다 vs `.block()` 으로 기다린다」 는 CPU 로는 구분되지 않는다.
4·5차가 «판별 불가» 로 남긴 자리가 닫혔다: 설계 §6 의 **첫 번째 문장**. 왕복 델타 +1.64~1.88ms 중 Spring 몫은 이 0.4~0.5 이고, 나머지는 AI 쪽·홉이다.

## 2. 주 판정 — 스레드 그룹별 CPU-ms/재부착 (블록 5개 범위)

| 그룹 | 무엇 | A·grpc | C·webclient | C − A | 규칙 1 |
|---|---|---|---|---|---|
| **클라이언트 경로** (tomcat+reactor+grpc-elg) | 주 판정 | 2.591 ~ 2.642 | 2.988 ~ 3.129 | **+0.371 ~ +0.531** | ✅ **안 겹침 — WebClient 가 더 쓴다** |
| tomcat (`http-nio-8080-e`) | 핸들러 + (A) 스텁 프레이밍·디코딩 / (C) `.block()` 대기 | 2.275 ~ 2.328 | 2.223 ~ 2.344 | −0.058 ~ +0.052 | 🟡 겹침 — **같다** |
| reactor (`reactor-http-ep`) | (C) 인코딩·I/O·디코딩 | — (스레드 없음) | 0.744 ~ 0.877 | — | C 에만 |
| grpc-elg (`grpc-default-wo`) | (A) 채널 netty I/O (+콜백 서버 I/O, 공통) | 0.314 ~ 0.317 | 0.000 | −0.317 ~ −0.314 | A 에만 |

### 2-1. 읽기

1. **델타 = reactor − grpc-elg.** 0.74~0.88 − 0.31 ≈ +0.43~0.57 — 주 판정의 +0.37~0.53 과 같은 자리다. 즉 WebClient 의 추가 비용은 통째로 **이벤트루프가 하는 일**(Jackson 인코딩 114KB · 응답 디코딩 · HTTP/1.1 I/O)이고, gRPC 는 같은 역할을 netty ELG 가 0.31 로 한다.
2. **호출 스레드는 같다.** 4차 §2-1 이 가설로 둔 「gRPC 는 호출 스레드가 프레이밍·디코딩까지 직접 하니 tomcat 몫이 더 클 것」 은 **안 나왔다** — 두 팔의 tomcat 그룹이 0.05~0.12 폭 안에서 겹친다. 핸들러(JWT·DB 114KB 읽기·JSON 응답)가 2.2 cpu-ms 이고 그 위에 얹히는 클라이언트 몫은 두 팔 모두 이 분해능 아래다. 「ThreadlessExecutor 가 호출 스레드에서 콜백을 돈다」 는 사실이지만 CPU 로는 안 보인다.
3. **콜백 서버 몫은 0 이었다.** C 팔의 grpc-elg 가 0.000 — c=1 이라 콜백(start·stop)이 칸당 1~2건이라서다. A 의 0.31 은 전부 클라이언트 채널 I/O 로 읽어도 된다.
4. **분해능**: 블록 범위 폭이 그룹당 0.05~0.14 cpu-ms — 5차 c=1 의 backend cgroup 폭(16~45)의 1/200. 스레드 분리 + 칸 20배가 그만큼 가져왔다.

## 4. 보조 — 지연·AI·구멍

- **Reattach p50**: A 4.62~4.81 · C 6.40~6.50 ms, 델타 **+1.64~1.88** — 5차 c=1 의 +2.3~3.8 보다 좁고 낮다(칸이 길어 분산이 줄었다). 이 중 Spring 클라이언트 몫이 0.4~0.5 cpu-ms 이니 **나머지 1.1~1.5 는 AI 쪽 + 홉**이다 — 5차의 AI 쪽 c=8 값(1.5~2.5)·홉(≤0.9)과 같은 자리.
- **JIT 가 안 끝났다.** 워밍업 2×500 뒤에도 호출당 3 cpu-ms 가 컴파일이다. 판정 그룹엔 안 섞이지만(스레드가 다르다) 절대값(핸들러 2.2 등)은 «JIT 진행 중» 조건의 값이다. 다음에 절대값을 쓰려면 워밍업을 더 길게.
- **샌 스레드** 블록 2 팔당 1개 — 어느 그룹인지 모르고 CPU 도 모른다. 블록 2 를 빼도 판정은 안 바뀐다(범위가 블록 1·3·4·5 안에 있다).
- 재시작 0(`restart-counts.txt`, `cells.tsv` 40열), `dmesg-tail.txt` OOM 없음, `docker-events.log` 는 rig 의 `--force-recreate` 뿐.
- `nginx-access.log`(5.1MB)는 저장소에 안 넣고 S3 에만(`s3://shadowfit-measure-055447613012/shadowfit/springclient-20260914-075216/springclient/nginx-access.log`). `tokens.txt` 뺐다.

## 5. 안 한 것 · 못 하는 말

- **Reactor 루프 0.74~0.88 의 내부**(인코딩 ↔ I/O ↔ 디코딩) — 스레드가 같아서 못 가른다. 프로세스 안 계기가 필요하고 그건 팔에 비대칭.
- **동시성** — c=1 뿐. 4차가 «동시성 대가 검출 안 됨» 으로 닫았고 이번 질문은 호출당 고정비.
- **D(중첩 JSON)의 Spring 쪽** — 이스케이프를 안 하니 더 쌀 것으로 보이나 안 쟀다(§7 ①).
- **절대값** — JIT 진행 중 + calib 14.0M 박스의 값. 델타만 옮긴다.
- **채택** — 이 라운드도 결정하지 않는다.

## 6. 이 결과가 바꾸는 서사

1. **«Spring 쪽 대가는 판별 불가»(4차·5차) → «+0.37~0.53 cpu-ms/호출, 자리는 Reactor 루프».** 상한 문장(≤1~2ms)이 실측으로 바뀐다. empirical-comparison §11 을 이 값으로 갱신한다.
2. **왕복 델타의 분해가 닫혔다**: c=1 +1.6~1.9ms = Spring 0.4~0.5(이 라운드) + AI 입구 ~1(5차·4차) + 홉 ≤0.9(3차). 세 라운드의 조각이 합에서 맞는다.
3. **«블로킹 브리지» 가설은 기각에 가깝다.** 호출 스레드 몫이 같다 — `.block()` 이 비싼 것이 아니라 루프가 하는 인코딩·I/O 가 gRPC 의 ELG 보다 0.4~0.5 더 든다. 4차 설계 §2-1 의 「브리지」 항목은 이 문서로 닫는다.
4. 채택 판단엔 **안 바뀌는 게 맞다**(설계 §1) — 0.4 cpu-ms 는 저울에 안 오른다. 표에 오르는 건 5차 그대로다.
