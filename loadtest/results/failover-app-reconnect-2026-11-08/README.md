무대: **EC2 `m6i.xlarge` 3대** (원본 DB · 리플리카 DB · 앱 + 탐침) · MySQL `mysql:8.0` GTID 비동기 복제 · 백엔드 jar(prod 프로파일, Java 21) ·

질문: 원본 DB 가 죽고 리플리카를 승격했을 때, **사용자가 다시 저장되는 걸 보기까지** 얼마나 걸리나? 승격 실험은 DB 쪽만 쟀다.

## 0. 한 줄

**DNS 바꾸기(B)는 5~30초, 앱 재시작(A)은 약 106초 — 잃은 쓰기는 16판 모두 0.**
단 B 는 네트워크가 끊기는 장애(K2)에서 **요청 약 14개가 약 16분 매달렸고**, A 의 106초 중 약 90초는 **앱이 안 꺼져서** 생긴 시간이다.
그리고 DB 장애가 클라이언트에겐 **401(인증 실패)** 로 보였다(§3).

## 2. 읽기

### 2-1. A 의 106초 중 약 90초는 «앱이 안 꺼지는» 시간

A 판(6·9·12·14·15)의 앱 로그 시각이 모두 같은 모양이다:

```
장애 +1.4초   systemctl restart → 종료 시작 (Commencing graceful shutdown)
     +31초    Tomcat graceful 끝 — 붙잡혀 있던 요청이 Hikari 30초에 걸려 끝남
     +91.5초  새 프로세스 Starting  ← 종료 시작 후 약 90초
     +104초   Started (기동 자체는 12.3~18.1초)
```

종료 시작부터 새 프로세스까지가 매번 약 90초 — **systemd 기본 정지 한도(`TimeoutStopSec` 90초) 에 걸려 강제 종료된 것과 맞는다.**
Tomcat 은 31초에 끝났는데 JVM 이 그 뒤로 안 내려갔다. 무엇이 붙잡았는지는 **확인하지 않았다**(스레드 덤프 없음).
→ «A = Spring 기동 시간» 이라는 설계의 예상과 달리, **죽은 DB 앞에선 종료가 기동보다 오래 걸린다.**
운영은 systemd 가 아니라 Docker 라서 정지 한도가 다르다(`docker stop` 기본 10초 뒤 강제 종료) — 운영 A 의 시간은 이 숫자가 아니다.

### 2-2. B·K2 — 새 요청은 5초에 돌아오지만, 끊긴 연결 위의 요청은 약 16분 매달림

- 네트워크를 끊으면 원본은 «끊겼다» 는 응답(RST)조차 안 보낸다. 이미 원본과 이야기하던 요청은 리눅스가 TCP 재전송을 포기할 때까지 기다린다
  (`tcp_retries2=15`, 약 924초 + Hikari 30초 ≈ 961초 관측)
- Connector/J `socketTimeout` 을 지정하지 않아서다(설계 §6-1 R-b, 일부러 기본값). 그 값을 정할 근거로 이 숫자를 쓴다 — 값은 정하지 않았다
- 매달린 13~14개는 결국 실패로 돌아왔다(401 — §3)

### 2-3. B·K1 의 30초 — 추정 둘, 이 데이터로는 못 가른다

프로세스를 죽이면 앱은 즉시 끊김을 알고 다시 연결하려 한다. 그 순간(전환 1.4초 **전**) DNS 는 아직 옛 주소를 준다.
- 추정 ① JVM 이 DNS 결과를 30초 기억한다(보안 관리자 없을 때 기본) — 옛 주소가 30초 남는다
- 추정 ② Hikari `connection-timeout` 30초 — 연결을 못 얻은 요청이 30초에 끝난다

둘 다 30초라 구분이 안 된다. K2 가 5초인 건 끊김을 몰라 바로 다시 묻지 않았고, 나중에 새 연결을 만들 때는 DNS 기억이 이미 지나 있었기 때문으로 보인다(확인 안 함).

## 3. 🔴 찾은 결함 — DB 장애가 401 로 보인다

실패 응답이 500 이 아니라 **401** 이었다(A 판마다 13~17건, B 판 1~2건 + 매달렸다 돌아온 요청).
`JwtAuthFilter.java:90` 이 요청마다 DB 에서 회원을 읽는데, DB 예외를 `:105` 의 `catch (Exception e)` 가 «토큰 불량» 과 같이 처리한다 —
앱 로그 `JWT 인증 실패: DataAccessResourceFailureException` 137줄. 클라이언트가 401 에 로그아웃하면 **DB 가 잠깐 흔들려도 사용자가 로그아웃된다**(프론트 동작은 확인 안 함). [#848](https://github.com/Shadowfit/init/issues/848).

## 4. 조건 — 인용할 때 떼면 안 되는 것

1. **알아채기·결정 시간 0.** 장애 직후 바로 승격·전환했다. 사람이 하면 사람 시간이 더해진다(§6-3 은 저녁 30분으로 잡았다)
2. **DNS 는 앱 박스의 dnsmasq**(TTL 0) — Route 53 이 아니다(설계 §6-1 R-a). 레코드가 퍼지는 시간이 빠져 **실제보다 낙관적**이다
3. **앱은 systemd 로 돌았다** — A 의 약 90초 정지 대기는 systemd 기본값에서 나왔다. 운영(Docker)과 다르다
4. 앱 DB 타임아웃은 지금 설정 그대로(Hikari 30초 · `socketTimeout`·`connectTimeout` 미지정)
5. 비동기 복제인데 잃은 게 0 인 건 쓰기가 초당 10번으로 가벼워 리플리카가 따라가 있었기 때문으로 본다 — 무거운 쓰기에서 두 박스 손실은 안 쟀다
6. K2 는 원본 박스에서 3306 을 드나드는 패킷을 버린 것 — 호스트 상실의 대리다
