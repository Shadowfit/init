# 리플리카 승격 시간 — 소스가 죽은 순간부터 리플리카가 새 쓰기를 받기까지 (2026-11-08, EC2)

설계 문서: [`../../../docs/decisions/rpo-rto-targets.md`](../../../docs/decisions/rpo-rto-targets.md) §5 구성 3 · §8 R1
짝 실험: [`../server-prep-and-ship-cost-2026-11-08/`](../server-prep-and-ship-cost-2026-11-08/README.md) §4 (구성 2 의 복구 시간 약 6.5~7분)
무대: **EC2 `m6i.xlarge` 1대** · gp3 200GB · `ap-northeast-2d` · MySQL **8.0.46**(`mysql:8.0`) · GTID 복제(비동기) ·
`flush=1`·`sync_binlog=1` · 버퍼풀 1GB · RUN_ID `promote-ec2-20261108-034706` · 커밋 `96677a25` · 10판(버림 2 + 본판 8)

질문: 리플리카(구성 3)를 붙이면 호스트 상실 RTO 가 구성 2 의 약 7분보다 실제로 짧아지나? 문서는 그렇게 가정만 했고 승격 시간을 잰 적이 없다.

## 0. 한 줄

**DB 쪽 승격은 밀린 게 없으면 약 0.25초, 약 21초 밀려 있으면 약 7.8초였다 — 승격 시간은 거의 전부 «밀린 것 따라잡기» 다.**
구성 2 의 약 7분보다 두 자릿수 짧다. 단 장애를 알아채고 · 승격을 결정하고 · 앱 연결을 바꾸는 시간은 **빠져 있다.**

  `docker exec` 로 mysql 클라이언트를 새로 띄우는데 한 번에 43~44ms(`exec_ms`)이고, 승격 경로에서 5번 띄운다(약 220ms)
- **stress 는 승격의 97% 이상이 «적용»(받아 둔 릴레이 로그를 끝까지 적용)** 이다. 밀린 3,258~3,440건을 7.6~7.9초에 적용 —
  초당 약 430건(건당 25행이라 초당 약 1만 행)
- 🟡 죽이기 직전 리플리카는 약 21초 밀려 있었는데 따라잡는 데는 약 7.8초였다. 추정: 소스와 리플리카가 한 박스라 부하 중엔
  CPU 를 나눠 썼고, 소스가 죽은 뒤엔 리플리카가 혼자 썼다(§3-3). 확인하지 않았다
- 잃은 트랜잭션은 10판 모두 0 — 밀린 것은 «받았지만 아직 적용 안 한» 것이었고, 받는 쪽은 소스를 따라가 있었다(§3-2)

## 2. 구성 2 와 나란히

| | 구성 2 (백업 + binlog 반출) | 구성 3 (+ 비동기 리플리카) |
|---|---|---|
| DB 가 다시 쓰기를 받기까지 | **약 6.5~7분** (새 서버 140초 + 붓기 174초 + 하루치 재생 80~95초, [합산](../server-prep-and-ship-cost-2026-11-08/README.md#4-구성-2-의-복구-시간에-대입하면)) | **0.25~8초** (이 실험) |
| 빠진 것 | 사람 시간 · S3 내려받기 | 사람 시간 · 앱 연결 전환 |

→ 사람 시간을 같은 크기로 더해도 구성 3 이 몇 분 짧다. 그 몇 분이 **목표 RTO 안에 들어가야 하는지**가 Q5 의 결정이다(이 실험은 정하지 않는다).

## 3. 조건 — 인용할 때 떼면 안 되는 것

1. **사람·앱 시간 제외.** 장애 감지 · 승격 결정 · 앱 연결(DataSource URL·DNS) 전환은 안 쟀다. 이 값은 «스크립트로 자동화했을 때의 하한» 이다
2. **비동기 복제인데 잃은 게 0 인 건 한 박스라서다.** 소스와 리플리카가 같은 박스의 컨테이너라 전송이 거의 즉시였다. 실제로 다른 박스·다른
   AZ 에 두면 «아직 못 받은» 몫이 생기고 그건 잃는다 — 그 양은 [다른 AZ 복제 실험](../replication-aws-cross-az-2026-09-02/README.md)을 본다
3. **한 박스 동거.** 부하 중 CPU 를 나눠 써서 밀림이 두 박스일 때와 다를 수 있고, 소스가 죽은 뒤엔 리플리카가 CPU 를 다 쓴다. 두 박스의 승격 시간은 안 쟀다
4. «죽음» 은 `docker kill` 이다 — 프로세스·네트워크가 한꺼번에 사라지는 호스트 상실의 대리
5. 리플리카 적용 스레드 수는 기본값(8.0.46 은 `replica_parallel_workers` 기본 4)이고 판마다 기록하지는 않았다
6. paced 는 문서 §8-1 **가정** 피크(측정 아님), stress 는 4개 연결이 240초간 최대 속도 — 상한 확인용이지 운영 값이 아니다
