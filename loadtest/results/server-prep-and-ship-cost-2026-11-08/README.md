## 0. 한 줄

1. **빈 EC2 를 띄워 복구 대상 MySQL 이 쿼리를 받기까지 약 140초**(3대: 139.5 · 139.7 · 142.9초). 그중 약 107~110초가
   `bootstrap.sh`(docker·이미지·저장소 준비)다
2. **가정 피크(초당 45행)에서 binlog 반출 한 번은 1초도 안 걸린다** — 60초 주기 파일 약 5.8MB 를 0.48~0.51초,
   300초 주기 약 29MB 를 0.70~0.71초에 올렸다. `FLUSH BINARY LOGS` 는 52~56ms.
   → 호스트 상실 실험이 남긴 «최대 손실 = 주기 + 업로드 시간» 의 업로드 시간은 이 조건에서 **1초 미만**이다

## 1. 새 서버 준비 시간

`run-instances` 를 부른 시각을 0 으로 둔 누적 시각(초):

| 단계 | node1 | node2 | node3 |
|---|---:|---:|---:|
| 커널 기동 (`/proc/uptime` 역산) | 6.6 | 6.9 | 7.2 |
| user-data 시작 | 12.6 | 12.4 | 12.8 |
| `bootstrap.sh` 내려받기 끝 | 12.9 | 12.4 | 12.8 |
| `bootstrap.sh` 끝 | 120.1 | 120.1 | 123.1 |
| **복구 대상 MySQL 이 쿼리를 받음** | **139.7** | **139.5** | **142.9** |

- 큰 덩어리는 `bootstrap.sh` 약 107~110초다(패키지·docker·MySQL/XtraBackup 이미지 내려받기·저장소 받기. `ROLE=db`, Flyway 건너뜀).
  그 안의 단계별 시간은 남기지 않았다
- 마지막 약 20초는 새 `mysql:8.0` 컨테이너가 빈 데이터 디렉터리를 초기화하고 쿼리를 받을 때까지다
  (임시 초기화 서버에 속지 않으려고 `@@skip_networking = 0` 을 기다렸다)
- 3대를 몇 초 간격으로 동시에 띄웠다 — 준비 시간은 «박스를 몇 번 띄웠나» 가 반복 수라서 3대가 곧 3회다
- `launch_times.tsv` 의 `t_running_ms` 는 `aws ec2 wait instance-running` 이 돌아온 시각인데, 그 명령은 15초 간격으로 묻는다 —
  **쓰지 않는다.** 대신 박스 안에서 잰 커널 기동 시각을 쓴다

## 2. 반출 업로드 비용

반출 = 주기마다 `FLUSH BINARY LOGS` 로 지금 파일을 닫고, 닫힌 파일을 `aws s3 cp` 로 올린다(호스트 상실 실험과 같은 방식).
한 번 반출할 때마다 한 줄을 남겼고, 그게 반복 단위다. 팔 순서는 ABBA(60 → 300 → 300 → 60)라 «팔» 과 «순서» 가 섞이지 않는다.

### 2-1. 가정 피크 (`paced` — 초당 45행, 문서 §8-1 가정) ← 인용할 값

| 반출 주기 | 반출 횟수 | 파일 크기 | **업로드** | FLUSH |
|---|---:|---|---:|---:|
| 60초 | 14 | 5.76~6.03MB | **481~505ms** | 52~56ms |
| 300초 | 4 | 28.7~28.9MB | **697~707ms** | 52~56ms |

- 업로드 시간은 파일이 5배 커져도 약 1.4배만 늘었다 — 이 크기에선 S3 요청 하나의 고정 비용이 대부분이다
- 하루 반출 횟수는 60초 주기 1,440번 · 300초 주기 288번이다. 요금은 이 결과에서 계산하지 않았다
- 🔴 초당 45행은 **측정이 아니라 문서 가정(피크)**이다. «가정 피크 기준» 을 떼고 인용하지 않는다

### 2-2. 쉬지 않고 쓸 때 (`stress` — 4개 연결이 최대 속도) — 상한 확인용, 운영 값 아님

`--max-binlog-size=1G` 라 파일이 1GB 에서 잘린다. 1GB 파일 기준:

| 반출 주기 | 1GB 파일 업로드 | 비고 |
|---|---|---|
| 60초 | 2.26~2.68초 (6건) | |
| 300초 | 첫 2~3개 **9.7~12.3초**, 나머지 2.2~3.3초 (10건) | 한 번에 1GB 파일 5개가 닫혀 차례로 올림 |

FLUSH 는 68~178ms 였다(파일이 클 때 첫 FLUSH).

- 🟡 300초 주기에서 앞쪽 파일만 느렸던 이유는 **확인하지 않았다.** 추정: 오래된 파일이 페이지 캐시에서 밀려나 gp3 기본 처리량
  (초당 125MB → 1GB 약 8.6초)으로 디스크에서 읽혔고, 그동안 writer 도 같은 디스크에 쓰고 있었다. 최근 파일은 캐시에 있어 2초대였다
- 쓰기량이 이만큼 크면 «업로드 시간» 이 주기 대비 무시할 수 없게 된다 — §R5(반출 주기 한계)의 신호가 여기서 보인다

## 3. 조건 — 인용할 때 떼면 안 되는 것

1. **준비 시간은 «빈 AL2023 에서 직접 부트스트랩» 경로**다. 이미지를 미리 구워 둔 AMI 로 띄우면 bootstrap 몫이 줄어든다 — 그건 안 쟀다
2. 준비 시간에 **사람 시간(장애 알아채기 · 결정 · 실행)과 백업·binlog 내려받기·붓기는 들어 있지 않다** — 그건 §4 처럼 다른 실험 값을 더한다
3. 업로드는 같은 리전 S3 · m6i.xlarge 네트워크다. 다른 리전으로 내보내면 늘 수 있다
4. FLUSH 가 그 순간 쓰기를 얼마나 막는지는 안 쟀다(writer 지연을 기록하지 않았다)
5. 한 박스 · 한 라운드다

## 4. 구성 2 의 복구 시간에 대입하면

구성 2 의 호스트 상실 RTO ≈ **새 서버 준비 + 백업 내려받기·붓기 + binlog 내려받기·재생** (+ 사람 시간).

| 단계 | 값 | 출처 |
|---|---|---|
| 새 서버 준비 | 약 140초 | 이 실험 §1 |
| 백업 붓기 (물리, 1억 행) | 약 174초 | [`backup-restore-rto-rpo.md`](../../../docs/decisions/backup-restore-rto-rpo.md) |
| binlog 재생 (DAU 1,000 가정 하루치 ≈ 0.6GB) | 약 80~95초 | [재생 실측](../binlog-replay-time-2026-11-07/README.md) |
| **합** | **약 6.5~7분** | |

⚠️ 서로 다른 실험의 값을 더한 것이라 «한 번에 쟀더니 7분» 이 아니다. 백업은 1억 행(합성) 값이고, 백업·binlog 를 S3 에서 내려받는
시간(1,000만 행 백업 약 2.5초 — 호스트 상실 실험)과 사람 시간은 빠져 있다. 백업 이후 시간이 길수록 재생 칸이 커진다(4일치 약 5분 20초).

## 5. 재현

```bash
bash launch.sh <커밋 SHA>      # 3대: node1 = 준비 + 반출 비용, node2·3 = 준비만. 결과는 S3 의 RUN_ID 아래
OUT=$PWD/_out S3_BASE= bash ship_cost.sh   # 로컬 스모크 (가짜 S3 — 업로드 값은 의미 없음)
```

산출물: `ec2/launch_times.tsv` · `ec2/node*/prep.tsv` · `ec2/node*/box.txt` · `ec2/node1/ship/ship_cost.tsv`(반출 1건 = 1줄) ·
`ec2/node1/ship/segments.tsv`(팔별 총량) · `ec2/node1/ship_run.log` · `ec2/node*.round.log`.
올린 binlog 사본은 크기 때문에 S3 에만 둔다 — `s3://shadowfit-measure-055447613012/shadowfit/shipcost-ec2-20261108-024203/shipstore/`.

🟡 `node*.round.log` 의 `bootstrap.sh: line 281: … command not found` 줄들은 bootstrap 의 `.env` 생성 단계에서 나온 것이다.
같은 로그에서 «compose 해석 확인 ✅» 가 나왔고 `ROLE=db` 경로는 끝까지 갔다 — 이 실험 값에는 영향이 없다고 본다(원인은 따로 안 봤다).
