# #276 ㄷ(자연키 PK) 비용 — EC2 본 측정 (2026-11-08 ~ 11-09)

설계 [`docs/decisions/r276-lock-root-cause-fix.md`](../../../docs/decisions/r276-lock-root-cause-fix.md) §5.
rig [`loadtest/r276-natpk/`](../../r276-natpk/). 이 디렉터리는 그 rig 를 EC2 에서 무인으로 돌린 원본이다.

ㄴ(RC)을 고를 때 «ㄷ 이 더 근본적이지만 치르는 값 네 줄이 전부 미측정» 이라 보류했다. 그 네 줄 중
① 삽입 · ② PK 재구성 · ③ 읽기 셋을 쟀다.

## 0. 판정

**ㄷ 의 상시 비용(삽입·읽기)은 거의 없거나 오히려 이득이고, 비용은 한 번 치르는 PK 재구성에 몰려 있다.**

| 단계 | 결과 | 한 줄 |
|---|---|---|
| ① 삽입 | 4조건 중 3조건에서 B 가 **+15~22% 빠름**. 버퍼풀 초과 · 활성 세션 675 에서만 B **−10%**(B′ ±0) | «행 전체가 흩어지면 크게 느려진다» 는 가설은 이 규모에서 **안 맞았다** |
| ② 재구성 (1,000만 행 · 약 21GB) | pt-osc **약 16분**(binlog +17GB) · 네이티브 INPLACE **약 100분**(binlog +0.85GB). 둘 다 쓰기 실패 0 · 최대 공백 약 1.2~1.35초 | 네이티브가 pt-osc 보다 **약 6배 느리다**. 기본 설정이면 네이티브는 **매번 실패**(1799) |
| ③ 읽기 | 세션 단위: 차이 없음(데움 p50 4.8~5.2ms). id 단건: B 가 데움 기준 +0.02~0.07ms | 상시 읽기 비용은 무시할 만하다 |

이 결과로 §5-1 의 «ㄷ 이 싸면 ㄴ 을 다시 연다» 조건이 걸린다. **다시 열지는 사용자 결정이다** — 이 문서는 값까지만.

### 1-1. 1차 라운드에서 팔 N 이 왜 실패했나

```
ERROR 1799 (HY000) at line 1: Creating index 'PRIMARY' required more than
'innodb_online_alter_log_max_size' bytes of modification log. Please try again.
```

`innodb_online_alter_log_max_size` 기본값은 128MiB 다. 네이티브 INPLACE 는 DDL 이 도는 동안 들어온 쓰기를
이 로그에 쌓아 두었다가 끝에 반영하는데, 약 2시간 도는 동안 writer 가 쓴 양이 128MiB 를 넘었다.
**약 2시간을 돈 뒤에 실패하고 모두 되돌린다** — 운영에서 겪으면 2시간을 버리고 원점이다.

이 오류는 1차 rig 에서 `*_ddl.log` 가 아니라 `mysql_stderr.log` 로 빠져 그때는 «원인 미확인» 이었다.
재측정 rig(`70f91cd2`)가 DDL 오류를 판별 로그에 남기도록 고치고 한도를 2GiB 로 올렸다.
**2GiB 는 «통과하는 값» 이지 «필요한 최소값» 이 아니다** — 실제로 얼마가 필요했는지는 안 쟀다.

## 2. ① 삽입 처리량 (c7i.xlarge · MySQL 8.0.46)

무대: 팔마다 과거 세션 2,000개 × 600행 = 120만 행을 깔고, 그 위에 20만 행을 동시 세션 68 / 675 개로 배치 삽입.
체제: 메모리 안(버퍼풀 4GB) · 버퍼풀 초과(64MB). 판: 팔 A·B·B′ × 4블록, 블록 0 버림, 라틴 방격.
값: 본블록 1~3 의 중앙값, 괄호는 A 대비, 대괄호는 세 블록 범위.

| 체제 · 활성 세션 | A (지금) | B (ㄷ) | B′ (B − idx_session_timestamp) |
|---|---|---|---|
| 메모리 · 68 | 9,039 행/초 [8,814~9,182] | **10,705 (+18%)** [10,586~11,224] | 10,560 (+17%) |
| 메모리 · 675 | 8,604 [8,572~8,638] | **9,859 (+15%)** [9,412~10,202] | 10,361 (+20%) |
| 버퍼풀 초과 · 68 | 8,903 [8,753~9,226] | **10,660 (+20%)** [10,592~10,762] | 10,903 (+22%) |
| 버퍼풀 초과 · 675 | 8,642 [8,564~8,689] | **7,812 (−10%)** [7,795~7,854] | 8,664 (±0%) |

네 조건 모두 A 와 B 의 세 블록 범위가 겹치지 않는다.

| 체제 · 활성 세션 | 디스크 읽기 A / B / B′ | 페이지 분할 A / B / B′ | 배치 p99 ms A / B / B′ |
|---|---|---|---|
| 메모리 · 68 | 71 / 119 / 63 | 34,605 / 30,302 / 29,609 | 929 / 535 / 522 |
| 메모리 · 675 | 85 / 125 / 68 | 34,693 / 30,601 / 29,931 | 837 / 726 / 629 |
| 버퍼풀 초과 · 68 | 2,709 / 2,056 / 1,585 | 34,787 / 30,361 / 29,656 | 113 / 81 / 83 |
| 버퍼풀 초과 · 675 | **3,274 / 10,576 / 9,312** | 35,233 / 30,984 / 29,974 | 123 / 156 / 144 |

- 흩어짐이 값을 치르는 건 **버퍼풀을 넘고 + 동시 세션이 많을 때** 뿐이었다. 그때 디스크 읽기가 A 의 3.2배로 뛴다
- 페이지 분할은 모든 조건에서 B 가 A 보다 **적다**(약 −12%). 왜 그런지는 안 봤다
- ⚠️ **메모리 체제의 배치 p99 가 버퍼풀 초과 체제보다 7~8배 크다**(A 929ms vs 113ms). 풀이 클수록 꼬리가 길어지는
  역전이다 — 더러운 페이지 플러시 정지일 수 있지만 **확인 안 했다**. 처리량 비교에는 영향이 없으나 p99 는 이 이유로
  체제 사이에 비교하지 않는다
- 무대가 120만~140만 행이다. 1억 행 규모에서 B 의 흩어짐이 얼마가 되는지는 이 값으로 말할 수 없다

## 3. ② PK 재구성 (m6i.xlarge · 1,000만 행)

서버는 `DROP PRIMARY KEY, ADD PRIMARY KEY(session_id, rep_number, timestamp_sec, created_at), ALGORITHM=INPLACE, LOCK=NONE`
을 **받았다**(08-12 `PARTITION BY` 의 1845 거절과 다르다). 그래서 팔이 셋이다.

- **N** — 네이티브 INPLACE, writer 가 쓰는 중
- **N0** — 네이티브 INPLACE, writer 없음(쓰기가 DDL 을 얼마나 늦추는지 보는 기준)
- **P** — pt-online-schema-change 3.6.0, writer 가 쓰는 중

| 팔 | 판 | DDL 소요 | writer 시도 · 실패 | 최대 쓰기 공백 | binlog 증가 | 디스크 최대 |
|---|---|---|---|---|---|---|
| **P** | 4판 (11-08 버림·r2·r3 + 11-09 r1) | **975.7~977.5초 (약 16분)** | 2,995~3,015 · 0 | 1,235~1,247ms | **+17,103~17,105MB** | 79~97GB |
| **N** | r1 · r3 · r5 | **5,958.9 · 5,992.9 · 5,996.5초 (약 100분)** | 25,067~25,212 · 0 | 1,226~1,352ms | +854~859MB | 84.5~84.7GB |
| **N0** | 버림 · r2 · r4 | 6,118.5 · 6,138.7 · 6,132.2초 | — | — | 0 | 약 82.6GB |

- **네이티브가 pt-osc 보다 약 6.1배 느리다.** «온라인 DDL 이 되면 pt-osc 가 필요 없다» 는 직관이 이 DDL 에선 거꾸로다.
  이유는 안 쟀다 — PK 를 바꾸면 클러스터드 인덱스 전체를 정렬해 다시 만드는데, 그 정렬(`innodb_sort_buffer_size` 기본 1MiB)이
  느린 게 아닐까 의심한다. 가설일 뿐이다
- **N0 이 N 보다 약 2.5% 느리다.** 판을 번갈아 돌렸으니(N0·N·N0·N·N0·N) 순서 효과로 보긴 어렵지만, 쓰기가 있는 쪽이
  빠를 이유는 모른다. 확실한 건 «쓰기가 DDL 을 늦추지는 않았다» 까지다
- **최대 쓰기 공백은 두 방식 모두 약 1.2~1.35초** 로 같다. writer 의 한 번 시도 최대가 약 1~1.15초라, 둘 다 DDL 이 쓰기를 막은 흔적은 없다
- 비용의 모양이 다르다 — **P 는 시간이 짧은 대신 binlog 를 17GB 쓴다**(복사하는 행이 전부 binlog 로 간다).
  리플리카가 있으면 이 17GB 가 그대로 복제 지연이 된다. **N 은 binlog 가 적은 대신 100분을 돌고, 그동안 쓰기 양이
  온라인 로그 한도를 넘으면 끝에서 실패한다**(§1-1)
- 디스크 최대는 원본 `tpl_A`(약 21GB)와 앞 판의 binlog 까지 포함한 값이라 **DDL 하나의 순수 비용이 아니다**

### 3-1. 08-12 online-ddl 과 직접 비교는 안 된다

설계 §5-4 는 «같은 시더·규모라 직접 비교된다» 고 적었지만 **행 크기가 다르다**. 08-12 는 1,000만 행에 디스크 최대
약 2.4GB(행당 약 240B), 이번은 `tpl_A` 가 data 20.5GB + index 0.68GB = 행당 **2,119B** 로 약 9배다(관절 좌표 JSON 이 들어 있다).
같은 1,000만 행이라도 옮기는 바이트가 9배라 08-12 의 pt-osc 112초와 이번 976초를 나란히 놓으면 안 된다.

## 4. ③ 세션 단위 읽기 (② 무대 그대로 · 표본 300 · 3판)

버퍼풀을 비우려고 MySQL 을 재시작한 직후(차가움)와 같은 표본을 한 번 더(데움). 값은 3판의 p50 중앙값.

| 조회 | 표 | 실행 계획 키 | 차가움 p50 | 데움 p50 |
|---|---|---|---|---|
| 세션 전체 (`findFramesBySessionId` 형태, 600행) | A | **`uk_pose_event`** | 14.30ms | 5.15ms |
| 〃 | B | `PRIMARY` | 13.79ms | 4.81ms |
| 〃 | B′ | `PRIMARY` | 11.56ms | 5.20ms |
| id 단건 (`findJointCoordinatesById` 형태) | A | `PRIMARY` | 1.48ms | 0.142ms |
| 〃 | B | `idx_id` → PK | 2.13ms | 0.166ms |
| 〃 | B′ | `idx_id` → PK | 2.14ms | 0.216ms |

- 세션 조회는 세 표 사이 차이가 작다(데움 기준 ±7%). B′ 의 차가움 −19% 는 3판뿐이라 «중복 인덱스를 빼면 빨라진다» 고 말하기엔 약하다
- ⚠️ **설계 §5-4 의 전제가 틀렸다** — A 의 세션 조회는 `idx_session_timestamp` 가 아니라 **`uk_pose_event`** 를 탄다
  (`uk_pose_event` 도 `session_id` 로 시작한다). 그래서 A 에서도 `idx_session_timestamp` 는 이 조회에 안 쓰인다
- id 단건은 B 에서 보조 인덱스 → PK 두 번 찾기가 되어 차가움 +44%, 데움 +0.02~0.07ms. 절대값이 1ms 미만이다

인덱스 크기 (`stats.jsonl`): A 681MB · B 646MB · **B′ 363MB** — `idx_session_timestamp` 를 빼면 보조 인덱스가 약 절반이 된다. data 는 셋 다 약 20.5GB.
