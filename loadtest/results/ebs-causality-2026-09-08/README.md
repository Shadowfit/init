## 2. 판정 — EBS 상한은 원인이 아니다

| 팔 | 최대 `write_KiBps` | gp3 기본 상한(128,000) 대비 | 박스 멈춤 |
|---|---:|---:|---|
| A (기본) | **1,239.4** | **0.97%** | **718초 통째로**(14:09:43→14:21:41) |
| B (상한 8배) | 3,035.4 | 2.37% | 74초 · 217초 · 44초 |

- **팔 B 도 멎었다** → 설계 §5 의 「🔴 인과 반증」 조건이 성립한다.
- 더 센 것은 **팔 A 조차 상한 근처에 못 갔다는 것**이다. 08-28 이 두 사고 모두에서 본
  **125MiB/s 눌러붙음이 이 라운드에서는 재현되지 않았다**(40~100배 차이).
- 하트비트 실패 첫 시각은 두 팔 다 **부하 시작 직후**(A 14:09:49 · B 14:09:55)이고,
  AWS 는 내내 `running/ok/ok` 로 봤다 — **08-28 과 같은 서명**이다. 단 이번엔 **리부트 없이
  스스로 돌아왔고** 판은 정상 완료했다(203/203 계정 · 부하 20분 완주).

🔴 **해석 한계**: 디스크 폴러가 멎은 것이 곧 커널이 멎었다는 뜻은 아니다. 이 폴러는 7초마다
`docker stats`·`docker exec` 를 부르므로 **docker 데몬이 막히면 폴러도 같이 멈춘다.**
「박스가 얼었다」와 「docker 가 막혔다」를 이 판은 **못 가른다.**

## 3. 원 질문의 채널이 처음으로 울렸다

08-28 은 두 라운드 다 박스가 먼저 죽어 이 채널을 **한 번도 못 봤다.**

| 팔 | `RestartCount` | 시각(UTC) | `OOMKilled` | `ExitCode` |
|---|---|---|---|---|
| A | 0 → **1** | 14:21:36 | **false** | — |
| B | 0 → **1** → **2** | 14:12:07 · 14:29:59 | **false** | 0 |

`entrypoint.sh` 의 `wait -n` 설계(워커 하나가 죽으면 컨테이너 전체가 내려간다)와 맞는 모양이지만
🔴 **어느 워커가 왜 죽었는지는 안 갈렸다** — 재기동이 이전 로그를 지운다. 로그 영속화가 선행이다.

## 4. 🆕 새 원인 후보 — 캡이 호스트 RAM 보다 크다

| | 값 |
|---|---|
| `shadowfit-ai` mem_limit | **20,971,520,000 B ≈ 19.5 GiB** |
| 호스트 RAM (`c7i.2xlarge`) | **15,708 MiB ≈ 15.3 GiB** |
| 스왑 | **0** |

캡이 물리 RAM 보다 크면 컨테이너는 **자기 한도에 영영 못 닿고**(`OOMKilled=false`), 압력은
**호스트 회수 경로**로 샌다. 회수 효율이 그 결과를 그대로 보여준다:

| 팔 | `pgscan_kswapd` | `pgsteal_kswapd` | 스캔/회수 |
|---|---:|---:|---:|
| A | **40,807,151,780** | 181,497,338 | **225 : 1** |
| B | 1,442,206,428 | 75,231,547 | 19 : 1 |

부하 종료 **78분 뒤에도** 팔 A 는 `kswapd0` CPU **65%** · load average **105**(8 vCPU 박스)였다.
스왑이 없어 익명 페이지를 못 내보내니 kswapd 가 회수 못 할 페이지를 계속 훑는 **회수 스래싱**이다.

**08-28 의 관측 넷을 한 기제로 설명한다:**

| 08-28 이 본 것 | 이 기제의 설명 |
|---|---|
| AWS 는 `running/ok/ok` | 하이퍼바이저 관점에선 실제로 정상 |
| SSH·앱 포트 전부 무응답 | kswapd 스래싱이 박스 전체를 세운다 |
| `OOMKilled=false` | **캡 > RAM 이라 cgroup 한도에 안 닿는다** |
| 「메모리는 안 튀었다(AI 604MB)」 | **컨테이너 사용량**을 봤지 **호스트 회수 압력**을 안 봤다 |

출처는 `bootstrap.sh` 의 `AI_MEM_LIMIT` 기본값 **20000m** 이다 — P6 의 `c7i.4xlarge`(32GiB)엔
맞지만 `c7i.2xlarge`(15.3GiB)엔 안 맞는다. **08-28 도 같은 조합이었다.**

🔴 **정황이지 인과가 아니다.** 「캡을 내리면 멈춤이 사라지는가」는 **미측정**이다(§6).
08-28 의 125MiB/s 를 이 기제로 설명하려면 **회수 중 더티 페이지 라이트백**을 걸어야 하는데
그것도 **안 걷었다.**

## 5. 라운드가 도중에 잡은 결함 셋

### 5-1. `--dry-run` 은 볼륨 파라미터 조합을 검증하지 않는다

매니페스트 §2 가 그걸 확인 수단으로 적어뒀는데 **틀렸다.** 비율을 위반한 조합
(`Iops=3000` + `Throughput=1000`)도 `DryRunOperation` 으로 통과했다. **음성 테스트가 없었으면
「조합 확인됨」으로 잘못 닫을 뻔했다.** 실제 확인은 기동 후 `describe-volumes` 로 했다.

### 5-2. `JWT_EXPIRATION_TIME` 이 컨테이너로 안 넘어갔다 → 고침(`ba334222`)

`.env` 를 12300 으로 고치고 backend 를 `--force-recreate` 했는데 **발급 토큰의 `exp` 가 그대로
1800** 이었다. `docker-compose.yml` 의 backend `environment:` 에 그 변수가 없어서 `.env` 값이
compose 치환에만 쓰이고 컨테이너 환경엔 안 들어간다 — **컨테이너 배포에서는 그 손잡이가 없는
것과 같았다.** 토큰을 디코드해 보고서야 알았다. 한 줄 추가로 고쳤고, 재확인 후 **12,300초**를
실측했다. 게이트도 실기에서 통과를 찍었다(`남은 11,757s / 필요 1,800s`).

### 5-3. 부하 rig 의 실패 경로가 `sleep` 을 건너뛴다

로그인 실패 시 `continue` 가 `sleep "$PREP_SLEEP"` 를 지나쳐서, 첫 실패가 나면 **203건이 1초
만에 소진**된다(판 2 에서 실제로 그렇게 됐다 — `emails` 203개가 전부 같은 `date +%s`).
레이트리밋 보호가 실패 구간에서만 사라지는 모양이라 **원인 진단을 어렵게 만든다.**

## 6. 🔴 못 한 것 — 캡 축은 한 판도 안 돌았다

판 2(팔 A `AI_MEM_LIMIT=8000m` ↔ 팔 B `20000m`, 나머지 동일)를 걸었으나 **계정 준비가
`0 / 203` 으로 중단**됐다. 원인은 **측정자의 조작 실수**다:

준비 확인을 `curl -s -m 5 -o /dev/null localhost:9090/actuator/health` 로 했는데, 이 명령은
**포트가 열리기만 하면 종료코드 0** 이라 HTTP 상태와 무관하게 통과한다. Spring 이 다 뜨기 전에
부하를 걸었고, 첫 로그인이 즉시 실패한 뒤 §5-3 때문에 203건이 1초에 타버렸다.
(같은 무대에서 나중에 `{"status":"UP"}` 확인 후 signup·login 둘 다 200 으로 재현했다.)

**그래서 §4 는 정황에서 멈춘다.** 다음 라운드의 1순위는 그대로 남는다 —
**캡 하나만 다르게 놓고 멈춤이 사라지는지 보는 것.** 준비 확인은 `{"status":"UP"}` **문자열**로.

### 그 외 안 한 것

- **팔 A′(08-28 커밋 `437ff913`) 대조군** — 시간이 모자라 못 돌렸다. 다만 §4 가 서면서
  「왜 08-28 과 다른가」의 1순위 후보가 코드(#684)에서 **캡**으로 옮겨갔고, **캡은 두 라운드가
  동일**하므로 A′ 로는 안 갈린다
- **게이트 2판째** — 반증이 **1판짜리**다([[feedback_measure_design_needs_repeats]])
- **회수 중 디스크 라이트백** — 08-28 의 125MiB/s 를 §4 로 설명하려면 필요한데 안 걷었다
- **어느 AI 워커가 왜 죽었나** — 재기동이 로그를 지운다(§3)

## 7. 운영 기록

- **회수기(§4-ㄴ)가 값을 했다** — 팔 A 는 SSH 가 12분간 죽었는데 **그 구간까지의 데이터가
  부하기에 살아남았다.** §2 의 팔 A 숫자는 전부 거기서 나왔다(`armA/disk_run1.csv` 73표본 ·
  `heartbeat.csv` 208회 중 92회 실패). 08-28 이 「영영 못 메운다」던 자리다.
- **디스크 폴러(§4-ㄱ)가 실기 초회에 정상 동작** — 장치 `nvme0n1` 자동 해석, 16열 전부 채워짐.
- 🔴 **리부트가 워치독을 지운다** — user-data 는 부팅 시 1회만 돈다. 판 사이 리부트 후 재무장했다.
  🔴 **그 뒤 재연장에서 `pkill` 로 옛 워치독을 죽인 뒤 새것이 안 붙어 대상 2대가 잠시
  무보호였다.** 확인 명령으로 발견했고, 부하기가 4분 뒤 자멸 예정이라 판을 살릴 수 없어
  그 자리에서 종료를 택했다.
- **종료 확인**: 4대 전부 `terminated` · 태그로 남은 볼륨 **0개**(프로비저닝 볼륨 포함) ·
  계정 전체 실행 중 인스턴스 **0대**.
- **요금: 미기입** — Cost Explorer 사후 조회로 `INSTANCES.txt` 에 채운다.
