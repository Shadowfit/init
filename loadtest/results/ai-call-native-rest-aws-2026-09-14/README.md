## 0. 한 줄

4차가 AI 쪽 호출당 +1~3 cpu-ms 를 «REST 미러가 gRPC 서비서를 감싼 겹의 대가» 로 읽었는데, **겹을 뺀 팔(C·native)이 미러(B)와
AI CPU/호출에서 겹친다** — c=1 델타 −1.54~+0.97, c=8 −0.25~+0.77(둘 다 판별 불가). **겹은 대가가 아니었다.**
대가는 **REST 경로 자체**에 있다: C−A(REST 고유)가 c=8 에서 **+1.49~2.53 cpu-ms/호출**(안 겹침), 포화 처리량은 A 226.5 → C 197.8 재부착/초(블록 평균, **−12.7%**).
그리고 **중첩 JSON(D·nested)은 더 비싸다** — C−D 가 c=1 −1.88~−0.29, c=8 −1.76~−1.19(둘 다 안 겹침, D 가 손해). 본문이 10.7% 작아졌는데도 그렇다.
설계 §6 의 넷 중 **세 번째 문장**이다 — 4차 §4-2 의 «구조적으로 예정» 해석은 **틀렸고**, 이 문서가 그것을 정정한다(§7).

| 뺄셈 | 뜻 | c=1 | c=8 |
|---|---|---|---|
| **B − C** | 겹(proto 재조립 + 서비서 호출)의 대가 | −1.54 ~ +0.97 🟡 겹침 | −0.25 ~ +0.77 🟡 겹침 |
| **C − A** | REST 라서 내는 값(JSON 파싱·pydantic·스레드풀) | −0.00 ~ +2.67 🟡 겹침(아슬) | **+1.49 ~ +2.53 ✅ 안 겹침** |
| **C − D** | 이중 인코딩의 대가 (음수 = nested 가 더 비쌈) | **−1.88 ~ −0.29 ✅ 안 겹침** | **−1.76 ~ −1.19 ✅ 안 겹침** |

### 2-1. 읽기

1. **B 와 C 가 같다.** 미러가 하던 «pydantic 객체 → proto 메시지 재조립(랜드마크 1,221개) → 서비서» 를 빼도 AI CPU 가 안 준다.
   4차가 «구조적으로 예정» 이라고 적은 그 겹은 cgroup 차분으로 **안 보이는 크기**다. 즉 4차의 B−A 델타는 처음부터 REST 경로의 값이었다.
2. **REST 고유 비용은 있다** — c=8 에서 호출당 1.5~2.5 cpu-ms. c=1 은 블록별 델타가 +0.40 / 0.00 / +2.67 / −0.00 / +1.07 로 **둘이 0 에 붙어 있다** — 칸이 1~2초라 cgroup 차분의 분해능이 호출당 1ms 안팎을 못 가른다. «없다» 도 «있다» 도 아니고 판별 불가다. c=8(칸 3~5초, 표본 800)에서는 5블록 전부 +1.49 이상이다.
   남는 후보는 설계 §3-1 이 못 가른다고 적어둔 셋 — JSON 본문 파싱(Starlette `request.json()` = 표준 `json.loads`) · pydantic 검증 · 동기 엔드포인트의 anyio 스레드풀 전환. 이 라운드도 그 안을 안 가른다.
3. **중첩 JSON 은 손해다.** 본문은 10.7% 작아졌는데 AI CPU 는 c=1 +0.3~1.9, c=8 +1.2~1.8 더 든다. 기제 후보: B·C 는 114KB 중 대부분이 **문자열 하나**라 표준 JSON 파서가 하는 일이 «긴 문자열 복사» 이고 그 안은 `orjson`(C)이 푼다; D 는 표준 파서가 **dict 1,221개 × 필드 5개**를 파이썬 객체로 직접 만들고 pydantic 이 `list[dict]` 를 훑는다. «파싱을 한 번 덜 한다» 가 «느린 파서에 더 많은 일을 준다» 로 뒤집힌 것으로 읽힌다 — 🟡 프로파일 없이 자리만 맞춘 해석이다.
4. **4차와 자릿수가 같다.** 4차 c=1 A 7.41~8.74 / B 8.80~10.56, 이번 7.80~9.07 / 8.93~10.04. 라운드 간 비교는 ㉠(calib 병기)로만 — 4차엔 calib 가 없어서 비율은 못 잰다.

## 3. 처리량 (재부착/초, 블록 5개 범위 · 괄호는 블록 평균)

| c | A·grpc | B·mirror | C·native | D·nested |
|--:|---|---|---|---|
| 1 | 63.3 ~ 89.6 (73.8) | 52.9 ~ 77.3 (67.0) | 47.9 ~ 78.8 (61.8) | 50.6 ~ 72.1 (63.0) |
| 8 | 208.1 ~ 243.2 (**226.5**) | 180.1 ~ 205.2 (190.7, −15.8%) | 175.6 ~ 212.3 (197.8, **−12.7%**) | 176.5 ~ 193.9 (184.2, −18.7%) |

- c=8 에서 **B−A 만 안 겹친다**(−63.1~−3.2). C−A 는 −36.0~−19.3 로 델타의 부호는 5블록 전부 음수지만 두 팔의 **범위가 한 칸 겹쳐**(A 하한 208.1 < C 상한 212.3) 규칙 1 로는 판별 불가다. B−C·C−D 는 겹침.
- 4차의 −15% 는 B/A 의 값이고 이번에도 −15.8% — **재현**. C 는 −12.7%, D 는 −18.7%. 백분율은 블록 평균이라 서사용이지 판정이 아니다.
- AI 컨테이너 CPU 점유(코어 환산)는 c=8 에서 네 팔 다 2.0~2.5 — 워커 3 이 포화에 가까운 같은 무대다.

| 1 | 5.11 ~ 5.59 | 7.21 ~ 8.34 | 7.47 ~ 9.26 | 7.88 ~ 9.27 | **+2.29 ~ +3.77 ✅** | 🟡 | 🟡 |

c=1 의 C−A +2.3~3.8ms 는 2차·3차·4차의 B−A(+1.8 / +1.4 / +1.2~3.9)와 같은 자리다 — 지연 축에서도 «겹을 빼도 그대로» 다.

### 4-2. nginx CPU/재부착 — B·C·D 에서 같은가

c=1 0.57~0.61 · c=8 0.42~0.47, 세 REST 팔이 겹친다(D 가 c=8 에서 0.007~0.042 만큼 낮다 — 본문 10.7% 의 몫으로 읽히지만 크기가 작다). 4차의 0.50~0.73 과 같은 자리. grpc 칸의 0.02~0.17 은 nginx 를 안 거치는 팔에서의 배경값이다.

### 4-3. backend CPU/재부착 — 판별 불가 (예상대로)

c=1 16~45 · c=8 16~23, 네 팔 전부 겹친다. 4차 §4-1 과 같은 이유(칸 1~5초, JIT·백그라운드가 차분에 섞임). C·D 는 Spring 전송 계층을 안 바꿨으므로 이 라운드가 물을 자리도 아니다.

### 4-4. Start 콜백 — 보조

c=8 에서 C−A 가 +16~46ms 로 안 겹치나(B−A 는 겹침), start 는 fire-and-forget 이라 판정 밖(설계 §3-3). c=1 은 전부 겹침.

## 6. 안 한 것 · 못 하는 말

- **C 의 잔여 내부 분해** — JSON 파싱 ↔ pydantic ↔ 스레드풀. 프로세스 안 계기가 필요하고 팔에 비대칭으로 붙는다. §2-1 3번의 «표준 파서 ↔ orjson» 은 **가설**이다.
- **개방 루프·절대값** — 4차와 같다. 이 무대의 값은 calib cpu 12.88M 과 함께만.
- **Spring 쪽 CPU** — 판별 불가.
- **처리량의 C−A** — 부호는 5블록 전부 음수지만 규칙 1 로는 못 가른다. «REST 로 가면 포화 처리량이 준다» 는 B 로만 말할 수 있고, C 는 «같은 방향, 판별 불가» 다.
- **채택** — 이 라운드도 결정하지 않는다.

## 7. 이 결과가 바꾸는 서사

1. **4차 §4-2 의 «구조적으로 예정» 은 틀렸다.** 미러의 겹은 측정 가능한 대가가 아니었고, 4차의 AI 쪽 +1~3 cpu-ms 는 REST 경로 자체의 값이었다. 4차 README §4-2 와 empirical-comparison §11-2 의 그 문장은 이 문서를 가리키며 정정한다.
2. **«REST 로 정리하면 얼마를 내나» 의 답이 미러 값 그대로다** — 재부착 +2~4ms(c=1) · AI 호출당 +1.5~2.5 cpu-ms(c=8) · 포화 처리량 −13~16%(블록 평균). 네이티브로 다시 짜도 안 줄어든다는 것이 이 라운드의 내용이다. 줄이려면 코드 구조가 아니라 **파서·검증 경로**(예: 본문을 pydantic 의 Rust JSON 파서로 직접 넘기기, 비동기 엔드포인트) 를 바꿔야 하는데 그건 잰 적 없다.
3. **계약을 «REST 답게» 고치면(중첩 JSON) 오히려 손해다.** 전선 −10.7% 가 CPU +1.2~1.8 cpu-ms 로 돌아왔다. REST 를 고른다면 지금의 «문자열 안의 문자열» 계약을 유지하는 편이 이 무대에서는 싸다.
4. 채택 판단에 오르는 것: 위 2·3 + 라우팅 이원화 논거(변함없음) + gRPC 근거 넷의 상태(§11-2, 변함없음). **결정은 사용자 몫.**
