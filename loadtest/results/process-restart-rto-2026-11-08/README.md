# 프로세스 재기동 RTO — mysqld 가 죽은 순간부터 다시 쿼리를 받기까지 (2026-11-08, EC2)

설계 문서: [`../../../docs/decisions/rpo-rto-targets.md`](../../../docs/decisions/rpo-rto-targets.md) §4 첫 줄 · §6-3 (목표 RTO)
무대: **EC2 `m6i.xlarge` 1대** · gp3 200GB · MySQL **8.0.46**(`mysql:8.0`) · `flush=1`·`sync_binlog=1` · binlog ROW ·
버퍼풀 2GB · redo 용량 2GB · RUN_ID `restart-ec2-20261108-060158` · 커밋 `22ce55f4` · 12판(버림 3 + 본판 9)

질문: OOM kill·크래시로 mysqld 만 죽고 디스크는 남았을 때(문서 §4 «프로세스 죽음»), 다시 쓸 수 있기까지 얼마나 걸리나?
그 시간은 죽는 순간 «디스크 반영이 덜 된 변경(redo)» 양에 따라 늘 것으로 예상했다.

## 0. 한 줄

**쉬는 중 1.3초 · 가정 피크(초당 45행) 1.9~2.4초 · 최대 쓰기 33.6~35.1초 — 재기동 시간은 쌓인 redo 양을 따라간다. 잃은 트랜잭션은 0.**
목표 RTO 19초(§6-3)는 가정 피크에선 맞고, 최대 쓰기에선 못 맞춘다.

- stress 는 체크포인트가 쓰기를 못 따라가 redo 가 용량(2GB)의 약 3분의 2 까지 쌓인 상태였다

## 2. 목표 RTO 와 나란히 (§6-3)

| 상황 | 재기동 | 목표 19초 |
|---|---|---|
| 쉼 | 1.3초 | ✅ |
| 가정 피크 (초당 45행) | 1.9~2.4초 | ✅ |
| 최대 쓰기 (4연결 240초) | 33.6~35.1초 | ❌ |

19초는 AI→Spring 결과 전달 재시도 한도(약 19초)에서 왔다 — 넘으면 방금 끝난 운동이 `FAILED` 가 된다.
최대 쓰기에서 못 맞추는 걸 어떻게 할지(redo 용량·체크포인트 설정 등)는 **정하지 않았다** — 재기동 시간을 줄이는 값은 평소 쓰기 비용과 맞바꾸는 것이라 따로 재야 한다.

## 3. 조건 — 인용할 때 떼면 안 되는 것

1. **감시·사람 시간 0.** 죽이고 바로 `docker start` 했다. 운영의 `restart: unless-stopped` 가 다시 띄우기까지의 시간은 안 쟀다
2. «죽음» 은 `docker kill`(SIGKILL) — 컨테이너만 죽고 호스트·볼륨은 남는다. 호스트 상실은 [다른 실험](../hostloss-rpo-2026-11-07/README.md)
3. paced 는 문서 §8-1 **가정** 피크(측정 아님), stress 는 4개 연결이 240초간 최대 속도 — 상한 확인용이지 운영 값이 아니다
4. 🟡 **redo 적용에 걸린 시간만 따로는 못 뽑았다.** 서버 로그에서 «복구 시작 · redo 적용 끝» 시각을 뽑으려 했는데(`recov_start_ms`·`redo_done_ms`)
   전부 비었다 — 로그 문구 매칭이 8.0.46 출력과 안 맞은 것으로 보인다(확인 안 함). 그래서 «34초 중 redo 적용이 몇 초» 는 말할 수 없다
5. 버퍼풀 2GB · redo 2GB 는 rig 의 값이다. 운영 설정에선 쌓이는 redo 상한이 달라 stress 의 숫자가 달라진다
6. 🟡 `round.log` 의 `bootstrap.sh: line 281: ... command not found` 는 이 rig 이 쓰지 않는 단계의 오류다 — 측정과 무관
