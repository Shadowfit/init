## 0. 한 줄

**nginx 홉은 싸다(0.1~0.8ms)** — 이건 두 판이 일치하고 도구 오프셋도 안 낀다.
**작은 페이로드의 프로토콜 비용도 확정**(0.45~1.38ms). 그런데 **큰 페이로드의 프로토콜 비용은
판정 불가**로 나왔다 — 대조군이 본 라운드를 뒤집었다. 아래 §4 가 이 라운드의 진짜 결과다.

## 4. 🔴 대조군이 이 표의 절반을 뒤집었다

§3 의 두 델타는 **신뢰도가 다르다**:

- `rest-nginx − rest-direct` → 둘 다 k6. **같은 도구**라 도구 오프셋이 뺄셈에서 사라진다.
- `rest-direct − grpc(ghz)` → k6 대 ghz. 이 차이에 «프로토콜» 말고 **«클라이언트 구현»** 이
  얼마나 섞였는지 이 판만으로는 못 가른다.

하필 두 번째가 이 라운드의 핵심 주장을 받치는 자리라, k6 하나로 두 프로토콜을 다 재는 팔
(`grpc-k6`, `k6/net/grpc`)을 붙여 다시 돌렸다. 결과:

| 동시성 | 크기 | 프로토콜 비용 — 본 라운드(ghz) | 프로토콜 비용 — 대조군(k6끼리) | 판정 |
|--:|:-:|--:|--:|---|
| 1 | S | +0.459 | +0.450 | ✅ **일치** |
| 3 | S | +1.380 | +1.290 | ✅ **일치** |
| 1 | L | +1.073 | **−0.480** | 🔴 **부호까지 뒤집힘** |
| 3 | L | +2.874 | **+0.740** | 🔴 4배 차이 |

| 동시성 | 크기 | nginx 홉 — 본 라운드 | nginx 홉 — 대조군 | 판정 |
|--:|:-:|--:|--:|---|
| 1 | S | +0.103 | +0.208 | ✅ 같은 자릿수 |
| 1 | L | +0.311 | +0.385 | ✅ 일치 |
| 3 | S | +0.269 | +0.385 | ✅ 같은 자릿수 |
| 3 | L | +0.730 | +0.755 | ✅ 일치 |

**읽는 법**: 큰 페이로드(84KB)에서 두 gRPC 클라이언트가 **서로 다른 답**을 준다. 그러면 그
델타는 서버 쪽 프로토콜 차이가 아니라 **클라이언트가 84KB 를 인코딩하는 비용**이 지배한다는
뜻이다 — k6 의 gRPC 팔은 매 반복 JS 객체를 protobuf 로 인코딩해 그 비용이 벽시계에 들어가고,
ghz 는 그 비용을 훨씬 적게 낸다. **둘 다 «Spring 의 Java gRPC 클라이언트» 가 아니다.**

⚠️ 대조군은 `Date.now()` 만 쓸 수 있어(k6 에 `performance` API 가 없다 — 확인함) 해상도가
**1ms** 다. 그래서 백분위가 아니라 **평균**으로 읽었다 — 절단 오차가 뺄셈에서 상쇄되기 때문이다.
같은 이유로 §3 표도 평균으로 맞춰 놓았다(백분위 표는 `*/table.md`).

## 5. 결론 — 이 라운드가 실제로 답한 것

| 질문 | 답 |
|---|---|
| «검증된 nginx 라우팅을 재사용하면 전송 비용을 얼마나 더 내나» | **0.1~0.8ms/호출.** 두 판이 일치하고 도구 오프셋도 안 낀다 — 이 라운드에서 가장 단단한 숫자다 |
| 작은 요청의 프로토콜 비용 | **0.45~1.38ms/호출.** 두 판이 일치 |
| 큰 요청(84KB)의 프로토콜 비용 | 🔴 **이 도구들로는 판정 불가.** 두 gRPC 클라이언트가 다른 답을 준다 |
| «이진화라 빠르다» (지도교수 조언, 설계문서 §1.4) | 작은 요청에선 **방향은 맞다**(gRPC 가 빠르다). 다만 **크기가 1ms 미만**이고, 큰 요청에서 커진다는 주장은 이 판이 **못 받친다** |
| nginx 라우팅이 헤더대로 갈라 보내나 | ✅ [`routing_evidence.txt`](./routing_evidence.txt) — `X-AI-Worker` 0/1/2 로 친 3건이 **각각 다른 프로세스**에서 처리됐다(프로세스별 검출기 풀 초기화 로그가 정확히 3번, 워커마다 한 번씩) |

**제품 관점**: 이 4개 RPC 는 세션당 몇 번 안 일어난다. 호출당 0.5~1ms 는 분 단위 세션에서
의미 있는 차이가 아니다. 즉 이 라운드는 «gRPC 가 빠르다» 를 근거로 gRPC 를 유지하는 논리를
**약화**시키고, «검증된 nginx 라우팅 재사용» 의 비용이 작다는 쪽을 **뒷받침**한다.

🔴 **그렇다고 이 문서가 채택을 결정하지 않는다.** 어느 쪽을 남기고 어느 쪽을 걷어낼지는
설계문서의 결정 로그에서 사용자가 정한다.

## 6. 이 라운드가 안 잰 것

- **절대 처리량 천장.** 닫힌 루프 지연 rig 다.
- **Spring 을 통과하는 종단 지연.** 측정 층을 «AI 직접» 으로 좁힌 결정의 결과다.
- **Spring 의 Java 클라이언트 비용.** §4 가 보여준 대로 클라이언트 구현이 델타를 지배할 수
  있는데, 정작 프로덕션 클라이언트(Java gRPC / Spring WebClient)로는 재지 않았다.
  큰 페이로드 답이 필요하면 **여기서 재야 한다** — 다음 라운드의 1순위.
- **콜백 3개(AI→Spring).** 그 방향은 라우팅 이득이 없어 미러 자체가 없다.
- **워커 3개로 흩어졌을 때의 처리량.** 전 팔을 워커 0 에 고정했다(공정성 장치).
