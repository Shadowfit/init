# ELI5 — 쉽게, 그러나 틀리지 않게

**쉬운 말로 바꾸는 것이지 덜 정확하게 만드는 것이 아니다.** 이 스킬의 실패 모드는
"어렵다"가 아니라 **"쉬워졌는데 틀렸다"** 이다.

## 무엇을 받나

| 입력 | 처리 |
|---|---|
| 이 저장소의 문서·코드 경로 | **먼저 읽는다.** 기억으로 설명하지 않는다 |
| 이슈 번호 · PR 번호 | `gh` 로 본문을 읽고 나서 |
| 일반 개념(GIL·인덱스·fsync 등) | 바로 설명 |
| "면접에서 어떻게 말하지" | 아래 §출력의 4번(진짜 용어)에 무게를 싣는다 |

## 출력 (한국어, 이 순서)

1. **한 줄** — 결론부터. 비유 없이, 사실만.
2. **왜 이게 문제인가 / 왜 필요한가** — 이게 없으면 무엇이 곤란한지. 동기가 없으면
   설명이 그냥 암기거리가 된다.
3. **비유 하나** — 일상 사물로. **하나만 쓴다**(섞으면 더 헷갈린다).
4. 🔴 **비유가 깨지는 곳** — **생략 금지.** 비유를 믿고 한 걸음 더 밀면 틀리는 지점을
   반드시 적는다. 이 줄이 이 스킬의 존재 이유다.
5. **진짜 용어** — 쉬운 말 ↔ 정식 용어 대응표. 면접에서 실제로 쓸 단어를 손에 쥐어준다.

기본은 **짧게**(각 항목 1~3줄). "깊게" 라고 하면 3~4번 사이에 **메커니즘 한 단계**를
더 넣는다 — 그래도 5번은 유지한다.

## 🔴 지켜야 하는 것

- **숫자를 뭉개지 않는다.** "훨씬 빠르다"가 아니라 "4.11배". 원문에 수가 있으면 그대로 들고 온다.
- **원문의 «미검증·추정·상관/인과·조건» 표시를 반드시 살린다.** 이 저장소 문서는 거의 전부
  단서가 붙어 있고, 쉽게 푼다는 명목으로 그걸 떼면 **불확실한 것을 사실로 세탁하는 것**이다.
  「상관이지 인과가 아니다」는 쉬운 말로 옮기되 없애지 않는다.
- **모르면 모른다고 한다.** 메커니즘이 문서에 안 적혀 있으면 지어내지 말고 "여긴 아직 안 갈렸다"로
  둔다. 그럴듯한 인과를 발명하는 것이 ELI5 의 가장 흔한 사고다.
- **조건을 지우지 않는다.** "단일 핫세션에서" · "이 박스에서" 같은 한정이 결론의 절반인 경우가
  많다. 조건이 길면 5번 뒤에 «이 말이 성립하는 조건» 한 줄로 뺀다.
- **면죄부를 쓰지 않는다.** "학생이니까 이 정도만 알면 된다" 류 금지 — 쉽게 설명하는 것과
  기준을 낮추는 것은 다른 일이다.
- **한국어.** 영어 용어는 처음 나올 때만 괄호로 병기한다(예: 교착 상태(deadlock)).

## 안 하는 것

- 이모지·불릿 도배. 4~5개 블록이면 충분하다
- "쉽게 말해서"를 붙여놓고 그다음 문장이 안 쉬운 것 — 그건 안 푼 것이다
- 비유 두 개 이상, 비유 안에서 또 비유
- 원문에 없는 예시 코드 지어내기 — 필요하면 실제 파일에서 인용한다

## 예

```
/eli5 GIL 이 왜 프로세스당 천장을 만드는데
/eli5 docs/decisions/outbox-reliable-messaging.md
/eli5 #603 깊게
/eli5 반동기 복제를 면접에서 어떻게 말하지
```

## 이 저장소에서 특히 조심할 것

- **결정 문서(`docs/decisions/`)는 «결정된 것»이 아니라 «분기점»이다.** 후보와 트레이드오프까지만
  적혀 있는 경우가 많다 — "이 문서에 이렇게 적혀 있다"를 "이렇게 하기로 했다"로 풀면 틀린다.
- **실측값에는 거의 항상 무대 조건이 붙어 있다.** 로컬 박스(2코어) 값과 EC2 값은 다른 물건이고,
  로컬은 절대 처리량을 못 잰다. 숫자를 옮길 때 어느 무대인지 같이 옮긴다.
